Every function in labeling/

One line each, in plain words, in the order they appear in the file. Written from the bodies, not the docstrings — where the two disagree, it says so.

What this package is for.

Stage 1 only writes a row for a day that produced at least one event, so a person who took a weekend off simply has no Saturday. This package gives everyone a row for every date between their first and last sighting — zeros for the quiet ones — and then reads answers/insiders.csv to mark which of those dates fall inside a known attack, and which people are insiders at all. It drops nothing, computes no statistics, and hands the result to Stage 3.

Why the fill has to come first. A day of no activity is an observation, not missing data. The scenario-2 story is somebody who resigns and stops showing up, and their silence is the strongest thing they do — an unfilled table has no row to mark on those days, so the signal would be deleted by construction rather than merely unlearned.

A wart worth knowing. __all__ names the label submodule but nothing in the file imports it, so from labeling import * raises AttributeError unless labeling.label has already been imported some other way. Nothing in the project does this — every caller writes from labeling.label import … — so it has never bitten, but the export list is currently decorative.

Zone 1 — the vocabulary and the two ways this stage can fail

Four module constants and two exception types; nothing here computes anything.

KEY_COLUMNS = ("user", "day") · _RULE = "=" * 78

The first is the pair that identifies a row everywhere in this file — merges, duplicate checks and sorts all take it rather than spelling the two names out each time. The second is just the horizontal line the printed page is boxed with.

WINDOW_START = "start_day" · WINDOW_END = "end_day"

Names for the two date columns of the parsed window table, which exists only inside this module and is never written to disk.

class GroundTruthError(ValueError)

Signals that insiders.csv is wrong: a missing column, no rows matching release 4.2, a window that ends before it starts, or one person filed under two scenarios.

class LabellingError(AssertionError)

Signals that the table this stage built is wrong: rows vanished, a person-date repeated, a blank crept in, or an attack day landed on somebody the answer key never names.

Two types rather than one so a corrupt input file can never be mistaken for a bug in the join.

Zone 2 — turning the answer file into date ranges

⭐ def load_insiders(path: Path, release: str = RELEASE_ID) -> pd.DataFrame

Reads the answer file with every column forced to text, keeps only the rows whose dataset field is the exact string "4.2", and returns one row per attack window as person, scenario number, start date, end date.

Text, not numbers, is the point: read numerically, "4.2" and "4.20" are the same value and two different CERT releases get mixed together.

def _to_day(stamps: pd.Series) -> pd.Series

Parses stamps like 07/07/2010 20:05:29 and discards the clock, leaving midnight of that date.

Doing it once here is what makes "the day is between start and end" literally true of the stored values, instead of true only if every later comparison remembers to strip the time itself.

def _validate_windows(windows: pd.DataFrame, path: Path) -> None

Refuses the file if any range runs backwards, if a scenario number outside 1/2/3 appears, or if one person is filed under two different scenarios.

A person with two ranges is fine and only logs a warning — the ranges simply both count.

Zone 3 — putting the missing days back

⭐ def calendar_fill(daily: pd.DataFrame) -> pd.DataFrame

Gives every person a row for each date between the first and last day they were seen, writing 0 into all the count columns on the dates that had no row, and leaving the rows that already existed exactly as they were.

It also quietly narrows the table: the output keeps only user, day and the known feature columns, so any extra column present in the input is dropped. The docstring's "strict superset" is true of the rows, not of the columns.

def _calendar_index(daily: pd.DataFrame) -> pd.DataFrame

Produces the complete person × date grid by taking each person's first and last day, working out how long their run is, and generating all the dates as one long stretch of integer arithmetic.

Not just speed: there is no per-person branch, so it cannot get one person's first or last day wrong while the other 999 are right.

Zone 4 — attaching the two ground-truth columns

⭐ def attach_labels(daily: pd.DataFrame, windows: pd.DataFrame) -> pd.DataFrame

Appends two small integer columns: one saying whether this date falls inside an attack, one saying which scenario this person belongs to, with 0 for everybody the answer key never names.

They are meant to disagree. An insider's ordinary Tuesday in March is a 0 in the first column and still a 2 in the second — Stage 4 needs the per-person value to balance its split, Stage 7 needs it to break results down by attack type.

⭐ def _window_mask(daily: pd.DataFrame, windows: pd.DataFrame) -> np.ndarray

Produces a true/false answer per row by walking the ~70 attack ranges and, for each, touching only that person's rows — comparing dates with both ends counted as inside.

A range naming somebody who has no rows at all is skipped silently here; the report flags it separately, because that means Stage 1 lost their activity, which is a data problem rather than a labelling one.

def build_labelled_counts(daily, windows) -> pd.DataFrame

Runs the fill and then the marking, in that order, because a day with no events has no row to mark until the fill creates one.

def _require_unique_keys(frame: pd.DataFrame, what: str) -> None

Stops with an error if the same person-and-date shows up more than once, which would multiply into several rows during the merge instead of failing loudly.

Zone 5 — the things that stop the run

⭐ def verify(labelled: pd.DataFrame, before: pd.DataFrame) -> None

Checks five impossibilities and raises on any of them: the table got shorter, a person-date repeated, a blank appeared anywhere, an attack day belongs to somebody benign, or an individual lost rows.

Docstring says four, the body runs five — it was written before the shrunk-user check was added. Everything merely surprising is left to the printed report instead.

def _users_that_lost_rows(after: pd.DataFrame, before: pd.DataFrame) -> list[str]

Compares row counts per person before and after and returns anyone who came out with fewer than they went in with, which should be nobody.

Zone 6 — the numbers and the printed page

@dataclass(frozen=True, slots=True) class LabelStats

An immutable bundle of the seven measurements the printed page needs, gathered once so the headline numbers and the pass/fail lines cannot disagree with each other.

@property def negatives(self) -> int

How many rows sit outside every attack range — everything left after subtracting the marked days.

@property def positive_rate(self) -> float

The fraction of all rows that are inside an attack, which is the imbalance every later stage has to work against. Returns 0.0 rather than dividing by zero on an empty table.

@property def pos_weight(self) -> float

How many ordinary rows there are per attack row.

Printed and then deliberately thrown away: Stage 5 works this out again from its own training rows, because freezing the whole-table figure would smuggle the test set's balance into the loss function.

def compute_stats(labelled, before, windows) -> LabelStats

Walks the finished table once and fills that bundle in, including the list of people the answer key names who nevertheless ended up with no attack day at all.

def format_report(labelled, before, windows, out=None) -> str

Assembles the page the run prints: rows before and after the fill, the date range, the class balance, the per-scenario table and the eight pass/fail lines.

def _scenario_lines(labelled, windows) -> list[str]

Three rows — one per attack type — giving how many people, how many marked days, and the average days each of those people contributes.

Worth reading rather than skipping: it's where you see that one attack type supplies the overwhelming majority of marked days, so any overall score is very nearly a score for that one type alone.

def _check_lines(labelled: pd.DataFrame, stats: LabelStats) -> list[str]

Eight statements about the result — insider count, everyone having at least one marked day, no blanks, no repeats, labels only ever 0 or 1 — each rendered as pass or CHECK.

Nothing here raises: these are the things that are suspicious rather than impossible, and a surprising number is something to look at, not necessarily something wrong.

def _check(label: str, passed: bool, detail: object) -> str

Lays one of those eight statements out as a fixed-width line: the word ok or CHECK, the padded description, then whatever detail was measured.

def format_user_report(labelled, user, windows=None, rows=30) -> str

Shows one person's thirty most eventful days in date order, with <<< beside the ones inside an attack, plus their ranges printed above.

The ranking is the clever bit: days are scored by how much activity they carry, but every marked day is pushed above every unmarked one first — so the last quiet day and the first flagged day always end up adjacent on screen, where a wrong date comparison is obvious.

def _window_lines(windows: pd.DataFrame, user: str) -> list[str]

One line per attack range belonging to that person: the two dates and how many days that covers with both ends counted.

Zone 7 — the command line

def main(argv: Sequence[str] | None = None) -> int

Reads the counts file, loads the answer key, fills and marks, runs the hard checks, writes the parquet, prints the page, and optionally prints one person's days.

Full runs and --sample runs write different filenames on purpose — Stage 1 was bitten by exactly this, when a seven-second development run replaced the real 1,000-user table.

6test_label.py — function by function

The three helpers — building inputs by hand instead of reading files

def _counts(rows: list[tuple[str, str]]) -> pd.DataFrame

Turns a list of person-and-date pairs into a Stage-1-shaped table with all 18 counts set to 1, so a 0 anywhere in a result can only have been inserted by the fill.

def _windows(rows: list[tuple[str, int, str, str]]) -> pd.DataFrame

Builds the parsed range table directly, skipping the CSV — so a test about the marking rule doesn't also depend on file reading working.

def _insiders_csv(path, rows: list[tuple[str, str, str, str, str]])

Writes a miniature real answer file to a temporary folder, including the details column that the loader insists on but never reads.

The marking rule — five tests on where the edges fall

def test_window_is_inclusive_at_both_ends() -> None

Seven days around a three-day attack: the 7th, 8th and 9th must all come out marked and the 6th and 10th must not.

def test_a_window_shorter_than_a_day_still_labels_that_day() -> None

Uses a real case from the dataset — an attack lasting 65 minutes — and requires the whole date to be marked, because the comparison is by date and not by clock.

def test_insiders_ordinary_day_is_negative_but_still_carries_the_scenario() -> None

An insider's March day and their July day: the first unmarked and the second marked, but both still carrying scenario 2. The two columns must not track each other.

def test_benign_user_is_all_zeros_in_both_columns() -> None

Somebody who appears nowhere in the answer key gets zeros in both new columns, stored in the small 8-bit integer type rather than a wider one.

def test_a_window_only_labels_its_own_user() -> None

Two people share a date and only the one the range names comes out marked — the guard against a comparison that forgot to filter by person.

Reading the answer file — four tests on the ways it can be misread

def test_release_filter_compares_dataset_as_a_string(tmp_path) -> None

An answer file holding releases 4.2, 5.2 and 4.20 must yield exactly one row. This is the test that fails the moment the column is read as a number.

def test_timestamps_are_normalised_to_midnight(tmp_path) -> None

A range starting at 20:05 and ending at 03:08 comes back as two bare dates, so nothing downstream has to remember to drop the time.

def test_a_release_with_no_rows_is_an_error_not_an_empty_table(tmp_path) -> None

A file with nothing for this release raises rather than returning an empty table — which would otherwise train a model on zero attack days without a single complaint.

def test_one_user_under_two_scenarios_is_rejected(tmp_path) -> None

The same person listed twice with different scenario numbers is refused, because the per-person column can only hold one value and picking either silently would be a guess.

The fill — five tests on what gets inserted and what must not be

def test_fill_inserts_exactly_the_missing_calendar_days() -> None

Friday, Monday and Tuesday become five rows; the two inserted weekend rows hold zeros and nothing anywhere is blank.

def test_fill_is_per_user_and_never_beyond_their_own_span() -> None

Somebody last seen in January is not expanded out to somebody else's May, which would fabricate months of absence that nothing in the world produced.

def test_fill_preserves_dtypes_and_existing_values() -> None

The rows that already existed keep their values and their storage types, including the one column among the eighteen that holds decimals rather than whole numbers.

def test_fill_makes_a_silent_day_labellable() -> None

Two rows eight days apart inside one attack: marking without filling finds 2 attack days, marking after filling finds 8. This is the entire argument for the ordering.

def test_duplicate_user_days_are_rejected_rather_than_multiplied() -> None

The same person and date twice raises immediately, rather than becoming four rows once the merge runs.

The invariants — two tests that the hard checks work in both directions

def test_verify_rejects_a_positive_day_on_a_benign_user() -> None

An attack day is forcibly written onto somebody the answer key never names, and the run must stop — this is the single join error that would poison every number downstream.

def test_verify_accepts_a_correctly_labelled_table() -> None

A properly built table passes without complaint, and the columns come out in exactly the order the later stages assume: person, date, the eighteen counts, scenario, then the flag.

7The five functions to actually remember

1
calendar_fill

The reason this stage exists. Without it, "the 28 rows before day d" is anything from 28 to 40 actual days depending on how many weekends that person skipped — and an employee who has resigned and stopped showing up produces no rows to mark at all, so their silence becomes invisible by construction.

2
attach_labels

The one place the two ground-truth columns are created, and the one place their difference is decided. Per-day versus per-person is not a technicality: Stage 4 balances its split on the per-person value, and Stage 7 reports per attack type with it.

3
_window_mask

The actual rule, in about fifteen lines: a date is inside if it is on or after the start and on or before the end, compared as dates. Every claim the project makes about what a positive is reduces to this comparison.

4
load_insiders

The release filter is the least obvious failure in the package. Read the dataset column as a number and 4.2 and 4.20 become indistinguishable, so you label other releases' people and miss your own — with no error, no blank, and a model that trains perfectly happily on the wrong answers.

5
verify

The line between "impossible" and "surprising". Five impossibilities stop the run here; everything merely odd — an insider with no attack days, an unexpected positive rate — is printed by the report instead, because a surprising number is something to look at, not automatically something wrong.

The sentence that covers the whole package.

"Stage 2 does two things and refuses to do a third. It puts back the days Stage 1 never wrote, because a silent day is an observation rather than a gap; and it reads the answer key onto those days, per day for the attack flag and per person for the scenario. It drops no rows and computes no statistics — both of those are Stage 3."
