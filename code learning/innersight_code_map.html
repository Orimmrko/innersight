Where everything lives

Not a list of functions — the four rules that let you guess correctly. If someone asks “show me where you do X”, you should be able to name the file before you open anything.

The goal is not memorising 158 function names.

It is being able to say, out loud and without scrolling: “That's Stage 3, so it's in baseline/, and it's a transformation rather than a check, so it's in the top third of the file.” Then open it and be right.

1The four rules

1
One package per pipeline stage.

Six folders, one for each transformation of the data. The question “which folder?” is really the question “which stage of the pipeline changes this?”

2
Inside a single-file stage, five zones in a fixed order.

Errors → the real work → verification → statistics and reports → the CLI. Every one of Stages 1–4 has exactly this shape, so knowing what kind of function you want tells you roughly how far down to scroll.

3
Private helpers sit directly below the function that calls them.

_calendar_index is immediately under calendar_fill. _window_mask is immediately under attach_labels. Find the public function and its machinery is the next thing down — you never have to hunt for it.

4
Names are verb-first and say what they do, not how.

causal_z_scores, calendar_fill, compute_pos_weight, sweep_threshold, recall_by_position. If you can phrase the thing you want as a verb phrase, you have most of the function name already.

The five zones, using a real file

baseline/baseline.py — Stage 3, 889 lines. Every single-file stage looks like this:

line 122 ZONE 1 · errors BaselineError the exception this stage raises 131 ZONE 2 · the work std_floors 204 causal_z_scores ← the thesis 298 build_dataset the actual transformation. Usually the shortest zone. 329 ZONE 3 · verify verify assertions about the output. Raises if violated. 401 ZONE 4 · analysis collapse 420 validation_gate 508 benign_exceedance measurements ABOUT the output, not part of producing it 564 ZONE 5 · report BaselineStats 582 compute_stats 609 format_report 723 format_user_report everything printed to the terminal 803 ZONE 6 · CLI main argument parsing, wiring, always last
Why this matters tomorrow. If you are asked “where do you compute the z-scores?” — that is Zone 2, near the top. If asked “how do you know they're right?” — Zone 3 or 4, the middle. If asked “what does it print?” — Zone 5, near the bottom. You can navigate to the right third of a 900-line file from the shape of the question alone.

The names that repeat — say “convention”, not “coincidence”

Nine names appear once per package: main, build_parser, format_report, verify, summarise, format_user_report, write, run, compute_stats.

That is deliberate parallel structure. The line to use:

“Every stage exposes the same surface — a verify, a format_report and a main. Once you can read one stage you can read all seven.”

2What kind of function lives in each package

extraction/ Stage 1

Anything that touches a raw CSV. This is the only package in the project that knows the raw logs exist. If a question involves the 16 GB, chunking, parsing dates, or the five source files, it is here and nowhere else.

Shape of the functions: five build_*_partial(chunk) builders — one per log — then a fold (aggregate_log) and a join (combine_daily_counts).

The one to know: _compact_distinct — why counting distinct PCs can't be done per chunk.

labeling/ Stage 2

Anything involving the answer key, or the calendar. The only package that opens insiders.csv. If the question contains the words “label”, “attack window”, “ground truth” or “missing days”, it is here.

The two to know: calendar_fill (zero-fills gaps so 28 rows really are 28 days) and attach_labels (marks days inside an attack window).

baseline/ Stage 3

The thesis. Everything about “unusual for this person” is here. If the question is about z-scores, personal history, the standard-deviation floor, or the 2σ gate, this is the package.

The one to know: causal_z_scores — scores each day against that person's prior days only. Line 204.

Named oddly but correctly: collapse reduces 18 z-scores to one number, and returns both the mean and the max because the conclusion flips depending on which you pick.

splitting/ Stage 4

Who goes where. Small and self-contained — it never touches the 18 features, only user, user_scenario and label. Anything about train/validation/test membership, stratification or seeds is here.

The one to know: split_users — assigns users, never rows.

modeling/ Stages 5 + 6

Both models, and everything they share. The only multi-file package where the split is by job rather than by stage:

data.pygetting numbers into tensors — clip, mask, split, standardise
models.pythe two architectures. Nothing else. 202 lines.
train.pythe training loop. Knows nothing about which model it is training.
metrics.pyevery number that scores a prediction
runner.pyorchestration — three seeds, checkpoints, curves

The intuition: ask “is this about the data, the architecture, the loop, the score, or the orchestration?” — that question maps one-to-one onto the five files.

evaluation/ Stage 7

Reads checkpoints, never trains anything. Also one file per job, and the file names are unusually literal:

corpus.pythe rows being evaluated
checkpoints.pyloading saved models
scoring.pycheckpoint + rows → probabilities
guards.pyeverything that could go wrong, as named checks
latency.pywhen in an attack was the insider first caught
falsepositives.pyinspecting the top-scoring benign rows
report.pywriting the results document
figures.pythe plots

3The two files that aren't stages

config.py

Every constant in the project, and nothing else defines one. If the question is “where does the number 28 come from?” or “why 07:00 to 19:00?” or “which websites count as job sites?” — the answer is always this file, and the reasoning is in a comment next to the value.

The line worth knowing: FEATURE_NAMES — that tuple's order is the input-vector layout. Reordering it raises no error and silently makes every saved checkpoint score the wrong feature.

evaluation/guards.py

The single best file to open in a viva. Eight functions, each named for the thing it refuses to allow:

split_disjointness            no user in two splits
standardiser_from_checkpoint  scaling wasn't refitted on test
threshold_from_checkpoint     the cutoff wasn't re-picked on test
identical_rows                both models scored exactly the same days
finite_predictions            no NaN, no infinity
beats_random                  better than the 0.004 baseline
not_suspiciously_good         above ~0.95 means leakage, not success
reproduces_training           re-scoring validation matches what training logged

If asked anything about integrity, leakage or trustworthiness — open this file and read the function names aloud. It answers faster than any explanation you could give.

4Finding anything in five seconds

Three questions, in order:

Q1
Which stage changes this?

Raw files → extraction. Labels or the calendar → labeling. Anything “unusual for this person” → baseline. Who's in which group → splitting. Tensors, architectures, training, scores → modeling. Reading a trained model → evaluation. A constant → config.py.

Q2
Is it work, a check, or a printout?

Work sits near the top of the file, checks in the middle, printing near the bottom, the CLI last. In the multi-file packages the same question picks the file instead of the zone.

Q3
Say it as a verb phrase.

“fill the calendar” → calendar_fill. “compute the positive weight” → compute_pos_weight. “sweep the threshold” → sweep_threshold. “recall by position” → recall_by_position. The naming was chosen so this works.

If you draw a blank on the day.

Say the rule instead of guessing: “Each package is one stage of the pipeline, and inside each one the real work is at the top, the checks are in the middle and the reporting is at the bottom — so that'll be in baseline/, near the top.”

Then open it. Being able to state the organising principle is worth more than remembering a line number, and it works even for a function you have forgotten.
