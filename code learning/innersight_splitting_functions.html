InnerSight · Stage 4 · function reference

Every function in splitting/

37 functions across three files, in plain language — what each one does, and which six are where the actual thinking lives.

splitting/ decides which of the 1,000 users are used to train the models, which are used to tune them, and which are held back to test them. It assigns people, never days, and it does the assignment three times with three different random seeds so the report can show how much the result depends on the draw. It copies no data: the output is data/splits.json, a list of names that indexes into the dataset Stage 3 already wrote.

The one thing to hold onto. This is about sixty lines of real logic, and it is the only stage that can invalidate every number in the final report without producing a single error message. A user's rows all describe the same person against the same personal baseline — put their Monday in training and their Tuesday in test and the model has already met them. The score that follows measures memorisation, and memorisation scores excellently.

01splitting/__init__.py

No functions at all. The file is a docstring stating the two decisions that carry the stage — split by user, stratify by user_scenario — plus a single line:

__all__ = ["split"]

That names the split submodule so from splitting import * pulls it in. Nothing is re-exported, so callers reach the functions the explicit way: from splitting.split import split_users.

Zone 1 — the constants and the error class

Values that other zones treat as contracts rather than conveniences: an ordering, a column allow-list, and a plausibility band.

Zone 2 — reading

Getting from a 465,000-row file to a 1,000-row table of people, and refusing anything that would make the rest meaningless.

def read_user_table(path: Path) -> pd.DataFrame

Opens the parquet file asking for three columns only, and hands them straight to user_table. Everything downstream in the module works on people, never on days.

def user_table(frame: pd.DataFrame) -> pd.DataFrame ⭐

Collapses a day-per-row table into a person-per-row table holding each person's scenario, their day count and their attack-day count, sorted by name. It stops with an error if the user column isn't text, or if any one person carries two different scenario numbers — that means the insider list was joined at the wrong grain, and every stratified count after it would be fiction.

Zone 3 — the split itself

Sixty lines that decide the whole stage: how to divide a headcount without losing anyone, and how to divide it the same way every time.

def allocate(n: int, fractions: SplitFractions = SPLIT) -> dict[str, int] ⭐

Cuts a count of n people into three whole numbers that add back up to exactly n, giving each leftover to whichever share was rounded down hardest. Rounding the three shares independently would quietly gain or lose a person, and losing six out of a thirty-person scenario group is exactly the kind of thing nobody notices.

def split_users( scenarios: Mapping[str, int] | pd.Series, seed: int, fractions: SplitFractions = SPLIT, ) -> dict[str, list[str]] ⭐

Takes each scenario group separately, sorts its members alphabetically, shuffles that sorted list with a generator seeded from the pair (seed, scenario), and deals out the first 60% / next 20% / last 20%. Sorting before shuffling means the order rows happened to arrive in can't reach the result, and giving each group its own generator means adding or removing scenario-1 users can't reshuffle the benign ones.

def split_all_seeds( table: pd.DataFrame, seeds: Sequence[int] = SEEDS, fractions: SplitFractions = SPLIT, ) -> dict[int, dict[str, list[str]]]

Runs the assignment once for each configured seed and returns them keyed by seed number, which is what lets the report show a range instead of a single lucky draw.

Zone 4 — summarising

Turning three lists of names into the counts a reader — and Stage 7 — will actually want, and writing them out diffably.

def summarise_split(users: Sequence[str], table: pd.DataFrame) -> dict[str, object] ⭐

Counts one split three ways — how many people, how many day-rows behind them, how many of those days are attacks — with a per-scenario breakdown of both the headcount and the attack days. Those per-scenario attack counts are what Stage 7 needs to say anything honest about recall per attack type, and they are computed here so nobody has to reopen the 16 MB table later.

def summarise( splits: Mapping[int, Mapping[str, Sequence[str]]], table: pd.DataFrame, ) -> dict[str, dict[str, dict[str, object]]]

Applies that count to all three splits of every seed, producing the nested block of numbers that goes into the written document.

def build_payload( splits: Mapping[int, Mapping[str, Sequence[str]]], table: pd.DataFrame, fractions: SplitFractions = SPLIT, ) -> dict[str, object]

Assembles the complete splits.json document: the fractions used, the seed list, the population size, the name lists themselves, and the summary block.

def dumps(payload: Mapping[str, object]) -> str

Renders that document as text with keys in alphabetical order, a fixed indent and a trailing newline, so two runs can be compared with an ordinary diff and a difference means something real.

Zone 5 — checks

The stage's own audit of its output, run on every real run — not only in the tests — with one finding allowed to be a warning.

class Check — a frozen record of one assertion: whether it held, the sentence describing it, and whether failing it should stop the run. fatal defaults to true.

@property def status(self) -> str

Turns the pass/fail flag into the word printed at the start of the report line: ok when it held, FAIL when a must-hold check broke, warn when a tolerated one did.

def check_splits( splits: Mapping[int, Mapping[str, Sequence[str]]], table: pd.DataFrame, fractions: SplitFractions = SPLIT, ) -> list[Check] ⭐

Tests six things against the real output: nobody appears in two splits, nobody is dropped or invented, each scenario is cut in the expected proportion, re-running a seed reproduces it exactly, different seeds really differ, and every split holds at least one insider of every attack type. Only the last is non-fatal — the 30-user sample has two scenario-2 insiders and cannot mathematically put one in all three splits.

def verify( splits: Mapping[int, Mapping[str, Sequence[str]]], table: pd.DataFrame, fractions: SplitFractions = SPLIT, ) -> list[Check]

Runs those six checks and raises if any must-hold one failed, so a broken assignment can never reach disk. Returns the full list either way, because the report prints the warnings too.

Zone 6 — the report

The block of text printed on every run. It is the stage's only real output for a human, so it carries the caveats as well as the counts.

def _seed_lines(seed: int, summary: Mapping[str, Mapping[str, object]]) -> list[str]

Builds one seed's block: a row per split with headcounts by scenario, rows, attack days and the attack-day rate, then the test set's attack-day count for each of the three scenarios, and a note if any rate falls outside the 0.2–0.7% band — worded to say "report it, do not reshuffle".

def format_report( payload: Mapping[str, object], table: pd.DataFrame, checks: Sequence[Check], out: Path | None = None, ) -> str

Glues everything into one printable string: the population census, the fractions and seeds, each seed's block, the across-seed spread, and every check with its ok/warn/FAIL word.

def _spread_lines( summary: Mapping[str, Mapping[str, Mapping[str, object]]], seeds: Sequence[int], ) -> list[str] ⭐

Reports the smallest, largest, mean and standard deviation of each split's attack-day count across the seeds, then names how many scenario-3 attack rows each seed's test set actually holds. If those counts swing by a third, a single reported recall figure is a statement about luck rather than about the model, and this is the line that says so.

Zone 7 — the CLI

One function, the whole run.

def main(argv: Sequence[str] | None = None) -> int

Parses the flags, picks the full or sample paths, reads the user table, splits it for every seed, verifies, writes the JSON and prints the report, returning 1 with a pointer to Stage 3 if the dataset is missing. Sample and full runs write to different files on purpose: Stage 1 was once wrecked by a seven-second dev run overwriting the real table.

Worth knowing: --seeds exists but its own help text argues against using it — generating extra seeds and keeping the tidiest is selection on the test set. Note also what main does not do: no pos_weight is computed here, because freezing a whole-table class balance would leak the test set's proportions into Stage 5's loss function.

Zone A — the two builders

Everything below runs on synthetic people, so these two decide what "a population" means in every test.

def make_population( counts: dict[int, int], days: int = 5, positives: dict[int, int] | None = None ) -> pd.DataFrame ⭐

Builds a day-per-row frame from a recipe like "930 users of scenario 0, 10 of scenario 3", giving each person the same number of days and marking the first few of them as attack days. Ids look like S3U0007 and the user column is given pandas' string type, which is what user_table's text check insists on.

Docstring vs body: the docstring claims ids are "built so that lexicographic order is NOT the order they appear in the frame". The body does the opposite — it loops scenarios in ascending order and indexes ascending within each, so S0U0000, S0U0001, … comes out in exactly alphabetical order. The order-independence tests do not rely on the claim; they reverse and re-sample the frame themselves. The comment is stale, not the code.
def realistic_table() -> pd.DataFrame

The r4.2 census as a one-row-per-person table: 930 benign plus 30, 30 and 10 insiders, so the proportion tests are asserting against the numbers the project really has.

Zone B — disjointness and completeness

The two failures that turn memorisation into a good score, or lose people without saying so.

def test_no_user_lands_in_two_splits() -> None

For every configured seed, checks the three name lists overlap nowhere — the leak that would let a model be tested on someone it was trained on.

def test_every_user_is_assigned_exactly_once() -> None

Checks the three lists together come to exactly the input population, with nobody dropped and nobody conjured up.

Zone C — stratification, and scenario 3 surviving it

The stage's central claim: each attack type is divided separately, so the rarest one still appears everywhere.

def test_each_scenario_is_divided_in_the_right_proportion() -> None

Hard-codes the expected counts for all four groups and every seed, so a change to the allocation arithmetic has to be deliberate.

def test_scenario_three_puts_an_insider_in_every_split() -> None ⭐

With only ten scenario-3 insiders in the whole release, checks each of the three splits gets at least one. Without this, the test set can end up with none of that attack type, and a third of the final results table is undefined rather than reported as missing.

Zone D — determinism and order independence

Four tests on the same worry: that the same seed might not mean the same split tomorrow, on another machine, or after an unrelated change.

def test_the_same_seed_twice_gives_a_byte_identical_document() -> None

Builds the finished JSON text twice and compares the two strings character for character.

def test_the_input_order_cannot_reach_the_shuffle() -> None ⭐

Feeds the same population three ways — as built, reversed, and randomly re-sorted — and demands identical assignments. The order rows come out of a parquet file is not guaranteed, so without the sort-first rule the same seed would give a different split elsewhere and nothing would warn you.

def test_a_dict_input_in_a_different_insertion_order_gives_the_same_split() -> None

The same demand when the input is a plain dictionary rather than a pandas column, since dictionaries iterate in insertion order.

def test_one_scenario_group_does_not_depend_on_the_others() -> None ⭐

Removes every scenario-1 user and checks the benign people land exactly where they did before. This is the evidence that each group draws from its own random stream, so an upstream change to one attack type cannot silently reshuffle all the others.

def test_different_seeds_produce_different_splits() -> None

Checks the three seeds really give three distinct test sets — otherwise the reported spread across seeds would be describing nothing.

Zone E — tiny inputs

Groups too small to divide cleanly. The worry is not a crash; it is a person quietly vanishing.

@pytest.mark.parametrize("n", list(range(0, 13))) def test_allocation_of_a_tiny_group_sums_to_the_group(n: int) -> None

For every group size from 0 to 12, checks the three parts add back to the whole and none of them is negative.

def test_a_scenario_smaller_than_the_number_of_splits_keeps_everyone() -> None

With groups of one, two and three people, checks everyone is still placed somewhere rather than discarded for being un-splittable.

def test_an_empty_population_does_not_crash() -> None

An empty input produces three empty lists rather than an error, so an unusual filter upstream degrades quietly instead of exploding.

Zone F — the summary block and the guards

What gets written, and what the stage refuses to write.

def test_the_summary_counts_rows_and_positives_not_users() -> None

On a small population whose numbers can be checked by hand, pins the exact row counts, attack-day counts and rate. Two people of the same scenario can carry wildly different attack-day totals — scenario 2 averages 56, scenario 3 exactly 2 — so a summary counting people would say nothing about class balance.

def test_the_document_carries_every_seed_and_every_user() -> None

Checks the assembled document reports 1,000 people, lists the configured seeds, and holds all 1,000 names under each one.

def test_a_scenario_that_changes_within_a_user_is_a_hard_failure() -> None

Flips one row's scenario so a person carries two, and requires an exception. Picking a value there would hide a bad join and quietly falsify every stratified count downstream.

def test_verify_raises_on_a_leaked_user() -> None

Copies one training name into the test list and checks the verifier refuses the whole thing rather than writing the file anyway.

def test_a_thin_scenario_is_reported_but_not_fatal() -> None

On a sample-sized population where one attack type has too few insiders to reach all three splits, checks the coverage finding is raised as a warning and the run continues — a fact about the sample, not a broken split.

def test_fractions_other_than_60_20_20_still_partition_the_population() -> None

Re-runs with a 70/15/15 division and checks everyone is still placed and train holds exactly 700, so the arithmetic isn't quietly hard-coded to the usual numbers.

def test_the_json_is_sorted_and_therefore_diffable() -> None

Checks the file ends in a newline, its top-level keys are alphabetical, and every name list inside is sorted — so a diff between two runs shows real changes rather than reordering.

04The five functions to actually remember

Thirty-seven functions, and five of them are the stage. The rest is reading, formatting and plumbing around these.

1
split_users

This is Stage 4. Sort each scenario group, shuffle it with a generator seeded from (seed, scenario), deal out 60/20/20. If you understand why each of those three words is in that order — sort, then shuffle, then per-group seed — you understand the whole stage.

2
user_table

The step that makes splitting by person possible at all: 465,000 days become 1,000 people before anything is decided. It also holds the stage's one hard refusal — a person with two scenario numbers means the insider list was joined at the wrong grain, and it stops rather than guessing.

3
allocate

Small, and the reason nobody disappears. On the real group sizes the fractions already come out whole, so the leftover-handling never fires — it exists entirely for the groups where it would, and for the tie-break that sends a group of one to train.

4
check_splits

The stage cannot be tested by looking at its output, because a wrong split looks exactly like a right one. This runs the six invariants on the real assignment on every real run, and its one deliberately non-fatal check is a good example of a guard that knows the difference between a bug and a fact about the data.

5
_spread_lines

Private, four lines of formatting, and it decides how the thesis is allowed to phrase its results. It prints how far the attack-day counts move between seeds and how many scenario-3 attack rows each test set holds. When that number is four, "recall on scenario 3" is a claim about four rows, and this is the line that forces you to say so.

Honourable mention: summarise_split — it computes positives_by_scenario, which is not in the original brief for the file format and is there because Stage 7 cannot report per-attack-type recall without it.

Counted against the source: 0 functions in __init__.py, 16 in split.py (15 module-level including main, plus the status property on Check) and 21 in test_split.py — 37 in total, all described above. Two classes, SplitError and Check, are covered in their zones.
