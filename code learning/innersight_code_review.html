InnerSight · codebase review

The code, reviewed the way it will be examined

A walk through all thirteen thousand lines from the perspective of someone whose job is to find the weak point — what each package does, why it is built that way, and where the hard questions will land.

How an examiner actually reads a final-year project.

Not line by line. They look for three things, in this order: is the experiment valid (could the result be an artefact?), is the code trustworthy (would I believe a number it printed?), and does the student understand what they built (can they defend a decision they did not have to make?).

Everything below is organised around those three questions, because that is the order the questions will come in.

The first thing an examiner will notice, and it cuts both ways. Thirteen thousand lines to compare two models with 641 and 4,897 parameters is a lot. The models themselves are about 120 lines. So the honest framing — and it is a good one — is that this is not a modelling project with some plumbing; it is a data-engineering and experimental-validity project with two small models at the end. Roughly a quarter of the code is tests and another large fraction is diagnostics that exist to catch silent failure. Say that before someone asks why the evaluation package is bigger than the models.

Every stage writes a file; the next stage reads that file; nothing recomputes. This is worth defending explicitly, because it is the decision that made the project finishable: Stage 1 takes ninety seconds over 16 GB and runs once, while stages 5–7 were run dozens of times. If the CNN's training script reached back to the raw logs, every debugging cycle would have cost an afternoon.

2Is the experiment valid?

This is the first question and the one that can sink a project outright. The claim is "Model B beats Model A because it sees temporal context." An examiner's job is to find another explanation.

Threat 1 — were the two models actually trained identically?

The defence here is unusually strong, and it is structural rather than promised.

train.py takes a model object and inspects nothing about it. Stage 6 added an architecture class and an entry point, and touched none of the shared modules. That claim is verifiable two ways: by diff, and by file timestamps —

data.py, metrics.py, run_model_a.py     15:15   Stage 5, never touched after
model_a checkpoints                     15:33
model_b checkpoints                     16:10 – 16:17
train.py, runner.py modified            16:48   ← AFTER both models were trained

Both checkpoint sets predate every subsequent modification. That is evidence, not assurance.

Second, sharper check. The training-split pos_weight must print 229.7 / 225.3 / 232.1. The whole-table figure is 244. If a run ever prints 244, the 27-day row mask was not applied before the weight was computed, which means the two models are on different rows and the comparison is void. A single number in the log that distinguishes correct from silently-wrong is exactly the kind of instrumentation an examiner rewards.

Threat 2 — leakage

Three leaks are possible in a project shaped like this, and each is closed differently.

LeakWhere it would happenHow it is prevented
Split by row, not by userStage 4users are assigned; every one of their ~465 rows follows. Tested for disjointness across all three seeds.
Standardiser fitted on data it will scoreStage 5 / 7structurally impossible — Corpus.build() takes a standardiser as a required argument. No code path in evaluation/ can fit one on the rows it is about to score.
Threshold re-selected on testStage 7scoring.py does not import sweep_threshold, and evaluate() is always called with choose_threshold=False.

This is the single most examiner-pleasing property in the codebase. Most students prevent leakage by being careful. Here two of the three leaks are prevented by type signature — the function that could commit them does not accept the arguments that would let it. Discipline fails at 2am; a required parameter does not.

Threat 3 — "B wins because it has 7.6× the parameters"

A live alternative explanation, and the project answers it with a control rather than an argument: Model B on a 7-day window. Identical architecture, identical parameter count — convolutions plus global pooling do not depend on sequence length — with less context. Seven is the floor, because two dilated k=3 layers have a 7-day receptive field. The run aborts if the two parameter counts ever differ, since the control separates nothing otherwise.

If B@7 lands between A and B@28, context is the driver and it is demonstrated, not asserted.

Threat 4 — the one that has not been closed yet

Onset versus persistence. Scenario-2 attacks run 45–59 days. For a day at position 30, Model B's entire 28-day window sits inside the attack — it sees 28 consecutive anomalous days and says "attack", which is easy. Roughly half of scenario-2 positives are like that. Nothing is leaking (the window reaches strictly backwards, holds only that user's rows, and no label is ever visible), but "detects the insider" and "notices an attack it already missed is still running" are different products and only the first is worth claiming. Stage 7 measures first-detection day per insider to settle it. Anticipating this question and instrumenting for it is worth more than the answer.

Every stage prints a report. A representative one, from Stage 1:

ok   no negative counts                 none

ok   logons approx logoffs, NOT equal   470,591 logons vs 384,268 logoffs

The logons/logoffs check is the one worth pointing at in a viva. It requires the two to be close but not equal. Exactly equal would mean something is synthesising logoffs; wildly different would mean the activity filter is broken. The dataset documentation states that a few logons are deliberately omitted to simulate dirty data — so a small mismatch is the expected state, and the check asserts the mismatch rather than the match. That is a student who read the documentation and thought about what "correct" means.

The tests were chosen by a stated criterion

Written at the top of the first test module and honoured in all seven:

Test the behaviours that are wrong silently — no exception, no NaN, just a number slightly off that nobody notices until the results make no sense.

Which is why the extraction package has six test functions rather than sixty. The flagship one:

Distinct counts across chunk boundaries

The file is read in 50,000-row batches, so one person's single day can straddle two batches. Sixteen of the eighteen features are additive and combine by addition. Two — unique_pcs_used and unique_filenames — are distinct counts:

batch 1:  Anna, Monday, PC-1     →  1 distinct PC
batch 2:  Anna, Monday, PC-1     →  1 distinct PC
                                    ─────────────
naive sum                           2   ✗
truth (same machine, seen twice)    1   ✓

So those two keep unique (user, day, value) triples alive to the very end and count once. The failure mode is what makes it worth a test: no crash, no NaN, just a number slightly too large in proportion to how many chunks a given user-day happened to straddle — which changes with batch size. It would have survived to the results table.

Behavioural verification beats assertion

Row counts prove a program ran. This proves it counted the right things:

KPC0073, reconstructed from our pipeline    │  the dataset's answer key
2010-07-07   upload-site visits: 1          │  07/07/2010 21:23  wikileaks.org
2010-07-12   upload-site visits: 1          │  07/12/2010 23:51  wikileaks.org
2010-07-15   upload-site visits: 1          │  07/15/2010 02:40  wikileaks.org
all 498 other days: 0                       │  (nothing else listed)

A known insider's timeline rebuilt from 32.8 million raw events, matching the published ground truth event for event. No schema assertion can do that.

And a test the project got wrong, then fixed properly

Model B is a 1D CNN over an (18, 28) grid. If the tensor arrives transposed, the network convolves across features while treating days as channels — producing plausible numbers that mean nothing.

The originally specified guard was: feed a ramp over days, reverse it, assert the output changes. A deliberately broken feature-axis model passed that test on all eight initialisations, because reversing a ramp also permutes the channels a feature-axis convolution reads, so both models respond.

The replacement is translation invariance: a bump at days 8–11 must score the same as at days 16–19. Measured separation — correct model 1.49e-08, broken model 7.47e-03. Six orders of magnitude. The test module ships the broken model explicitly, plus a mutation test proving the guard fails on it.

strong Finding that your own verification is invalid, and building a mutation test to prove the replacement works, is postgraduate-level practice.

4Does the student understand what they built?

This is where most vivas are won or lost, and it is tested by asking about decisions that had alternatives. Six of those are visible in the code.

1. Per-day labels, not 28-day windows

The original design labelled a 28-day window positive only if ≥50% of it fell inside an attack. Scenario 1 lasts 1–12 days and scenario 3 lasts 2 — neither can fill 14 of 28 days. That rule silently deleted 40 of the 70 insiders and left 125 positives. Per-day labelling keeps all 70 and yields 1,892.

A 15× increase in training signal from changing a labelling rule — before any model existed. This is the highest-leverage decision in the project and it is not a modelling decision at all.

2. Calendar fill, and why it is not cosmetic

Stage 1 emits a row only for days with events, so weekends vanish. Stage 2 fills each user's calendar with zeros between their first and last observed day. Two reasons: Model B needs 28 consecutive calendar days (28 rows can otherwise span 40 days with nothing raising), and a day of no activity is an observation, not missing data — a resigned insider who has stopped coming in produces exactly that.

Measured consequence: 528 of the 1,892 positives — 28% — exist only after the fill.

3. Expanding window, not an exponential moving average

The z-score baseline scores each day against that person's own prior days. An EMA with a two-week half-life was the more sophisticated option and was rejected for a measured reason: scenario-2 attacks last 45–59 days, long enough that an EMA would substantially absorb the attack into the baseline it is measured against — and scenario 2 is 88% of all positives.

It still absorbs, and the project quantified that rather than hiding it: scenario-2 days score 0.40× as high in the last third of their window as the first. That number is both an honest limitation and the mechanism behind Model B's advantage.

4. Clip to ±10 before standardising

z-scores reach 716 against a typical 0.42. The subtlety worth being able to explain: standardising does not fix an outlier, it amplifies the damage. The outlier inflates the feature's standard deviation, so every normal row is divided by a larger number and squashed toward zero while the outlier still towers. Clipping first keeps the divisor honest.

5. Two domain lists decided by measurement, not intuition

Sixteen features are mechanical counts. Two depend on which websites count — the only place in the pipeline where a thumb could rest on the scale. Both were settled by one test applied uniformly: does traffic to this domain concentrate inside labelled attack windows?

monster.com        insider A 10 in / 0 out    insider B  7 / 0    → keep
aol.com/jobs                 5 / 0                       5 / 0    → ADD
craigslist.org              17 / 22                      3 / 0    → drop
linkedin.com       40,446 hits, most-visited domain in the dataset → drop
mediafire.com      ~334,000 hits, no ground truth on r4.2         → drop

The mediafire removal is the strongest story. It was 90% of one feature while carrying no ground-truth signal, and the damage was per-user rather than uniform: an insider who never used mediafire kept a baseline of zero and his leak-site visit produced a huge deviation, while an insider who browsed it routinely had a noisy baseline that swallowed the same visit. Detection was depending on unrelated browsing habits.

6. Average pooling, and the tuning attempt that proved it

A post-hoc variant with mean+max pooling lost — AUPRC 0.677 → 0.602. But the shape of the loss is the finding: scenario 1 rose 6.6 points, scenario 2 fell 11.0. Scenario 2 is 88% of positives, so it decides the metric.

The pooling operator selects which attack profile the model can detect. A max channel offers the shortcut "find the single worst day" — right for a burst, wrong for a drift whose individual days are unremarkable. A negative result with a mechanism is worth more than a lucky win, and reporting it unprompted is the behaviour of someone doing science rather than demonstrating a tool.

5Three practices above the usual bar

The prediction was registered before the experiment

Written into the Stage 6 brief before any Model B code existed, and copied into the package README before the run so it could not be retrofitted:

PredictedMeasured
Scenario 2B clearly beats A22.7% → 71.9%✅ held
Scenario 1roughly a tie40.5% → 61.2%❌ missed
Scenario 3tie4/12 → 4/12✅ held
Overallahead but modestly0.151 → 0.677⚠️ 4× off

Two of four predictions were wrong, and both are reported as wrong. The scenario-1 explanation is the interesting part: a spike judged against 27 quiet days inside the same window is a stronger signal than the spike alone. Temporal context helps short bursts too — which the student did not expect and now understands.

Guards print values, not verdicts

A boolean saying "the standardiser came from the checkpoint" is as convincing as no check at all. So the standardiser guard refits one on training rows purely for comparison and prints both sets of statistics, and the row-identity guard compares a SHA-256 digest of every row's (user, day, label) — which catches a reordering that a row count would not.

The test split is opened once, and the opening is recorded

run_phase2 refuses to start until the validation phase has written its artifact, appends to TEST_SPLIT_OPENED.json on every opening, and requires --force --reason '...' for a second pass — with the reason recorded so the write-up can disclose it. The discipline is enforced by the program rather than by the student's memory at 2am.

6Where I would press hardest

Your evaluation package is bigger than your models. Justify that.

The honest answer is the strong one: the models are 120 lines because they are supposed to be small — 641 and 4,897 parameters against ~1,140 positive training rows. The engineering is not in the architectures, it is in making a 0.4%-positive comparison on 464,687 rows believable. Three-quarters of evaluation/ is guards, leakage prevention and analyses that exist to test the result rather than produce it.

Weak answer to avoid: "it needed to be thorough." Point at what specific failure each part prevents.

You changed the standard-deviation floor from what your own specification said. Did you tune on the labels?

The order of the justification decides this. The specified formula produced a median of exactly zero for 8 of the 18 features, because 73.5% of employees never connect a USB stick — so the floor was not a scale estimate at all, it collapsed onto a fallback constant. The estimator was changed to use employees who exhibit the behaviour at all.

That reasoning uses only the distribution of the data and never touches the labels. The 54/70 versus 66/70 comparison is confirmation reported afterwards, not the reason for the change. Say it in that order or it sounds like tuning.

Only three random seeds. Why should I trust ±0.02?

Legitimate hit, and the honest answer names the limit. Three seeds is thin, and the seeds vary the split as well as the initialisation, so the spread conflates two sources of variance. A proper design would be three weight initialisations within each split — nine runs. It was scoped out on time, and the project says so rather than implying otherwise.

What can still be claimed: Model B's worst seed beats Model A's best by 3.7× with no overlap. That separation does not require a tight confidence interval to be convincing.

Your domain lists encode knowledge of what the attacks were. Isn't that cheating?

The candidate domains come from the dataset's published scenario descriptions, which is standard practice for this benchmark. What was excluded was decided by one stated test applied uniformly, and two upload domains carrying no ground truth at all were deliberately retained so the feature is not a lookup for the single domain the answer key names.

The concession to make voluntarily: a real deployment would not have this knowledge on day one. It is listed in the limitations.

Show me your commit history.

There isn't one — the repository is uncommitted. This is a genuine weakness and there is no good answer to it. Fix it before submission rather than trying to defend it.

The sentence to open the viva with.

“The project is a controlled experiment with one variable. Two networks — 641 and 4,897 parameters — trained on identical rows, with an identical standardiser, loss, optimiser, schedule, seeds and device; the only difference is that one sees a single day and the other sees the twenty-eight days ending on it. Most of the thirteen thousand lines exist to make that claim verifiable rather than merely stated, and I can show you the two independent checks that prove the shared code never changed between the runs.”
