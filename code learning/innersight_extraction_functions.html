InnerSight · Stage 1 · function reference

Every function in extraction/

All 31 functions in extract.py, all 7 in test_extract.py, in plain language and in file order. Read from the body, not the docstring.

What this package is for.

The CERT r4.2 release is five raw activity logs totalling about 16 GB, one row per event — a logon, a USB plug, a file copy, an email, a web request. extraction/ reads all five once and boils them down to a single small table: one row per person per calendar day, carrying 18 numbers that describe what that person did that day. It is the only code in the project that ever opens the raw release; every later stage reads the small table it writes and nothing else.

How to read this. Each function gets a signature and one or two lines saying what it actually does. ⭐ marks the six functions where the real thinking is — the rest is plumbing, and honest plumbing at that. Where a docstring and the code disagree, the code is described and the disagreement is flagged in a warts box at the end of the chapter.

1extraction/__init__.py

23 lines, zero functions. It is a docstring and one assignment. Worth reading once anyway, because it is where the three run commands are written down:

python -m extraction.extract                 # 30-user sample, ~7 s
python -m extraction.extract --full          # full r4.2, ~1-3 h
python -m extraction.extract --user KPC0073  # inspect one user's days

The only executable line is __all__ = ["extract"]. That names a submodule, not a function — so from extraction import * pulls in the extract module, while a plain import extraction does not. Nothing else in the project relies on either, so this is decoration rather than machinery.

One thing to know. Those commands must be run from the project root. extract.py does from config import ... — a top-level import, not a relative one — so running it from inside extraction/ fails before it does anything.

zone 1 the constants and the error class

Two module-level validators that run before the module finishes importing, so a misconfiguration is a startup crash rather than a wrong number three hours later.

SignatureWhat it does
def _check_feature_partition() -> NoneChecks that each of the 18 feature names is produced by exactly one of the five logs. Two logs claiming the same feature would silently overwrite each other in the join; a feature claimed by nobody would ship as a column of zeros.
def _alternation(domains: Sequence[str], name: str) -> strGlues a list of domains into one a\.com|b\.com search string, lowercased, with dots escaped so . can't match any character. It refuses an empty list, because an empty pattern matches every string and would score every single web request as a job-site hit.

zone 2 the five per-log builders

One function per raw log. Each takes a chunk of rows and returns what that chunk contributes to the daily table — nothing more; they never see the file, the stream, or each other.

SignatureWhat it does
def build_logon_partial(chunk: pd.DataFrame) -> LogPartialTurns logon/logoff rows into five numbers: sessions started, sessions ended, late-night starts, weekend starts, and the machines used. Only starts count toward the late-night and weekend tallies — otherwise a single 2am session would be counted twice once its logoff landed.
def build_device_partial(chunk: pd.DataFrame) -> LogPartialCounts USB plugs, USB unplugs, and any device event falling outside 7am–7pm. Unplugs count too, on the view that a drive inserted at 18:55 and pulled at 19:30 is one late-night episode either way.
def build_file_partial(chunk: pd.DataFrame) -> LogPartialCounts file copies per day and keeps the filenames for the distinct tally. If the release ships no "was it copied to removable media" column, every row is treated as such a copy — which is why that number equals the plain file count exactly on r4.2.
def build_email_partial(chunk: pd.DataFrame) -> LogPartialCounts messages sent, messages with at least one recipient outside the org, messages of 1 MB or more, and total bytes. r4.2 has no sent-vs-received column, so every row is taken as a message the named person sent.
def build_http_partial(chunk: pd.DataFrame) -> LogPartialCounts web requests, plus how many URLs contain a job-board domain and how many contain a file-sharing domain. Matching is "does this text appear anywhere in the lowercased URL", which is what lets a path-shaped entry like aol.com/jobs work at all.

zone 3 the fold and the join

The arithmetic that turns a stream of chunk-sized contributions into one table. This is the zone that makes the memory story true.

SignatureWhat it does
⭐ def aggregate_log(log: str, chunks: Iterable[pd.DataFrame], *, compact_every: int = 64) -> pd.DataFrameFeeds every chunk of one log through its builder and accumulates the results, so a 14.5 GB file is never held in memory — only the running totals, which are bounded by people × days. Every 64 chunks it squashes the accumulated pile back down to one table, purely so hundreds of thousands of tiny frames don't stay pinned until the end.
⭐ def combine_daily_counts(per_log: Mapping[str, pd.DataFrame]) -> pd.DataFrameStitches the five per-log tables into the Stage 1 output, keeping every (person, day) that appears in any log and filling every gap with a real 0 rather than a blank. Columns come out in the fixed config order, because that ordering is the feature-vector layout every later stage assumes.
def daily_counts(per_log_chunks: Mapping[str, Iterable[pd.DataFrame]], *, compact_every: int = 64) -> pd.DataFrameTwo lines of wiring: fold each log, then join the results. This is the seam the tests plug into, since it accepts plain lists of two-row frames exactly as happily as generators over the real release.
def daily_counts_from_dir(data_dir: Path | str, *, chunk_size: int = 50_000, compact_every: int = 64) -> pd.DataFrameThe production entry point: point it at a release folder and it opens all five CSVs as streams and hands back the finished table. It fails immediately if the folder is missing, and fails as soon as reading starts if any one of the five files is.

zone 4 reading files

The only three functions in the project that know what a CSV is. Everything above them receives DataFrames and has no idea where they came from.

SignatureWhat it does
⭐ def _stream_log(data_dir: Path, log: str, *, chunk_size: int) -> Iterator[pd.DataFrame]Hands out 50,000-row pieces of one CSV, loading only the columns that log's builder actually reads. That projection is the whole trick for http.csv — three columns out of six, and in particular never content, which is most of the 14.5 GB.
def _validated_header(path: Path, log: str) -> list[str]Reads only the header row and confirms every column the project's contract promises is present, before any data is touched. Checking the full contract up front means a renamed column fails loudly, even though only a subset is loaded afterwards.
def _parse_dates_in_place(chunk: pd.DataFrame, path: Path) -> NoneConverts the date text to real timestamps using CERT's known MM/DD/YYYY HH:MM:SS layout, falling back to guessing row by row only if that fails. The order is the point: per-row guessing is invisible on a 100-row fixture and costs minutes on a 28-million-row log.

zone 5 small shared helpers

Twelve short functions the builders and the fold are assembled from. Individually trivial; two of them encode decisions that would be wrong silently if made differently.

SignatureWhat it does
def _key_frame(chunk: pd.DataFrame) -> pd.DataFrameBuilds the two-column (person, calendar day) address for every row, with the clock time flattened to midnight. Every grouping in the module is by that pair.
def _after_hours(chunk: pd.DataFrame) -> pd.SeriesMarks rows timestamped before 7am or from 7pm onward. Those hours are one fixed org-wide definition of the working day, not a per-person schedule — personal normality is Stage 3's job, not this one's.
def _ones(chunk: pd.DataFrame) -> pd.SeriesA column of 1s, one per row, so that "how many rows" can be summed by exactly the same machinery as every other feature.
def _count(mask: pd.Series) -> pd.SeriesTurns a true/false column into 1s and 0s, treating "unknown" as "didn't happen". Comparing against a blank cell in pandas gives neither true nor false but a third, contagious state, and it has to be pinned to 0 before it reaches the totals.
def _truthy(series: pd.Series) -> pd.SeriesDecides what counts as true in a column that might hold real booleans or might hold text, accepting true / 1 / yes / y / t in any casing and with stray spaces. Only file.csv needs it, and only on releases newer than r4.2.
⭐ def _has_external_recipient(chunk: pd.DataFrame) -> pd.SeriesFlags a message when any address across to/cc/bcc sits outside dtaa.com, worked out by comparing the number of @ signs against the number of internal-domain matches rather than splitting addresses apart — one vectorised pass per column instead of per-row work on a 1.36 GB file. The internal pattern deliberately refuses to match a lookalike host such as @dtaa.com.evil.net.
def _sum_by_key(keys: pd.DataFrame, columns: Mapping[str, pd.Series]) -> pd.DataFrameAdds a batch of per-row numbers up into per-person-per-day totals. Rows with no user or an unreadable date are dropped rather than pooled under a blank key, so they count for nobody instead of for a phantom person.
def _distinct_by_key(keys: pd.DataFrame, values: pd.Series) -> pd.DataFrameReduces a chunk to its unique (person, day, thing) combinations — the raw material a distinct count is taken from later, and never here.
def _compact_sums(parts: list[pd.DataFrame]) -> pd.DataFrameAdds a stack of partial total-tables into one. Safe to do at any moment, which is exactly what separates additive features from the two distinct ones.
⭐ def _compact_distinct(parts: list[pd.DataFrame]) -> pd.DataFrameMerges accumulated combination tables by stacking and de-duplicating them, and pointedly never counts. PC-42 seen in two chunks of one person's day is one machine, not two — so counting can happen once, at the very end, and a per-chunk count would be wrong in silent proportion to how many chunks a person's day happened to straddle.
def _empty_log_frame(log: str) -> pd.DataFrameA zero-row table with the right columns and the right index types, returned when a log turns out to contain nothing at all. Handing back the correct shape means the join downstream needs no special case for it.
def _union_key_index(frames: Iterable[pd.DataFrame]) -> pd.MultiIndexCollects every (person, day) appearing in any of the per-log tables into one sorted, duplicate-free list. That list is the set of rows Stage 1 emits.

zone 6 the report

Everything printed to the terminal after a run. None of it raises — this zone's job is to make a wrong number visible, not to decide it is wrong.

⭐ def _check_lines(daily: pd.DataFrame, totals: pd.Series) -> list[str]The actual sanity checks: no negative counts, no blanks, no repeated (person, day), the three URL-derived totals non-zero, and logon/logoff totals within 25% of each other but not identical. Showing their first 30 days instead would be useless, because an attack is rarely in January.

zone 7 the CLI

Argument parsing and wiring. One function, always last in the file.

SignatureWhat it does
def main(argv: Sequence[str] | None = None) -> intParses the command line, builds the table from either the 30-user sample or the full release, writes it to Parquet and prints the report. Sample and full runs default to different output files on purpose, so a seven-second test can't quietly overwrite the three-hour one.
Warts — where the docstrings and the code disagree.
  • format_user_report's docstring says "Print one user's days". It doesn't print; it returns a string, and main prints it. Same for format_report.
  • The module docstring says "18 integer counts". Seventeen are integers; total_email_size is deliberately a float, because a byte total overflows a 32-bit integer and arrives from a column that can be blank.
  • build_http_partial and _has_external_recipient both write .astype("str").fillna(""). By the time fillna runs, blanks have already become the literal text "nan", so it never does anything. Harmless — "nan" contains no @ and matches no domain — but it reads as protection that isn't there.
  • _check_lines labels one check "logons approx logoffs, not equal", and the code means it: exactly equal totals are reported as CHECK, not ok. That is intentional (perfectly paired totals would suggest generated rather than observed data) but it does mean a suspiciously tidy result reads as a failure.
  • _alternation's docstring says "compile"; it builds a pattern string and never calls re.compile. pandas compiles it later.
  • In aggregate_log, an empty chunk is skipped before the every-64 compaction check, so an empty chunk landing exactly on the 64th slot skips that one compaction. Purely a memory timing detail — the result is identical.

What is not tested. Nothing here reads a file. _stream_log, _validated_header and _parse_dates_in_place have no unit test — the CSV-reading zone is covered by running the 30-user sample end to end in about seven seconds, and by the checks in _check_lines. That is a deliberate trade, and worth saying out loud before someone else points at it.

4The five functions to actually remember

Twenty-six of the thirty-one are plumbing you can re-derive from the name. These five are decisions, and each one is wrong in a way that produces plausible numbers rather than an error.

1
aggregate_log — why 16 GB fits on a laptop

Nothing is ever held whole. Each chunk is reduced to per-person-per-day contributions the moment it arrives, and only the running totals persist. The input is unbounded; the state is bounded by people × days, which is roughly 500,000 rows. If you are asked one question about this stage, it will be this one.

2
_compact_distinct — why two features can't be added

Sixteen of the eighteen features combine by addition. Two — machines used and distinct filenames — do not: the same machine seen in two chunks of one person's day is one machine. So the unique combinations are carried around untouched and counted exactly once, at the end. Count them per chunk instead and the error is invisible, and grows with how many chunks a person's day happens to straddle.

3
combine_daily_counts — three decisions in one join

The rows are the union of every log's (person, day), so a day that exists only in web traffic still produces a row. Missing is filled with a real 0, because "no USB events today" is an observation and not an absence of data. And the columns come out in one fixed order, because that order is the vector layout every later stage reads positionally.

4
_stream_log — where the time actually goes

The header is checked in full against the contract before a single data row is read; then only the columns the builder needs are loaded. On http.csv that is three columns out of six and, crucially, never content — which is the majority of the 14.5 GB. The saving isn't from clever code, it's from not reading most of the file.

5
_check_lines — the checks that unit tests can't do

Tests prove the code does what was written. These prove what was written is true of the world. The one that matters most: if job-site visits total zero, URL matching never fired — and thirty of the insiders in this dataset are people whose entire signature is job hunting. Every downstream stage would still run perfectly happily on the result.

The sixth star. _has_external_recipient is starred above as the cleverest small thing in the file — comparing the count of @ signs against the count of internal-domain matches, so no address is ever split — but it didn't make this list, because being clever is not the same as being load-bearing. If it were wrong, one feature out of eighteen would be wrong. If any of the five above were wrong, the whole table would be.
