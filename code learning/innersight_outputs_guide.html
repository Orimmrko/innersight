InnerSight · data/ and outputs/

What all these files are

Two folders, thirty-odd files, five formats. Once you know the three naming rules, you can identify any of them without opening it.

The one-sentence mental model.

data/ holds the pipeline's intermediate products — one file per stage, each one the input to the next. outputs/ holds everything the models produced — trained weights, measured numbers, logs and figures.

Nothing in either folder is source code, and nothing in either is written by hand. Every file is regenerable by re-running a stage.

1Three naming rules that identify any file

.sample

Built from the 30-user development copy, not the real dataset. Those 30 users include 9 insiders — a 30% insider rate against the real 7% — so every number from a .sample file is meaningless. They exist so a 7-second test run can never overwrite a real result. If you are ever unsure whether a number is real, check for this infix first.

_seed42
_seed123
_seed456

Three different random splits of the 1,000 users — not three attempts at the same thing. Each seed puts different people in train, validation and test, so each produces its own trained model. Results are always reported as mean ± standard deviation across the three, because a single split is a single draw of a lottery.

_v2

The tuning attempt that lost. Dropout, mean+max pooling and a learning-rate schedule; validation AUPRC fell 0.677 → 0.602. Excluded from every result. The files stay on disk as a record and the reason it lost is worth one paragraph, but no _v2 file appears in any table.

Two more tags will appear once the last runs finish: _nopw (the class-weighting ablation) and _w7 (the 7-day capacity control). Both are experiments about the result, not the result.

2data/ — one file per stage

Each stage reads the previous file and writes the next. Nothing recomputes.

FileSizeMade byWhat's in it
daily_counts.parquet2.8 MBStage 1330,452 rows — user, day, 18 raw counts
labelled_counts.parquet3.5 MBStage 2464,687 rows — the same, plus zero-filled days, plus label and user_scenario
dataset.parquet16 MBStage 3464,687 rows — counts replaced by z-scores. This is what the models train on.
splits.json61 KBStage 4which users are in train / validation / test, for each of the three seeds
Why does dataset.parquet jump to 16 MB with the same number of rows? Because the contents changed from small whole numbers to decimals. A column of counts is mostly zeros and small integers, which compresses enormously. A column of z-scores is high-precision decimals with almost no repetition, so there is nothing to compress. Same rows, five times the file. It is a good sign, not a problem — it is what "we replaced counts with deviations" looks like on disk.

Reading them

import pandas as pd
df = pd.read_parquet("data/dataset.parquet")
df.head()
df[df.user == "KPC0073"]           # one person's whole history
df[df.label == 1].user.nunique()   # 70 insiders

Parquet is a compressed columnar format — it is not readable in a text editor, and that is the point: it loads in under a second and remembers the exact data types, so a date stays a date and an integer stays an integer between stages.

splits.json — the only human-readable one

{
  "fractions": {"train": 0.6, "val": 0.2, "test": 0.2},
  "seeds": [42, 123, 456],
  "splits":  { "42": {"train": ["AAF0535", ...], "val": [...], "test": [...] }, ... },
  "summary": { "42": {"test": {"users": 200, "rows": 93287,
                              "positive_rows": 383, "positive_rate": 0.0041,
                              "positives_by_scenario": {"1": 40, "2": 339, "3": 4}}}}
}

The summary block is the useful half. You can answer "how many attack days are in the test set?" by opening the file, without loading any data or running anything.

3outputs/ — what the models produced

Four kinds of thing, and it helps to think of them as answering four different questions.

*_metrics.json the numbers

Question it answers: how well did it do? This is the file to open when you need a figure. Everything else in outputs/ is supporting evidence.

Three sections that matter:

aggregate       mean ± std across the three seeds — the headline numbers
per_seed        one record per seed, including the full epoch-by-epoch history
per_scenario    recall broken down by attack type, pooled and per-seed

Plus four flags at the top that are worth knowing exist:

pos_weight_enabled              was the class-imbalance fix on?
collapse_guard_fired_any_seed   did the model degenerate to one answer?
leakage_suspected_any_seed      did AUPRC go suspiciously high?
device                          "mps" — the Apple GPU

Getting a headline number out:

import json
m = json.load(open("outputs/model_b_metrics.json"))
m["aggregate"]["auprc"]            # {'mean': 0.6767, 'std': 0.0342, 'n': 3}
m["aggregate"]["random_baseline"]  # ~0.0043 — always quote this beside it
m["per_scenario"]["2"]             # scenario 2: hits_summed / attack_days_summed

*_run.log the transcript

Question it answers: what actually happened during training? Plain text, exactly what appeared in the terminal. This is the file to open when someone doubts a number, because it shows the run rather than summarising it.

Each seed's block opens with the setup, and those lines are worth being able to read aloud:

rows 464,687, masked out as warm-up 27,000 (5.8%), positives lost to the mask 0
rows with any |z| > 10 before clipping: 2,138 (0.46%)
train: 600 users, 264,609 target rows, 1,147 positive (0.4335%)
val:   200 users,  85,191 target rows,   362 positive (0.4249%)
pos_weight (train only) = 229.7  [263,462 negatives / 1,147 positives]
random-baseline AUPRC on validation = 0.00425
ModelA: 641 trainable parameters

Then one line per epoch:

epoch  1  train_loss 1.06119  val_loss 0.84237  val_AUPRC 0.0423
          val_P@50 0.240  mean_prob 0.33423  distinct 84,067   0.9s

And after the first epoch, the guards print their actual values rather than a verdict:

guard | predicted prob min 0.045485 max 1.000000 mean 0.334230 std 0.204481
guard | 84,067 distinct predicted values, ok
guard | val AUPRC 0.0423 > random baseline 0.00425, ok
The line to point at if challenged on fairness. pos_weight (train only) = 229.7. If it ever printed 244 instead, the 27-day row mask was not applied before the weight was computed, which would mean the two models trained on different rows. One number in the log separates correct from silently wrong.

checkpoints/*.pt the trained models

Question it answers: can I use this model again? A .pt file is PyTorch's save format — technically a zip archive, not readable by eye.

Each one carries four things, not just the weights:

the weights641 numbers for Model A, 4,897 for Model B
the decision thresholdthe cutoff chosen on validation. A model without it is not a working system.
the standardiserthe mean and spread used to scale the inputs — so the same transform is reapplied exactly
the configurationwhich model, which seed, one day or twenty-eight, which device

Why this matters: Stage 7 loads a checkpoint and re-applies the stored threshold and standardiser rather than recomputing them. Recomputing either on the test set would be leakage. Storing them inside the file is what makes that impossible by accident.

Six real files — two models × three seeds — at ~6 KB each for Model A and ~24 KB for Model B.

figures/*_curves.png the training curves

Question it answers: did it actually learn? This is the single most convincing artifact you can show — it is hard to fake a loss curve.

What healthy looks like: training loss falls steadily; validation AUPRC rises then flattens; the run stops shortly after the best point.

One thing on Model B's curve will look wrong and isn't. Its validation loss rises while its validation AUPRC also rises — loss 0.336 → 1.076 while AUPRC went 0.254 → 0.713. That is why the project stops on AUPRC and not on loss: stopping on loss would have halted Model B around epoch 8 at AUPRC ≈ 0.43 and thrown away two-thirds of the result. Have that explanation ready, because it is the sort of thing an examiner spots and asks about.

stage3_gate.csv the go / no-go table

Question it answers: was the signal there before any model existed? One row per insider, all 70, produced by Stage 3 before anything was trained.

user, scenario, days, window_days, peak, late_ratio,
pre_attack_max, attack_max, lift_max, passes_max,
pre_attack_mean, attack_mean, lift_mean, passes_mean

Reading one row — AAM0658, a scenario-1 insider:

window_days 7his attack lasted 7 days
pre_attack_max 2.10before the attack, his loudest feature averaged 2.1σ
attack_max 9.20during it, 9.2σ
lift_max 4.384.4× louder during the attack than before it
passes_max Truecleared the 2σ bar

Why both _max and _mean: collapsing 18 z-scores into one number is ambiguous and the conclusion flips depending on which you pick — the mean dilutes a sharp three-feature attack across fifteen features that never moved, the max is noisy enough that an ordinary day clears 2σ. The project reports both, always, rather than resolving it quietly.

The result: 66 of 70 insiders cleared 2σ. That is what licensed building the rest of the project.

If you only remember one thing about these folders.

data/ is the pipeline — one file per stage, each the input to the next. outputs/ is the evidence — numbers, transcripts, weights and pictures. Anything with .sample in its name is a rehearsal and must never be quoted, and anything with _v2 is an experiment that lost.
