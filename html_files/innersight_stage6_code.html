InnerSight · Stage 6 code · defence preparation

Walk me through the code

Stage 6 is the smallest stage in the project and the most consequential. One class, one entry point, nineteen tests, and nothing else touched. What was added, how the 28-day window is cut without allocating 880 MB, the three ways this stage could have produced numbers that were quietly meaningless, and the test the brief asked for that had to be thrown away because it did not work.

The one-sentence answer to “what did you write for Stage 6?”

“A convolutional network that reads twenty-eight days instead of one, and a command-line entry point that hands it to the existing training loop. That is deliberately all of it — the data pipeline, the training loop, the metrics and the three-seed runner were written in Stage 5 to be model-agnostic, so Stage 6 changes nothing about how the two models are trained. If I had needed to edit any of those four files, the two models would not have been trained identically and the comparison would have been weaker for it.”

1.1 — The two expressions that differ from Model A's entry point

run_model_b.py and run_model_a.py are the same file with two substitutions:

Everything else — device resolution, data preparation, the class weight, the three-seed sweep, checkpointing, aggregation, the curves figure — lives in runner.py and is executed by identical code for both models.

One deliberate deviation from the project's own convention. Model B's three architectural constants — 32 channels, kernel 3, dilation 2 — live in models.py rather than in config.py where every other hyperparameter lives. The reason is the prime directive: a constant added to config.py is harmless in fact but not provably harmless by inspection, and “both models ran under identical settings” is the claim the entire project rests on. It is a wart, it is intentional, and it is written down.

2 — Model B, line by line

modeling/models.py 
self.conv1 = nn.Conv1d(18, 32, kernel_size=3, padding=1, dilation=1)
self.conv2 = nn.Conv1d(32, 32, kernel_size=3, padding=2, dilation=2)
self.head  = nn.Linear(32, 1)

def forward(self, x):                     # x is (batch, 18, 28)
    h = relu(self.conv1(x))               #      (batch, 32, 28)
    h = relu(self.conv2(h))               #      (batch, 32, 28)
    return self.head(h.mean(dim=2)).squeeze(-1)   # (batch,)

The input is channels-first, and that is not a formatting preference

Conv1d reads (batch, channels, length). Here the eighteen features are the channels and the twenty-eight days are the length, so the convolution slides along time. Getting this backwards is the central hazard of the whole stage — §5 is about nothing else.

Why the padding numbers are 1 and 2

Both layers use “same” padding, so the time axis stays 28 long from input to pool. For an odd kernel the required padding is dilation × (kernel − 1) ÷ 2 — which is 1 for the first layer and 2 for the second. If it were left at 1 for both, the second layer would shorten the sequence and the average at the end would be taken over a shrinking remnant of the window rather than the window.

Why the second layer skips a day

Two stacked kernel-3 layers see five days. Setting the second layer's dilation to 2 — look at every other position rather than every position — extends that to seven days, at exactly the same parameter count.

1 + (3−1)·1 + (3−1)·2  =  7 days of reach, for 0 extra parameters

Since scenario 2 is a 45–59 day drift, temporal reach is the scarce resource. Buying it with more layers would cost parameters this model cannot afford; dilation buys it for nothing. The tests assert both that the reach is 7 and that the dilated and undilated versions have identical parameter counts, so the claim cannot silently stop being true.

The parameter count, and the tripwire on it

conv1   18 × 32 × 3 + 32  =  1,760
conv2   32 × 32 × 3 + 32  =  3,104
head              32 + 1  =     33
                             ─────
                             4,897

There is a test asserting exactly 4,897. It exists as a tripwire against a future “improvement”: roughly 1,147 attack days in the training split against 4,897 parameters is about 0.23 positives per parameter, already thinner than Model A's 1.8. A deeper Model B would memorise those rows and win the comparison for the wrong reason.

The return shape is (batch,), not (batch, 1), and the brief asked for the latter. This is a deliberate departure. BCEWithLogitsLoss given a (batch, 1) input against a (batch,) target does not raise — it broadcasts to (batch, batch) and trains perfectly happily on a loss that compares every prediction to every label. There is no error and no warning; the model simply learns nothing meaningful. Model A returns (batch,), the prediction buffer in the training loop is (n,), and Model B matches both.
And no sigmoid in forward. The loss function applies one internally for numerical stability. A second one squashes the output twice: gradients shrink toward nothing and the model barely trains, with no error and a loss curve that merely looks disappointing. A test feeds inputs scaled by 50 and asserts the outputs land outside [0, 1].

3 — The window: 28 days per row without allocating 880 MB

The obvious implementation is to build a tensor of every window up front. It does not fit comfortably:

437,000 target rows × 18 features × 28 days × 4 bytes  ≈  880 MB

…and it would store every row up to 28 times over. Instead, SplitData keeps every row of its people's history in one contiguous array plus a list of positions marking which rows are prediction targets, and the windows are cut per batch:

modeling/data.py — written in Stage 5, called for the first time in Stage 6 
offsets = arange(-27, 1)                       # -27 … 0
rows    = positions[batch].unsqueeze(1) + offsets
gathered = features.index_select(0, rows.flatten())
return gathered.reshape(-1, 28, 18).permute(0, 2, 1)   # (batch, 18, 28)
The reason this matters beyond memory. Model B reads the same array Model A reads, with the same scaler already applied, through the same code path. A second tensor built by a second function is exactly where two runs quietly stop being identical. Slicing on demand costs nothing and removes that risk entirely.

Three properties this has to have, and how each is guaranteed

PropertyWhy it would be silent if brokenGuaranteed by

How the window test actually works, because it is the neatest thing in the file. The synthetic table encodes the person's identity into feature 0 and the day index into feature 1, at magnitudes small enough to survive the ±10 clip untouched. Standardisation is affine, so inverting it recovers the codes exactly. The test then reads the gathered windows back and asserts that every one of the 28 rows carries the target's own person-code, and that the day-codes are 28 consecutive integers ending on the target's day. It checks the contents rather than the shape.

4 — The three lines that could have gone silently wrong

The class weight is a fingerprint of which rows were used

It is computed from the training split on every run, never written down:

pos_weight (train only) = 229.7  [263,462 negatives / 1,147 positives]

Computed on the whole table it comes out near 244; computed on the rows that are actually scored — after the 27-day warm-up mask — it comes out near 230. So the single number 229.7 proves the mask was applied before the weight, and it matches Model A seed for seed. The entry point prints the three expected values as a banner before training starts, so a wrong number is visible immediately rather than in the metrics file afterwards.

The row set is decided once, in Stage 5, for both models

Model B cannot score anybody's first 27 days. If Model A scored them and Model B did not, the two would be measured on different data — and those rows are the warm-up period where every feature is exactly zero, the easiest negatives in the table. Dropping them lifts the positive rate, and AUPRC rises with the positive rate mechanically. Model B would have collected roughly 6% for nothing. So the mask applies to both models, for training and evaluation alike, and it is Stage 5's code rather than Stage 6's.

The fairness watch, which exists to catch a bias in Model B's favour being absent

modeling/run_model_b.py 
if best_epoch >= epochs_run - 1:
    warn("validation AUPRC was still improving when training ended")

All three of Model A's seeds stopped on patience with room to spare. A 4,897-parameter CNN can converge more slowly than a 641-parameter network, and a Model B cut off while still improving would be biased against the hypothesis being tested. The fix, if it fired, would be to raise the budget for both models and re-run Model A too — raising it for B alone would turn the training budget into a second variable. It did not fire.

5 — The test the brief asked for, and why it was thrown away

This is the part of Stage 6 worth talking about.

The brief specified the most important test in the stage: prove the convolution runs across days and not across features. Its suggested method was to feed a ramp rising over the 28 days and assert the output changes when the ramp is reversed — since a feature-axis convolution would be blind to the reversal.

That test does not work. It was written, and then it was tested against the bug it was supposed to catch.

The mutation check that killed it

Rather than trust the test, the broken model was written out explicitly — a Conv1d stack wired around the day axis, days as channels — and the ramp test was run against it across eight random initialisations:

wrong-axis model, response to reversing the ramp:
  8.67e-03  4.63e-03  3.34e-03  8.79e-03  1.34e-02  1.09e-02  1.19e-03  8.83e-03

it responded every single time.  The test would have PASSED on the bug.

The reason, once seen, is obvious: reversing the ramp also permutes the channels that a feature-axis convolution reads, so that model notices too. Both models respond, so the test discriminates nothing. It would have sat in the suite looking reassuring while the model produced meaningless numbers.

What replaced it: translation invariance

The property that genuinely separates the two orientations is that a convolution over time, with “same” padding followed by a global average, gives the identical answer to a pattern that has moved along the window. Slide the pattern, the feature maps slide with it, the mean is unchanged. A feature-axis convolution hands the shifted pattern to an entirely different set of filters.

identical bump at days 8–11  vs.  days 16–19,  8 initialisations each:

  ModelB              max response   1.49e-08     ← invariant, as required
  _FeatureAxisModel   min response   7.47e-03     ← six orders of magnitude larger
And the broken model ships in the test file permanently. _FeatureAxisModel lives in test_model_b.py alongside a second test asserting that the first one fails on it. That is the difference between a guard and a decoration: the suite proves that its most important test would actually catch the failure it names, rather than merely passing on correct code.
The line to use

“The brief told me what the most dangerous silent failure was and suggested a test for it. I wrote the test, then I built the bug and ran the test against it — and the test passed. So I threw it away and found a property that does discriminate, by six orders of magnitude. The broken model is still in the test file, with a test asserting the guard fails on it. A test for a silent failure is only worth its lines if the failure would actually trip it.”

A smaller correction from the same investigation. The brief also stated that Conv1d would accept a transposed (batch, 28, 18) batch “without error”. It would not: 18 ≠ 28, so PyTorch's own channel check raises. ModelB.forward validates the shape anyway and names the failure explicitly, because the dangerous version of this bug is a model built around the wrong axis rather than fed a wrong batch.

6 — The 19 tests

Same criterion as Stages 1 to 5: cover the failures that are silent — no exception, no missing value, just a number quietly wrong that survives into a results table.

The time axis — 6 tests

Translation invariance (the important one); the mutation check proving it fails on _FeatureAxisModel; that a transposed batch is refused rather than convolved; that the wiring is right (conv1.in_channels == 18, “same” padding on both layers); that the reach is 7 days at an unchanged parameter count; and that a sustained lift across the whole window actually reaches the output, which is what checks the pool is over days rather than a no-op.

The mechanism itself — 1 test

That the model can tell a rising trend from a falling one. Not a failure guard but a capability check, and it is the property the entire thesis depends on: a model blind to the direction of a drift would have no way to profit from a 28-day window.

Window contents and person boundaries — 3 tests

Every window holds 28 consecutive days ending on its target's own day; every row of every window carries the target's own person; and a target sitting inside its person's warm-up is refused rather than wrapping to the previous person.

Both models see the same rows — 2 tests

Same count, same order, same labels, and the last column of each window is exactly Model A's input row. Plus: the class weight comes from the prepared labels, so it cannot differ between the two views by construction.

Raw logits — 1 test

Outputs land outside [0, 1] under large inputs, and no sigmoid module exists anywhere in the graph.

Determinism — 2 tests

The same seed twice gives bit-identical weights, seeding in the order runner.py actually uses — before the model is constructed, because seeding afterwards draws the initial weights from whatever state the process happened to be in. Different seeds give different weights.

Shape and size contract — 3 tests

(B, 18, 28) in and (B,) out for batch sizes 1, 7 and 512; the 4,897-parameter tripwire; and refusal of an even kernel or a reach longer than the window, either of which would silently make the second layer a no-op.

End to end — 1 test

The CNN and the window view go through the unmodified Stage 5 training loop and beat the random baseline. This is the prime directive expressed as a test: if it needed a change in train.py, the two models were not trained identically.

6 + 1 + 3 + 2 + 1 + 2 + 3 + 1 = 19, on top of Stage 5's 28, for 47 in about four seconds. None of them needs r4.2 present — they build a small synthetic calendar-dense table.

Why nineteen and not two hundred. Stage 6 adds exactly one class, so it adds exactly one new family of failure: everything to do with the second axis of the input. A test that a function returns a float is not worth its line. A test that a window ends on the right day is the difference between a result and an artefact.

7 — What is in a checkpoint, and how Stage 7 loads both models

Why all three travel together. A model whose decision threshold lives in a notebook and whose input scaling lives in a dataframe is not a working system — it is a matrix. Stage 7 has to apply exactly the transform these weights were trained under and exactly the threshold validation chose, and the only way to guarantee that months later is for the file to carry them.

Both models' checkpoints are written by the same function in runner.py and have the same shape, and each declares its own input_kind. So Stage 7 loads both through a single code path and builds the right view from the file rather than from an assumption — which also means there will be exactly one place in the codebase that opens the test split.

8 — The tuning branch: built, run, measured, reverted

After the result was recorded, three changes to Model B were implemented behind a --tuned flag: dropout, mean-and-max pooling, and a cosine learning-rate decay. Two things about how that was done are worth describing, because they are the reason the reported result survived it.

Every option defaulted to the reported behaviour

Nothing was rewired. A new pooling mode, a new schedule option and a passthrough for training overrides were added, each defaulting to exactly what Model A and Model B had already been trained with. That was verified rather than claimed: both models' outputs were captured before the change and re-compared field by field afterwards, excluding wall-clock timings. Identical for both. A test was added pinning the defaults, so a future change that shifted one would fail a test instead of silently invalidating two runs and a report.

The variant could not overwrite the result

The flag forced an output tag, so the tuned run wrote to *_v2_* filenames. There is a test asserting that the tagged checkpoint, metrics and figure paths all differ from the untagged ones — because a variant silently overwriting thirteen minutes of reported results is the single most expensive mistake available in this stage, and in Stage 1 a smoke run did once replace a real table.

The tuned model scored 0.6022 against Model B's 0.6767. It lost. The code was reverted to the exact state that produced the reported result — the shared files restored from the pristine Stage 5 copies and re-verified identical, the suite back to 47 tests, and the sample run re-checked field by field against a pre-change baseline. The measurement was kept, in STAGE6_TUNING_RESULT.md, because the way it lost is a finding: adding a maximum channel raised scenario-1 recall 6.6 points and cost 11.0 points of scenario 2, which is 88% of the positives.

The honest note on that revert. The flags are gone from the code, so the run instructions written for them were replaced with a stub pointing at the result. The *_v2_* output files were left in place deliberately — they are the evidence behind the claim, and deleting them would leave the write-up asserting a measurement with nothing behind it.

9 — Questions to rehearse

Show me the part of the code that makes the comparison fair.

It is mostly the absence of code. The training loop takes a model object, two input views, labels and a config, and nothing in it inspects the model — there is no branch that knows whether it is training a small network on one day or a convolutional one on twenty-eight. So Stage 6 hands it a completely different architecture and changes nothing about how training happens.

Concretely: data.py, train.py, runner.py and metrics.py are byte-identical to their Stage 5 versions, checked by file comparison after the run rather than remembered. The two entry points differ in two expressions: which model class, and which view of a split. Everything else executes the same lines.

How do you know the convolution is looking at time and not at the features?

Because a pattern moved eight days later scores identically — 1.5 × 10⁻⁸ of difference across eight random initialisations. Convolution over time with “same” padding and a global average is translation-invariant; a convolution over features hands the shifted pattern to different filters and the answer moves by about 10⁻².

And I know that test discriminates because I built the broken model and ran it against it. The first version of the test — the one suggested in the brief, reversing a rising ramp — passed on the broken model every time out of eight. It would have been a test that proved nothing. The broken model is still in the test file with a test asserting the guard fails on it.

You have 437,000 windows of 18 by 28. How does that fit in memory?

It does not, and it is never built. Materialising them would be about 880 MB and would store each row up to 28 times over. Instead each split keeps every one of its people's rows in one contiguous array plus a list of positions marking which rows are prediction targets, and each batch's windows are cut on demand by an index operation.

The memory saving is the smaller benefit. The important one is that Model B reads the same array Model A reads, with the same scaler already applied, through the same code path — rather than a second tensor built by a second function, which is exactly where two runs quietly stop being identical.

What stops a window from reaching into the previous person's data?

Two things, one structural and one asserted. Structurally, each person's rows are contiguous and in date order, and the row mask guarantees no target is ever within a person's first 27 rows — so reaching back 27 always stays inside that person. Defensively, window_view() checks that invariant and raises if it is ever violated, rather than wrapping around to the previous person's history.

And there is a test that proves it on real gathered data rather than by argument: the person's identity is encoded into a feature at a magnitude that survives the clip, the scaler is inverted to recover it exactly, and the test asserts that all 28 rows of every window carry the target's own code.

Why does the model return a flat vector instead of a column?

Because a column would be a silent disaster. The loss function given a (batch, 1) input against a (batch,) target does not raise — it broadcasts to (batch, batch) and compares every prediction to every label. Training proceeds, the loss goes down, and the number means nothing.

The brief actually specified a column. I departed from it and documented why. Model A returns a flat vector, the prediction buffer in the training loop is a flat vector, and there is a test asserting the shape for three different batch sizes.

Why are Model B's constants not in the config file with everything else?

Because Stage 6's rule was that it adds an architecture and edits nothing else, so that Model A could not possibly have been trained under different settings. Adding constants to the config file would have been harmless in fact but not provably harmless by reading the diff.

It is a deliberate inconsistency with the rest of the project, it is documented in the file itself, and it should be moved once the comparison is finished. I would rather have one visible wart than a change that requires trusting me about its effects.

You added tuning code and then removed it. Did that disturb the result?

No, and I checked rather than assumed. Every option defaulted to the behaviour already reported, and the variant wrote to separate filenames with a test asserting it could not collide with the real ones. Before making any change I captured both models' outputs; afterwards I re-ran and compared them field by field, and they were identical.

After the tuned model lost, I reverted. The shared files were restored from the pristine Stage 5 copies and re-verified byte-identical, the suite went back to 47 tests, and the sample run was re-compared against the pre-change baseline. The measurement was kept because the way it lost is a finding; the code was not.

If you had to point at one line as the most dangerous in the stage, which is it?

The permute at the end of the window gather — the one that turns (rows, days, features) into (rows, features, days). Every silent failure in this stage lives there or downstream of it. Get it wrong and every tensor still has a plausible shape, training still converges, the loss curve still looks healthy, and the model is convolving across features while treating days as independent channels.

That is why the most important test in the file is behavioural rather than structural, and why it ships with a proof that it catches the bug it names.

The sentence to end on.

“Stage 6 is about a hundred and twenty lines of model and entry point, and nineteen tests. It is small because Stage 5 was built so that it could be — the data pipeline, the training loop, the metrics and the three-seed runner are byte-identical to what Model A was trained under, checked rather than remembered. The interesting work was not writing the network; it was working out which mistakes would have produced a plausible number and no error at all, and then proving that the tests for them actually catch them — including the one the brief recommended, which did not.”
