InnerSight · Stage 2 code · defence preparation

Walk me through the code

The two files in labeling/, what each part does and why it is written that way, the exact lines someone might point at, and why there are 16 tests and not 60.

The one-sentence answer to “what does your code do?”

“It gives each person a complete calendar, filling the days they generated nothing with zeros, then goes through the 70 attack periods from the answer key and marks the days inside them — turning a list of date ranges into a yes/no answer on every single row, without deleting a row or changing a number.”

1 — What is in the folder

labeling/
├── __init__.py        what the stage is, and how to run it
├── label.py           the program — about 700 lines including comments
├── test_label.py      16 tests
└── README.md          the stage written up, with the measured results

It is laid out the same way as extraction/ (Stage 1): program, tests, README, run from the project folder. Everything it needs — file paths, column names, the release number — comes from config.py. Nothing is typed in twice.

terminalpython -m labeling.label                  # the real table,  ~4 seconds
python -m labeling.label --sample         # 30-person sample, ~1 second
python -m labeling.label --user KPC0073   # print one person's days
python -m pytest labeling/test_label.py   # run the 16 tests
Why --sample saves to a different filename. Stage 1 got burned by this exactly once: the quick test run and the real run saved to the same file, so a 7-second test silently wiped out the 1,000-person table — and every later stage would have used the small one without complaining. Now they are two separate filenames and the flag picks which. Tiny guard, but the failure it prevents shows up only as results that look suspiciously good.

2 — How the program is put together

Three functions do the work. Each one takes data in and gives data back — no files, no hidden state — which is what makes each one testable on its own.

read the counts file ──┐
                       ├─→ build_labelled_counts(daily, windows)
read the answer key ───┘         │
                                 ├─→ calendar_fill(daily)          add the missing days
                                 └─→ attach_labels(filled, windows)   add the two columns
                                             │
                                             ├─→ verify(...)         stop if something is impossible
                                             ├─→ format_report(...)  print the checks
                                             └─→ save the file

Keeping attach_labels separate matters for one practical reason: it works on any table with a person column and a day column, filled or not. That is what lets a test run the same labelling on the filled and unfilled version of one input and prove the answer is different.

3 — Reading the answer key

Read every column as text

label.py# Every column as text. `dataset` in particular must never be inferred as a
# float -- "4.2" and 4.2 are different filter keys and only one of them is
# right, and a numeric read also silently reformats "4.10" style ids.
answers = pd.read_csv(path, dtype="str")

windows = answers.loc[answers["dataset"].str.strip() == release].copy()

The answer key holds all ten CERT releases — 190 lines, of which 70 are ours. If pandas decides the release column is a number, comparing it to the text "4.2" matches nothing, and we save a table with zero bad days. That table would train, evaluate and report perfectly happily, scoring zero forever, and it would look like a modelling problem rather than a typing problem. This is the single most dangerous line in the file.

Finding nothing is an error, not an empty answer

label.pyif windows.empty:
    found = sorted(answers["dataset"].dropna().unique())
    raise GroundTruthError(
        f"no rows in {path} have dataset == {release!r}. Values present: "
        f"{found}. Note this must be compared as a string.")

The error message lists the values it did find, because the realistic cause is either the typing problem above or a rebuilt answer file — and both are obvious from that list. An empty answer key must never be treated as a valid result.

Cut off the clock time immediately, not later

label.pydef _to_day(stamps: pd.Series) -> pd.Series:
    return pd.to_datetime(
        stamps.str.strip(), format=INSIDERS_DATE_FORMAT
    ).dt.normalize()

Our rule is "day falls between the start day and the end day". Cutting the time off here makes that sentence literally true of the values we store. Doing it later, at comparison time, would make it true only as long as every future comparison remembers to do it — and if one forgot, the result would be a one-day error on a few insiders. No crash, no warning, and nothing in the totals would look wrong.

The date format is written out rather than guessed. Inside release 4.2 all 70 attacks use MM/DD/YYYY HH:MM:SS, but other releases in the same file are not padded — 3/6/2010 1:41:56 appears under r2. Filtering to our release first is what makes one strict format safe.

4 — Filling in the calendar

4.1 The list of days is built with arithmetic, not a loop

label.pyspan = daily.groupby(USER_COLUMN, sort=True)[DAY_COLUMN].agg(["min", "max"])
lengths = ((span["max"] - span["min"]).dt.days + 1).to_numpy()

starts = span["min"].to_numpy()
# Offset of each row within its own user's run: a global arange minus the
# arange value at which that user's run began.
run_starts = np.repeat(np.cumsum(lengths) - lengths, lengths)
offsets = np.arange(int(lengths.sum())) - run_starts

The obvious way is a loop that builds a date range for each person and glues 1,000 pieces together. This way is faster — but speed is not the reason, because at 1,000 people both finish instantly.

The reason is that there is no per-person step that could go wrong for one person and not the rest. Everyone's dates come from the same two operations, so the code either works for everybody or fails visibly for everybody. A loop with a mistake in an edge case — say, a person with exactly one recorded day — would give a table that is correct for 999 people and quietly one row short for the thousandth. Nobody would notice.

4.2 Join, then fill, then fix the number types back

label.pyfilled = complete.merge(daily, on=list(KEY_COLUMNS), how="left")

# A left merge marks the inserted days as NaN. Every one of those is a real
# zero -- a day this person was employed and generated no event.
for name in features:
    filled[name] = filled[name].fillna(0).astype(dtypes[name])

Two deliberate things here.

We save the number types before the join and put them back after. When you join like this, any column that gains a single missing value gets converted from whole numbers to decimals. A table of 464,687 rows where every count is quietly a decimal would flow all the way to the models without a single complaint. Seventeen features go back to whole numbers, and total email size goes back to a decimal because it always was one.

We fill the gaps first and convert afterwards, never the other way round — a whole-number column cannot hold the "missing" value the join creates, so converting first would fail outright.

5 — The lines someone might point at

Why we loop over 70 attacks instead of 464,687 rows

label.pyrows_by_user = daily.groupby(USER_COLUMN).indices
days = daily[DAY_COLUMN].to_numpy()

for window in windows.itertuples(index=False):
    positions = rows_by_user.get(getattr(window, USER_COLUMN))
    if positions is None:
        continue
    window_days = days[positions]
    in_window = (window_days >= ...start) & (window_days <= ...end)
    inside[positions[in_window]] = True

Looping over rows in Python at this size would be indefensible. Looping over attacks is 70 turns, and each one only touches the ~460 rows belonging to one person, so the whole thing takes milliseconds.

It also has a property the alternatives don't: because the loop only ever writes "yes", two overlapping attacks for the same person would combine correctly on their own. A join-based version would silently duplicate rows instead. No person in r4.2 has two attacks — but the code doesn't depend on that staying true.

Both ends of the attack count

label.py# Inclusive at both ends: a 65-minute window still owns its whole day.
in_window = (window_days >= np.datetime64(start)) & (window_days <= np.datetime64(end))

>= and <=, not > and <. BIH0745's whole attack is one afternoon; with an exclusive end he would have zero bad days, and the check "every insider has at least one bad day" would fire. Two tests pin this down — one for a multi-day attack's first and last day, one for an attack that starts and ends on the same date.

An attack naming someone who isn't in the table is skipped

label.pypositions = rows_by_user.get(getattr(window, USER_COLUMN))
if positions is None:
    continue

This is what makes --sample work. The 30-person sample contains 9 of the 70 insiders, so 61 attacks name people who simply are not there. Skipping them is right.

The situation that would be a problem is different: an insider who is in the table but ends up with no bad days, meaning their attack fell outside their employment dates. That is caught separately by the report, because it is a data problem rather than a code problem.

Both new columns are stored as small integers

label.pylabelled[SCENARIO_COLUMN] = (
    labelled[USER_COLUMN].map(scenario_by_user)
    .fillna(BENIGN_SCENARIO).astype("int8"))
labelled[LABEL_COLUMN] = _window_mask(labelled, windows).astype("int8")

int8 holds numbers from −128 to 127. Our values are 0–3 and 0–1, so it is honest about the range, and across 464,687 rows it is the difference between 7 MB and under 1 MB.

The .fillna(BENIGN_SCENARIO) is doing the real work. Looking up a person in the answer key gives "not found" for 930 of the 1,000 employees, and we turn that into an explicit 0 — normal employee — rather than leaving it as a missing value that could spread through later calculations.

The column name is imported, never typed

config.pyLABEL_COLUMN: Final[str] = "label"
SCENARIO_COLUMN: Final[str] = "user_scenario"

The answer key already has a column called scenario, meaning the same idea at a different level. Two columns with one name is how a join produces scenario_x and scenario_y and somebody picks the wrong one. Ours is user_scenario, the name lives in config.py, and Stages 3 to 7 import it from there.

The answer-key path is a function, not a fixed value

config.pydef insiders_csv_path() -> Path:
    return resolve_answers() / INSIDERS_FILENAME

Every other path in config.py is a fixed value. This one can't be, because the answer key may live on an external drive. Working it out at startup would make config.py fail to load whenever the drive is unplugged — which would break every stage in the project, including the ones that never touch the answer key.

6 — Two kinds of checking, and why both

Same split as Stage 1, for the same reason. Tests prove the code does what we wrote. Runtime checks prove that what we wrote is true of the real world.

verify() — stops the programformat_report() — just prints
Containsthings that are impossiblethings that are surprising
If it failserror, run stopsprints CHECK instead of ok
Examplea bad day belonging to a normal employeean insider with no bad days at all

The difference is worth being able to explain. A bad day on someone the answer key never mentions cannot happen if the join worked — that is a broken program, so it stops. An insider with no bad days is a statement about the data: their attack fell outside their employment dates. That needs looking at, but it is not necessarily wrong, and stopping would be the code overruling the dataset.

actual output from the real runSanity checks:
  ok    70 users flagged as insiders             70 flagged
  ok    every insider has >= 1 positive row      none missing
  ok    no label=1 row belongs to a benign user  none
  ok    user_scenario constant per user          0 user(s) vary
  ok    no NaNs anywhere                         none
  ok    no duplicate (user, day)                 0 duplicates
  ok    row count did not decrease               330,452 -> 464,687
  ok    labels are 0/1 only                      [0, 1]
The check that would be easiest to leave out and hardest to miss: "row count did not decrease". The fill is only supposed to add rows. But a join with a slightly wrong key column, or a duplicate in the input, quietly gives you a table that is smaller or bigger than it should be — and every number downstream would still look reasonable. Comparing the before and after count is one line and catches a whole family of join bugs.

7 — The 16 tests, and why those 16

The rule for choosing them is written at the top of the test file, and it is inherited from Stage 1: test the things that go wrong silently. No crash, no missing value — just a labels column that is slightly off, and a model that appears to train fine.

The labelling rule — 5 tests

If asked “only sixteen tests?”

“Sixteen tests chosen by a rule, not sixteen tests to hit a coverage number. Every one targets a failure that gives no error message — a boundary off by one day, a filter that matches nothing, whole numbers turning into decimals, a duplicate that multiplies rows. Testing that a day inside an attack gets marked 1 would raise the coverage number and catch nothing, because that failure is obvious the first time you print the output. The one I'd point at is fill_makes_a_silent_day_labellable — it labels the same data twice, once filled and once not, and checks the answer is different. That's the entire reason for this stage, written as a test.”

What the tests deliberately don't do

None of them read the real dataset. Every test builds its own three to seven rows, including a small fake answer key written to a temporary folder. That keeps the whole suite under a second — and, more importantly, keeps it honest. A test that read the real answer key and checked for 1,892 bad days would still pass if the rule were wrong in a way that happened to give the right total. The real table is checked separately, by going through all 70 attacks by hand.

8 — Questions to rehearse

Walk me through what happens when I run this.

It reads the counts file, then reads the answer key as text and keeps only release 4.2 — that gives 70 attacks, and the clock times are cut off both ends. Then it works out each person's first and last day, builds the list of every day in between, and joins the counts onto it. Days that weren't there come back empty, get filled with zeros, and the number types are restored. Then it looks up each person in the answer key to fill in user_scenario, defaulting to 0, and goes through the 70 attacks marking the matching days. Four impossible-things checks run, the file is saved, and the report prints. About four seconds in total.

Why is the fill here rather than in Stage 1 or Stage 3?

Not Stage 1, because that is the slow pass — 90 seconds over 16 GB — and nothing that might change belongs inside it. Not Stage 3, because by then the labelling would already have run on a table missing 528 of its 1,892 bad days, and those would be absent rather than wrongly marked, with nothing raising an error. It has to happen after extraction and before labelling, which leaves exactly one place.

You loop in Python over the attacks. Isn't that slow?

It is 70 turns, and each one only touches one person's ~460 rows out of 464,687, so the whole step takes milliseconds. Looping over rows would be indefensible; looping over attacks is not. It also buys correctness — because the loop only ever writes "yes", two overlapping attacks on one person would combine correctly, whereas a join-based version would duplicate rows.

What is the most dangerous line in this file?

Reading the answer key as text, and the comparison right after it. That file holds all ten CERT releases. If the release column gets read as a number, comparing it to "4.2" matches nothing and we save a table with zero bad days. Nothing downstream would object — the models train, the evaluation runs, and every score is zero, which looks like a modelling failure rather than a typing error. That is why finding nothing raises an error listing what it did find, and why one test deliberately includes a 4.20 line that a number-based read cannot tell apart from ours.

Why do some checks stop the program and others only print a warning?

Because they are different kinds of claim. A bad day on someone the answer key never names cannot happen if the join is right, so that is a broken program and the run stops. An insider with no bad days is a statement about the data — their attack fell outside their employment dates — and that needs investigating rather than aborting. Stopping there would be the code overruling the dataset. The report marks it and carries on.

How would you find out if this stage were subtly wrong?

The failure I worry about is being off by one day, because nothing visible changes — the row counts, the percentage of bad days and the per-scenario totals would all still look sensible. So there are three defences. Two tests pin both edges of the window explicitly. The report prints bad-day totals per attack type, which we compared against numbers worked out directly from the answer key. And there is a hand check written in the README: --user KPC0073 must show 1 from 7 to 15 July and 0 on 6 July. That one-day gap only appears if the comparison includes both ends, works on dates rather than times, and is lined up correctly. Off by one in either direction and the gap moves.

The sentence to end on.

“Three functions, sixteen tests, four seconds. The code is small because the job is a lookup. The difficulty isn't the calculation — it's the three or four places where getting it wrong produces no error at all: text compared as a number, a boundary that excludes its own last day, whole numbers quietly turning into decimals, and a bad example that ends up missing rather than mislabelled.”
