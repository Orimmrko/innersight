InnerSight · Stage 3 code · defence preparation

Walk me through the code

The two files in baseline/, what each part does and why it is written that way, the four lines someone might point at, the bug the tests found, and why there are 16 tests and not 60.

The one-sentence answer to “what does your code do?”

“For each person separately, it walks their days in order and turns each of the 18 counts into a distance from that person's own earlier days — with a floor under the division so a never-done-it-before day gives a big number instead of infinity, and the first 30 days blanked because a baseline built from three days isn't one. Then it checks the answer is worth having before anything gets trained on it.”

1 — What is in the folder

baseline/
├── __init__.py           what the stage is, and how to run it
├── baseline.py           the program — about 800 lines including comments
├── test_baseline.py      16 tests

Same layout as extraction/ and labeling/: program, tests, README, run from the project folder. Every path, column name and constant comes from config.py. Nothing is typed in twice.

terminalpython -m baseline.baseline                    # the real table,  ~5 seconds
python -m baseline.baseline --sample           # 30-person sample, ~1 second
python -m baseline.baseline --user KPC0073     # raw counts beside z-scores
python -m baseline.baseline --floor-all-users  # the rejected floor, for comparison
python -m pytest baseline/ -q                  # run the 16 tests
Third stage, third separate sample filename. Stage 1 was burned once when a 7-second test run overwrote the 1,000-person table, so --sample reads and writes its own filenames at every stage. Here that is dataset.sample.parquet against dataset.parquet. The failure it prevents shows up only as results that look suspiciously good.

2 — How the program is put together

read labelled_counts.parquet
        │
        ├─→ std_floors(counts)              one floor per feature
        ├─→ causal_z_scores(counts, floors) the arithmetic
        │        └─ returns (z-scores, which rows were blanked)
        ├─→ verify(...)                     stop if something is impossible
        ├─→ validation_gate(...)            do insiders actually stand out?
        ├─→ format_report(...)              print everything
        └─→ save dataset.parquet

Each function takes data in and gives data back — no files, no hidden state — which is what makes each one testable alone. causal_z_scores in particular takes the floors as an argument rather than computing them, so a test can pass in a floor of exactly 0.5 and check the arithmetic against a number worked out by hand.

3 — The arithmetic, in four lines

Expanding, then shift — in that order

baseline.pygrouped = ordered.groupby(users, sort=False)
# `.expanding()` includes today; `.shift(1)` within the same user removes
# it. Doing it in that order -- rather than shifting the values first -- is
# what keeps the window "all days before t" for every t, including the
# first day of each user, where the shift correctly yields nothing.
mean_prior = grouped.expanding().mean().reset_index(level=0, drop=True)
std_prior  = grouped.expanding().std(ddof=1).reset_index(level=0, drop=True)
mean_prior = mean_prior.groupby(users, sort=False).shift(1)
std_prior  = std_prior.groupby(users, sort=False).shift(1)

expanding() means “everything up to and including today”. The shift(1) slides that answer down by one row within each person, so the value sitting on today's row is the summary of everything before today. Today is out.

The order matters and the comment says why. Shifting the raw values first and then expanding would also produce a number — a slightly different, slightly wrong one — and nothing would flag it.

Both groupby calls are on users, which is what confines every calculation to one person. Drop either and the whole table gets scored against one pooled average.

The division, with the floor

baseline.pydenominator = np.maximum(
    std_prior.fillna(0.0).to_numpy(),
    np.maximum(floors.reindex(columns).to_numpy(), STD_FLOOR),
)
scores = (ordered.to_numpy() - mean_prior.fillna(0.0).to_numpy()) / denominator

Two nested maximums. The inner one guarantees the floor itself is never zero; the outer one uses whichever is larger, the person's real spread or the floor. For someone with genuine day-to-day variation, the floor never binds and they are scored by their own spread. For someone whose count has never moved, the floor is the whole denominator.

3.1 — Why not the textbook variance formula

This is the line that would have produced a file full of missing values. The obvious way to compute a running spread is average of x² − (average of x)². Our total_email_size runs to about 100,000,000. Both of those terms are then around 1016, and subtracting two numbers that size in floating point can come out negative — which becomes a missing value the moment you take a square root. It would appear on some people and not others, in one feature out of eighteen.

So the code uses pandas' expanding() aggregations, which accumulate with a numerically stable running update instead. It is slower in principle and completely irrelevant in practice — 464,687 rows by 18 features takes about three seconds.

There is a test that exists solely to fail if someone ever “optimises” this back into cumulative sums: it builds a feature with values around 108 and asserts no missing values appear.

4 — The lines someone might point at

Sort to compute, restore to write

baseline.py# Sort for the computation, remember how to put it back. Causality is
# defined by chronological order, so this is not cosmetic -- but the
# contract with Stage 4 is that row order survives the stage untouched.
order = counts.sort_values(list(KEY_COLUMNS), kind="stable").index
...
z = z_ordered.reindex(counts.index)

Two requirements pull in opposite directions. “Days before today” only means anything if the rows are in date order. But every later stage relies on row order being unchanged, because that is how the labels line up.

Sorting without restoring would silently reshuffle Stage 4's rows. Restoring without sorting would silently mis-score an unsorted input. A test does both: it scores a table, scores a shuffled copy of the same table, joins the two results back together by person and day, and asserts they agree.

The floor is a median over people who actually do the thing

baseline.pyper_user_std = counts.groupby(USER_COLUMN, sort=False)[columns].std(ddof=1)
if active_only:
    per_user_std = per_user_std.where(per_user_std > 0)
typical = per_user_std.median(skipna=True)
floors = (multiplier * typical).astype("float64")

One line — .where(per_user_std > 0) — and it is the biggest single decision in the file. 73.5% of employees have a USB count that never varies, 81% for after-hours logins, 88.6% for after-hours USB. Include them and the median is exactly zero for eight of eighteen features, the floor falls back to its default of 1, and “one USB connection” becomes one standard deviation on a count that is normally nought.

Measured both ways: the validation gate goes from 54/70 to 66/70 and KPC0073's first USB day from z=2.0 to z=20.9, while the ordinary-day rate moves only 11.6% → 13.4%. The active_only switch is a real argument with a CLI flag behind it, so the comparison is reproducible rather than asserted.

A feature nobody varies still gets a floor

baseline.pydead = ~np.isfinite(floors.to_numpy()) | (floors.to_numpy() <= 0.0)
floors[dead] = fallback   # 1.0

Even after excluding inactive people, one feature has no variation anywhere: large_attachment_count is identically zero for all 1,000 employees on r4.2 — a known dead feature carried over from Stage 1, because the definition is right and the release simply has no data for it. Its floor becomes 1.0, so it contributes exactly zero forever rather than dividing by nothing the day it moves.

Two blanking rules, not one

baseline.pywarmup_ordered = _warmup_mask(users, max(min_history, MIN_PRIOR_DAYS))
scores[warmup_ordered, :] = 0.0

MIN_HISTORY_DAYS is 30 and is the judgement call: a baseline from three days is fiction. MIN_PRIOR_DAYS is 2 and is arithmetic: with no earlier days there is no average, and with one earlier day there is no spread.

At 30 the second bound never binds and changes not one value in the delivered file. It exists so that lowering the warm-up later — a reasonable thing for someone to try — degrades gracefully instead of injecting 1,000 fake spikes. It was added because a test found the bug, not because anyone reasoned about it. See §6.

The scores are written unclipped, on purpose

config.py# Stage 3 does NOT apply this -- it writes the raw z-scores, because the
# whole point of the KPC0073 hand-check is to see the un-clipped number.
Z_CLIP: Final[float] = 10.0

Z_CLIP exists, and Stage 3 deliberately does not use it. Clipping at 10 here would flatten the 107σ that makes the hand-check convincing, and it would do it inside the saved file where nobody could get it back. The constant is a hint for whoever builds the training tensors, and it is the threshold for the “rows with any |z| > 10” line in the report — 2,138 rows, 0.46%, which is how we know the floor is not set absurdly low.

5 — Two kinds of checking, and why both

Same split as Stages 1 and 2. Tests prove the code does what we wrote. Runtime checks prove that what we wrote is true of the real world.

verify() — stops the programformat_report() — just prints
Containsthings that are impossiblethings that are surprising
If it failserror, run stopsthe number is printed for a human to read
Examplea missing value anywhere in the 18 featuresan insider whose attack does not stand out

The distinction is worth being able to explain. A missing value cannot exist if the arithmetic is right, so that is a broken program and it stops. An insider who does not stand out is a statement about the world — that person's attack really is quiet — and stopping there would be the code overruling the dataset.

The four things that stop the run

  • Any missing value or infinity in the 18 features. This is the stage where a wrong floor or an unstable variance formula would show up, and the error message names which columns.
  • Row count or column order changed. Column order is the CNN's channel order — reordering raises nothing and silently invalidates every checkpoint trained afterwards.
  • Either label column changed. This stage never reads the labels to decide anything, so if they moved, something merged that shouldn't have.
  • An attack day inside somebody's warm-up. It would come out as a row of eighteen zeros and be undetectable forever. On r4.2 it cannot happen — the earliest attack is 10 June against data from 2 January — which is exactly why an assertion is the right shape: free, and it catches a changed release.

And one that catches the laziest possible bug

baseline.pyif not (values < 0).any():
    raise BaselineError(
        "no negative z-scores anywhere, so the values are still raw counts")

Raw counts are never negative; z-scores are negative about half the time. If this stage silently passed its input straight through — a plausible bug, one wrong variable name — the output file would have exactly the right shape, exactly the right row count, exactly the right labels, and would train exactly as well as noise. Nothing else in the pipeline would object. One line catches it.

6 — The 16 tests, and the bug they found

The rule for choosing them is inherited from Stages 1 and 2: test the things that go wrong silently. No crash, no missing value — just a number that is subtly wrong and survives all the way to the results table.

Two of these failed on the first run, and one was a real bug. first_day_of_a_user_has_no_history_and_scores_zero and users_are_scored_only_against_themselves both failed for the same reason: with no earlier days at all, the average came out as “missing”, got replaced by zero, and the first row of every person was being scored as value ÷ floor. For a heavy user that is an enormous number that means nothing except “this person exists”. The warm-up was hiding it in production, so it would never have shown up in the output — until somebody lowered the warm-up. The fix is MIN_PRIOR_DAYS = 2.

The second failure was a test that was wrong, not code: a fixture built from a perfectly constant history, which makes every z-score exactly zero and would have passed for the wrong reason. It was rebuilt with variation in it.

If asked “only sixteen tests?”

“Sixteen chosen by a rule, not sixteen to hit a coverage number. Every one targets a failure that gives no error message — a spike measured against an average that includes itself, a division by zero, an off-by-one at the warm-up edge, one person's history leaking into another's. The one I'd point at is the first: sixty flat days and one spike, and it checks the spike was divided by the average from before it — and explicitly not by the one that includes it. That single assertion is the whole idea of the stage, written as a test. And two of the sixteen failed on the first run, which is the best evidence I have that they were worth writing.”

What the tests deliberately don't do

None of them read the real dataset. Each builds its own synthetic person with a handful of days, so the whole suite runs in under a second and stays honest — a test that read the real file and checked for 66 of 70 would still pass if the formula were wrong in a way that happened to give the same total.

7 — How the finished file was checked

The tests check the code. This checks the file.

The delivered dataset.parquet was recomputed by a second, deliberately naive program: a plain Python loop written from the written specification rather than from the module, re-deriving the floors from scratch and re-slicing every person's history by hand. Sixteen people, including every one we hand-checked.

Worst disagreement: 6 parts in 100 million.

Alongside it, checked directly on the saved file rather than the in-memory table: row count, the person and day columns, column order, number types, both label columns, no missing values, the warm-up rows all exactly zero, and no attack day inside a warm-up.

8 — The report is part of the program

Stage 3 prints its validation gate on every run, and one line of that report is there specifically to stop us fooling ourselves:

What a 'pass' is worth - the same threshold on BENIGN users' scored days:
  414,954 benign days: 13.41% already exceed 2 sigma on max|z|, 0.105% on mean|z|
Why that line is in the code and not just in the write-up. “66 of 70 insiders exceed 2σ” is unreadable on its own. If a seventh of every ordinary employee's days also clear the bar, then passing means the insider is loud and the bar is cheap. Printing the benign rate next to the gate, on every run, means the caveat cannot be separated from the headline by accident.

9 — Questions to rehearse

Walk me through what happens when I run this.

It reads the labelled table. First it works out one floor per feature: each person's own spread in that feature, the median across the people who actually vary, times 0.1. Then it sorts by person and day, and for each person runs an expanding average and spread shifted down one row, so each day is summarised by everything before it. Divide, floor the denominator, blank each person's first 30 days, convert to 32-bit floats and put the rows back in their original order.

Then four impossible-things checks, the validation gate over the 70 insiders, save the file, print the report. About five seconds.

What is the most dangerous line in this file?

The .shift(1). Without it every day is scored against an average that includes itself, which means a big day partly cancels itself out — and nothing anywhere would signal a problem. The row count is right, there are no missing values, the numbers are all plausible and simply too small. It would look like a weak signal, and we'd have spent the remaining time blaming the models.

Runner-up is the variance formula. If someone rewrote the expanding aggregation as cumulative sums for speed, total_email_size at 108 would produce a negative variance in floating point and a missing value under the square root — in one feature, for some people. There's a test for each.

You sort the table and then unsort it. Why not just keep it sorted?

Because two different things need to be true. The maths only means anything in date order — “days before today” is defined by the sort. But the contract every later stage relies on is that row order and row count come through this stage untouched, so the labels stay lined up.

Sorting and leaving it sorted would silently reorder Stage 4's rows. Not sorting at all would silently mis-score if anything upstream ever changed its order. So it sorts, computes, and restores — and there's a test that scores a table and a shuffled copy of it and asserts they agree row for row.

Why does one function compute the floors and another use them?

So the arithmetic can be tested with a floor I chose by hand. If causal_z_scores computed its own floors, every test of the division would depend on a population statistic, and I couldn't write an assertion like “this must equal 99 divided by 0.5”. Passing the floors in means the maths tests check the maths and the floor tests check the floor.

It also made the floor comparison possible at all — running the whole pipeline both ways is a one-line change because the floor is an argument, not a hidden step.

Your gate says 66 of 70 pass. Isn't that the code marking its own homework?

It would be, if that were the only number printed. That's why the same report prints how many ordinary employee-days clear the identical bar — 13.4% — right underneath. And it prints both ways of summarising a day side by side, which disagree: 66 of 70 on the peak, 18 of 70 on the average.

The gate's job isn't to say the method works. It's to say whether there is anything for a model to find, before we spend two days building one. If it had come back at 5 of 70 we'd have gone back to Stage 1 instead.

How would you find out if this stage were subtly wrong?

The failure I worry about is a z-score that's plausible and too small, because nothing visible changes — no crash, no missing values, sensible-looking ranges. So there are three defences.

Tests pin the arithmetic against hand-computed numbers, including one that asserts the answer is not the value you'd get by including today. The finished file was recomputed by an independent naive loop written from the spec, agreeing to six parts in a hundred million. And there's a hand check in the README: KPC0073's 6 July has to be large and finite. Infinity means the floor isn't applied; a small number means the shift is inverted. That one value discriminates between the three ways this stage can be wrong.

Why is this a separate stage from the models?

Because it's the part that has to be right before anything else matters, and it's cheap to re-run — five seconds against several minutes of training. Keeping it separate is also what made the validation gate possible: it's a stage whose main output is a question answered, not a file, and that question had to be answered before Stage 5 existed.

And there's a specific thing it must not absorb. Stage 5 standardises each feature across the population; Stage 3 standardises across time within a person. They look similar and they're orthogonal, and merging them would make it impossible to say which normalisation the models are benefiting from.

The sentence to end on.

“Four lines of arithmetic, sixteen tests, five seconds. The code is small because the idea is small — compare today to your own past. The difficulty is in the three or four places where getting it wrong produces no error at all: an average that includes the day it's measuring, a variance formula that goes negative at 108, a floor computed over people who never do the thing, and a first row scored against a history that doesn't exist. Two of those, the tests found before I did.”
