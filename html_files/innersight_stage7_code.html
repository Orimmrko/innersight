InnerSight · Stage 7 code · defence preparation

Walk me through the code

Stage 7 writes no model and trains nothing that is reported. It is a package whose entire job is to make three specific cheats impossible to commit by accident, and then to measure four things. What was added, how each cheat is prevented by structure rather than by care, the fifty-four tests, and the one wart that was found and deliberately not fixed.

State. The package is written, linted and tested — 101 tests pass across the project — and the whole pipeline has been proven end to end on the 30-user sample. The full-release runs are outstanding, so this document describes the machinery rather than the results. None of it changes when the numbers arrive.

The one-sentence answer to “what did you write for Stage 7?”

“A package that loads the two trained models through a single code path, applies the decision threshold and the input scaling that were saved inside their checkpoints, scores the sealed test split once, and writes the report. The interesting part is what it is unable to do: there is no function in it that can fit a scaler on evaluation rows, no import of the threshold-selection code, and no filename pattern that will open the tuning variant that lost.”

Nothing in modeling/ was touched, and that is a load-bearing property rather than tidiness. Stage 7 measures an experiment. If it could edit the code that ran the experiment, “both models were trained identically” would depend on trusting the order in which files were saved. The 47 Stage 5–6 tests still pass unchanged, which is the cheap proof.

1.1 — Why eleven modules rather than one script

Each file answers one question, and the split is not arbitrary — it is the reason the guards are checkable. corpus.py is the only place that builds rows; scoring.py is the only place that produces a probability; guards.py imports both and can therefore assert things about them that a single script would only be able to do. When the claim is “this code cannot refit a scaler”, that claim is worth much more if it is a statement about a module with one job than about a four-hundred-line function.

2 — Three cheats, and how each is made structurally impossible

These are the three ways Stage 7 could have produced a better number with no error, no warning and nothing to notice afterwards. None of them is prevented by remembering not to do it.

2.1 — Refitting the input scaling on the rows being scored

The mean and standard deviation used to scale inputs were fitted on training people in Stage 5 and written into every checkpoint. Refitting them on the test rows would raise the score and raise nothing else.

evaluation/corpus.py 
def build(self, name, seed, standardiser, *, users=None) -> EvalSplit:
    #                     ^^^^^^^^^^^^^^ required argument, never computed here
The scaler is a required parameter of the only function that builds rows. There is no default and no fallback, so there is no code path in the package that can score a split under statistics derived from that split. The caller passes the one it read out of the checkpoint.

A single function in the package does fit a scaler — refit_train_standardiser() — and its docstring says what it is for: it exists so a guard can compare the checkpoint's values against a fresh training-only fit and print both. Its result is never applied to anything, and the only caller is guards.py.

The test that proves it

wrong = Standardiser(mean=full(18, 100.0), std=full(18, 0.5))
split = corpus.build("val", 7, wrong)
assert split.features.mean() < -100      # it really used the one it was handed

A deliberately absurd scaler is passed in. If the module quietly fitted its own, the features would come out neatly standardised anyway and the test would fail.

2.2 — Re-choosing the decision threshold on test

This is the easiest cheat in the project. The threshold was picked on validation by maximising F1; picking it again on test would improve every recall figure and would look completely normal in the output.

The prevention is an absence: evaluation/scoring.py does not import sweep_threshold.

What it has instead is describe_at_threshold(), which computes precision, recall, F1 and the flagged-row count at a cutoff handed in. It is a description, not a choice, and the distinction is the whole of the matter. The evaluation call is always evaluate(..., choose_threshold=False, threshold=<from the checkpoint>).

And a guard on top of the absence

ok  threshold loaded from checkpoint, not re-swept —
    model_a seed 42: 0.958200 (1,168 rows flagged); model_b seed 42: 0.818441 (444 rows flagged); …

The applied value is compared byte-for-byte against the stored one and printed with the number of days it flags. Cheap, and it is the check that would catch a re-sweep introduced later by somebody tidying up.

2.3 — The variant that lost getting into a table

Model B v2 — the tuning attempt with dropout, mean-and-max pooling and a decaying learning rate — scored 0.6022 against 0.6767. Its checkpoints are still on disk, deliberately, because they are the evidence behind the finding about pooling. Nothing stops a tired person from typing that path.

evaluation/checkpoints.py 
_HEADLINE_NAME = re.compile(r"^(?:model_a|model_b)_seed\d+(?:\.sample)?\.pt$")
The exclusion is a regular expression rather than a rule in a document. Every tagged run — model_b_v2_seed42.pt, model_a_nopw_seed42.pt, model_b_w7_seed42.pt — fails to match, so load_checkpoint() raises with an explanation instead of loading. Reaching a control on purpose requires calling load_variant_checkpoint(), which still refuses v2 outright. There is a test for each case.

3 — Building the test split without writing a second pipeline

modeling.data.prepare() deliberately refuses to build the test split — that was Stage 5's way of guaranteeing exactly one place in the codebase could open it. So Stage 7 needs its own way in, and the hazard is obvious: a second pipeline that almost agrees with the first produces numbers that are wrong in a way nothing would ever reveal.

evaluation/corpus.py 
from modeling.data import (
    load_dataset, clip_z_scores, target_mask, load_splits, _build_split,
)
Nothing is reimplemented. The clip, the 27-day warm-up mask, the split lookup and the tensor construction are the same functions the training runs called. If Stage 3 ever changes the parquet, this module breaks in the same place training would — which is the desirable failure.

The one thing that had to be added: the dates

Detection latency is a question about calendar days, and SplitData does not keep them. So EvalSplit carries the day of every scored row alongside the tensors — derived from the same boolean mask and the same positions.

positions  = flatnonzero(is_target[belongs])
users_here = rows[USER].to_numpy()[positions]

if not array_equal(users_here, data.users):
    raise EvaluationError("row alignment slipped …")
Why the assertion is there rather than a comment saying the two must agree. If the date array and the feature tensor ever fell out of step, every latency number would be wrong and every AUPRC would be right — so nothing downstream would look odd. The check costs one array comparison and turns a plausible latency table into an exception.

The raw z-scores are kept too — clipped but not standardised. Section 6's inspection has to print the eighteen numbers for a human to read, and standardised values are the model's units, not a reader's.

4 — One loader, two architectures, no branch that knows which

A loader that has to be told which model it is opening is a loader that can be told wrong, and the entire result depends on both models being evaluated by identical code. Stage 5 and Stage 6 wrote their checkpoints through the same function, so each file already declares what it is:

outputs/checkpoints/model_b_seed42.pt 
model_class     "ModelA" | "ModelB"
input_kind      "point"  | "window"     → which view of a split to build
window_days     1 | 28
threshold       the cut-off chosen on validation
standardiser    mean, std, and the feature order so a reordering is refused
state_dict      the weights, from the best-AUPRC epoch — not the last
def view(self, split):
    return split.point_view() if self.input_kind == "point" \
           else split.window_view(self.window_days)

Three consistency checks run before anything is scored: the architecture named must be one the package can rebuild; input_kind must agree with it (a ModelB stamped "point" is a corrupt file, not a configuration); and the threshold must be strictly inside (0, 1), because a 0 or a 1 means the sweep found nothing and every flagged-row count downstream would be meaningless. The weights load with strict=True, which is the check that the class named in the file is the class the weights belong to.

5 — The detection-latency arithmetic

The measurement that decides what the project may claim, and it is mostly index arithmetic — which is exactly the kind of code that is confidently wrong.

The attack window comes from the labels, not from the answer key

insiders.csv lives on an external drive that is not always mounted, and more importantly it is not what the models were scored against. So an insider's window is derived from their own labelled days: the first labelled day is day 1. Non-contiguous windows are detected and warned about rather than silently accepted — on r4.2 every window is a single date range with a row for every calendar day inside it, so a gap means an upstream assumption has moved.

position = (day - window.first_day).days + 1        # 1-based, day 1 = onset

BUCKETS = (("days 1-7", 1, 7), ("days 8-14", 8, 14),
           ("days 15-28", 15, 28), ("days 29+", 29, None))
“Detected” means a day that is both labelled an attack day and scored above the threshold. A high-scoring day outside the labelled window does not count as a detection here — deliberately, even though §6 argues some of those are real. Crediting them would be scoring the model against a story rather than against the labels. They are reported separately, as their own finding.

The decision rule is a constant, declared before the data

evaluation/latency.py 
PERSISTENCE_RATIO = 1.5     # late/early recall above this → persistence detector
FLAT_RATIO        = 1.25    # within this of each other    → flat
ONSET_MEDIAN_DAYS = 7.0     # median first detection beyond a week → not onset
This is the part worth defending out loud. These three numbers were written before any measurement existed, so the verdict is a consequence of the data rather than a description of it. Choosing them afterwards — even honestly — would make “Model B detects onset” unfalsifiable, because any bucket profile can be described as flat enough if you get to pick “enough” last.

Insiders who were never caught are counted, not dropped

median first detection: day N   IQR a–b   X of Y insiders detected   Z never caught

A median computed only over the insiders that were found is a much better-looking number than one that acknowledges the misses, and it is the number most reports would print. Both appear, always, side by side.

6 — The nine rows: turning an impression into a count

Stage 6 left an anomaly open — Model B seed 123 scored P@10 = 0.100 against P@50 = 0.520, meaning nine of its ten highest-scoring days are labelled benign. The brief asked for those rows to be printed and looked at.

Printing them is easy. The hazard is what happens next: a human looks at ten rows, forms an impression, and writes the sentence they were hoping for. So the module classifies each row and derives the sentence from the counts.

ReadingHow it is decided
insider, inside the window's dates but unlabelledthe day falls between the person's first and last labelled attack day
insider, within 28 days of their windowdistance to the nearest labelled day ≤ 28
insider, far from their labelled windowdistance > 28
a person with no labelled attack at allno window exists for them

Each row also prints its rank over all rows rather than among benign ones — “rank 3” means third-highest overall, which is the number the anomaly is about — plus the loud features above two sigma, and the distance in days from the labelled window.

Then the sentence is chosen by majority, and both possible sentences are written into the code in advance. If most of the rows are insiders' own days near their window, the report says the precision figures are a lower bound. If most belong to people with no labelled attack, it says these are genuine false positives and precision should be read at face value. There is a test for each branch. Deciding the wording before seeing the counts is the only way the flattering version stays honest when it happens to be true.

7 — The guards, and why they print numbers

Two of the brief's required checks specify that values must be printed. That is the entire design of this module: a boolean saying “the scaler came from the checkpoint” carries exactly as much information as no check at all.

ok  seed 42: standardiser loaded from checkpoint, not refit — all 2 checkpoint(s)
    match a train-only refit to 1e-9; mean[0]=-0.017065 std[0]=1.010514,
    mean[1]=-0.016164 std[1]=1.010489, mean[2]=+0.004012 std[2]=0.993616
ok  seed 42: both models scored on identical rows — 93,142 rows, 376 positive
    (0.4037%), digest 322668fc6486dce2
ok  threshold loaded from checkpoint, not re-swept — model_a seed 42: 0.958200 …

The row digest, and why it is a hash rather than a count

sha256( users || days || labels )[:16]

Both models must be scored on identical rows. A row count catches a dropped row. A hash of every row's person, day and label also catches a reordering — which is the failure that would leave both average precisions plausible and both wrong, and which no amount of staring at the output would reveal.

The guard that makes the rest believable

reproduces_training — re-score validation from the checkpoints and compare against what Stages 5 and 6 logged.

If loading the weights, rebuilding the architecture, applying the stored scaler and applying the stored threshold reproduces 0.1237 / 0.1687 / 0.1615 for Model A and 0.7127 / 0.6306 / 0.6868 for Model B, then the identical machinery pointed at the test split is doing what it claims. If it does not, nothing downstream is worth reading.

On the 30-user smoke run it matched to four decimal places on all six checkpoints. It is deliberately non-fatal, because a genuine device difference can move the last decimal — and it prints both figures, so the size of the gap is visible rather than merely classified.

And one guard designed to fail on a good result

if auprc >= 0.95:  →  FAIL, exit code 3

At a 0.4% positive rate with labels this coarse, near-perfect ranking means a split applied by row instead of by person, a scaler fitted on everything, or a label leaking into a feature. This is the guard most likely to be argued with at three in the morning, which is precisely why it is in code and why the entry point exits non-zero on it.

8 — The phase gate and the audit trail

The brief's rule is that Phase 1 finishes before the test split is opened, because after that no model may change. That is a discipline, and disciplines are what fail at midnight before a deadline. Two mechanisms turn it into behaviour.

evaluation/testpass.py 
def require_phase1(...):
    if not artifact.is_file():
        raise PhaseOrderError("Phase 1 has not been run: …
            Brief §4 — once the test split is opened no model may change …")

The ordering becomes a missing-file error rather than a habit.

outputs/TEST_SPLIT_OPENED.json
{"openings": [{"when": "2026-08-08T…Z", "seeds": [42,123,456],
               "sample": false, "forced": false, "reason": "first pass"}]}
A second real opening is refused unless it is forced with a written reason, and the reason is appended to the file. This is not security — anyone can delete the file. It is a note to the person about to do it, at the moment they are doing it, that the number they are about to produce is no longer a single-pass test result and the write-up has to say so. Sample runs are recorded separately and do not burn the real one.

9 — The report writes what was measured, not what was hoped

The generated report contains a great deal of prose, and prose is where a result quietly becomes a claim. Every sentence that asserts a direction is derived from the numbers.

if ratio >= 1.1:   "Model B's average precision is Nx Model A's …"
elif ratio <= 0.9: "Model B scores BELOW Model A on test — that contradicts
                    the validation result and is a finding to investigate
                    and report, not to smooth over."
else:              "The two models are level on test — temporal context
                    bought nothing measurable here, which is itself the
                    answer to the question asked."
This was tested by building the report from data where Model B loses, and reading what it said. The sample split has almost no scenario-1 or scenario-2 attack days, so Model B does badly on it — which made an accidental but useful adversarial case. The prediction scorecard also distinguishes unscored from missed: a scenario with no attack days in the split is not a failed prediction, and calling it one would be inventing evidence.

Missing optional inputs render as a visible “not run — see the cut order” section rather than disappearing. If the seven-day control or the ablation is cut for time, the report has a hole a reader can see, which is worth more than one that looks complete.

10 — The 54 tests

Same criterion as every stage before: cover the failures that are silent. Stage 7's silent failures are all of the form “a number that is a little too good”.

The row set — 7 tests

That the warm-up mask costs exactly 27 rows per person and zero positives; that the date array, the raw z-scores and the feature tensor are aligned to the same rows; that build() uses the scaler it was handed rather than one of its own; that the raw features really are unstandardised; and that the row digest changes under a reordering.

Checkpoint loading — 8 tests

That a v2 path cannot be loaded by either entry point; that nopw and w7 are refused by the headline loader; that a ModelB stamped "point" is rejected as inconsistent; that a threshold of 1.0 is rejected; that missing keys are named; and that a seven-day control's window length is taken from the caller rather than from the file that mis-states it.

The threshold is applied, never chosen — 4 tests

Given labels and scores where a sweep would obviously prefer a different cut-off, describe_at_threshold reports what the cut-off it was given actually does. Plus the zero-rows-above-threshold case, which must be a zero rather than a crash.

Latency arithmetic — 8 tests

On a synthetic corpus with a planted attack of known length: that day 1 of the window is day 1; that the window is derived correctly from the labels; that an insider nobody detected is counted rather than dropped; that the buckets partition positions without overlap or gap; that bucket totals sum to the attack days; and that the decision rule reads a climbing profile as persistence and a flat one as onset.

False-positive classification — 4 tests

That rank is over all rows rather than only benign ones; that all eighteen z-scores are reported; and that each of the two possible report sentences is produced by the counts that should produce it.

The guards — 13 tests

Each one is tested by fabricating the mistake it exists to catch: a scaler fitted on the validation rows instead of the training rows; two models carrying different scalers; a test person planted in the training split; a swapped threshold; two models scored on different row sets; and a model whose predictions rank the labels perfectly, which must trip the leakage ceiling.

Phase ordering and the audit trail — 5 tests

That the test split cannot be opened before Phase 1 has written its file; that a second opening is refused; that a forced one is recorded with its reason; and that a sample run does not burn the real pass.

The report builder — 3 tests

That missing optional inputs say “not run” rather than vanishing; that the random baseline appears beside the headline average precision; and that a report built from sample data is stamped as meaningless.

The capacity control's premise — 2 tests

That ModelB(days=7), ModelB(days=14) and ModelB(days=28) have identical parameter counts — the assumption the entire control rests on — and that a six-day window is refused, because the receptive field is seven.

7 + 8 + 4 + 8 + 4 + 13 + 5 + 3 + 2 = 54, on top of the 47 from Stages 5 and 6, for 101 in about ten seconds. None of them needs r4.2 present — they build a small synthetic calendar-dense table with planted insiders.

The pattern worth pointing at. Thirteen of the fifty-four tests do not test the guards' happy path — they construct the exact mistake the guard names and assert it is caught. A guard that has only ever been run on correct code is a decoration.

11 — The wart, found and deliberately not fixed

runner.save_checkpoint writes the wrong window_days for the seven-day control. It stamps config.WINDOW_DAYS on any window model rather than the length the view actually used, so a B@7 checkpoint claims 28 days on disk.

Two reasons it was left alone. The brief forbids editing runner.py — Stage 7 measures the experiment and does not get to modify the code that ran it. And the control is validation-only and its checkpoint is never reloaded, so the field is never read in anger.

evaluation/checkpoints.py 
load_variant_checkpoint(path, model_name=…, expected_window_days=7)
    → overrides the stored value with the caller's
    → then pushes a zero batch of that shape through the weights

So instead of trusting a field that is known to be wrong, the caller states what it expects and the weights are made to prove they accept it.

The line to use

“I found a bug in Stage 5's checkpoint writer while building Stage 7, and I did not fix it — because fixing it would have meant editing a file that both reported models were trained through, and ‘I changed the training code after training but it was only a metadata field' is not a sentence I want in this project. I worked around it where the value is read, and wrote it down in three places instead.”

13 — Questions to rehearse

Show me the line that stops you from tuning on the test set.

There isn't one line — there is a missing import. evaluation/scoring.py does not import sweep_threshold, which is the function that would search for a cut-off. What it has is describe_at_threshold, which reports what a cut-off handed to it actually does. Every call into the metrics code passes choose_threshold=False.

The same shape applies to the input scaling: the only function that builds evaluation rows takes the scaler as a required argument with no default, so there is no path that scales a split by statistics derived from that split. And both are then checked at runtime and printed, because an absence in the source is a good argument and a printed comparison is evidence.

You built a second data pipeline for the test split. How do you know it matches the training one?

I did not build a second one. Stage 5's prepare() deliberately refuses to construct the test split — that was how it guaranteed only one place could open it — so Stage 7 imports the same underlying functions: the clipper, the warm-up mask, the split lookup and the tensor builder. Nothing is reimplemented, so if the upstream table ever changes, this breaks in the same place training would.

The one thing I had to add is the calendar dates, because latency is a question about days and the training data structure does not keep them. Those are derived from the same mask and the same positions, and there is an assertion that the person column derived that way matches the one the shared function produced — because if those ever diverged, every latency number would be wrong and every accuracy number would still be right.

Why can't the loader just open any checkpoint I give it?

Because one of them is a model that lost, and the brief is unambiguous that it must not appear in any comparison. Leaving that to memory is how it ends up in a table at one in the morning. The loader accepts only filenames matching the pattern the reported experiment produced, so every tagged run — the tuning variant, the class-weighting ablation, the seven-day control — fails to open and says why.

Reaching a control deliberately takes a different function, and even that one refuses the tuning variant outright. The controls are not competing models and they never touch the test split.

Your latency thresholds look arbitrary. Why 1.5 and not 2?

They are a judgement, and the only thing that makes a judgement defensible here is when it was made. All three are module constants in latency.py, written before any measurement existed. If I had chosen them after seeing the bucket profile, “the recall is flat enough” would be unfalsifiable, because I would be picking what “enough” means last.

I would rather defend a number somebody disagrees with than a number nobody can check. And the report prints the underlying counts either way, so a reader who prefers a different cut-off can apply it themselves.

Fifty-four tests for code that only reads files and computes metrics. Isn't that excessive?

The metrics themselves are three lines calling scikit-learn and I did not test those. What is tested is everything around them, because Stage 7's failure mode is not a crash — it is a number that is quietly a bit too good.

Thirteen of the tests fabricate the exact mistake a guard names and assert it is caught: a scaler fitted on the wrong rows, a test person planted in the training split, a swapped threshold, two models scored on different data, predictions that rank the labels perfectly. A guard that has only ever been run on correct code has never been tested at all — that lesson came from Stage 6, where the test the brief recommended turned out to pass on the bug it was supposed to catch.

If you had to point at one line as the most dangerous in the stage, which is it?

The one that decides which scaler to apply. Everything else in Stage 7 either raises or is obviously wrong, but scaling the test rows by statistics fitted on the test rows produces a better score, a completely normal-looking output, and no error of any kind. It would survive into the report and into the defence.

That is why it is a required argument rather than a default, why the only function in the package that fits a scaler exists solely to feed a comparison, and why the guard prints the actual means and standard deviations instead of a tick.

The sentence to end on.

“Stage 7 is a few thousand lines that compute about a dozen numbers. Almost none of it is the computation. It is the part that makes three specific cheats impossible to commit by accident — a scaler that cannot be refitted, a threshold that cannot be re-chosen, and a losing variant that cannot be loaded — and then prints the values behind each of those claims so that you do not have to take my word for any of it.”
