InnerSight · Stage 5 code · defence preparation

Walk me through the code

The seven files in modeling/, what each part does and why it is written that way, the one abstraction that makes Stage 6 nearly free, the lines someone might point at, and why there are 28 tests and not 200.

The one-sentence answer to “what does your code do?”

“It takes the z-scored table, decides once which rows either model is allowed to be asked about, clips the extremes, rescales each feature using only the training people, and then runs a training loop that has no idea which model it is training — so the second model can be dropped in later without any of that changing. Then it trains the first model three times, on three different splits, and keeps the best epoch's weights together with the threshold and the scaler in one file.”

Same layout as extraction/, labeling/, baseline/ and splitting/: program, tests, README, run from the project folder. Every path, column name and constant comes from config.py.

terminalpython -m modeling.run_model_a                  # 3 seeds, full data,  ~2 minutes
python -m modeling.run_model_a --sample         # 30-person sample,     ~6 seconds

Fifth stage, fifth separate sample filename. Stage 1 was burned once when a 7-second test run overwrote the 1,000-person table. Here --sample appends .sample to every checkpoint, metrics file and figure, and --no-pos-weight adds _nopw, so the ablation cannot overwrite the real result either. The filenames are built by functions in config.py rather than formatted inline, because a forgotten suffix is exactly how this goes wrong.

1.1 — The one file the brief did not ask for

runner.py is an addition, and the reason is the whole point of the stage. Everything around the training loop — resolving the device, preparing the data, computing the class weight, running the three seeds, saving a checkpoint, aggregating mean ± spread, drawing the curves — is identical for both models. Leaving it inside run_model_a.py would force Stage 6 either to import from a file named after the other model, or to copy it.

And a copy is where two runs quietly stop being identical. Not immediately — later, when someone fixes something in one of them. The comparison would still produce a number and nobody would know.

Every function takes data in and gives data back. prepare accepts an optional dataframe and split dictionary purely so the tests can hand it twelve synthetic people instead of the real file — which is why the whole suite runs in five seconds and never touches r4.2.

2.1 — The abstraction that makes Stage 6 nearly free

train_model takes a model object and two views. A view is a tiny thing: it can tell you how many rows it has, and it can hand you a batch given a list of indices.

train.pyclass InputView(Protocol):
    """What the loop needs from an input source, and nothing more."""

    def __len__(self) -> int: ...
    def gather(self, index: torch.Tensor) -> torch.Tensor: ...
    def to(self, device: str | torch.device) -> InputView: ...

Model A passes a PointView — one row per day, shape (batch, 18). Model B will pass a WindowView, shape (batch, 18, 28). The training loop cannot tell the difference, and there is nothing anywhere in it that inspects the model's type or the shape of its input.

The line to use

“The training loop has no idea which model it is training. That is not tidiness, it is the experimental control. If Stage 6 ever needed to edit that file, the two models would not have been trained identically and I would have to say so in the results.”

Why the windows are cut on demand rather than built up front

data.pydef gather(self, index: torch.Tensor) -> torch.Tensor:
    selected = self.positions.index_select(0, index.to(self.positions.device))
    offsets = torch.arange(-(self.days - 1), 1, dtype=torch.int64, ...)
    rows = (selected.unsqueeze(1) + offsets.unsqueeze(0)).reshape(-1)
    gathered = self.features.index_select(0, rows.to(device))
    return gathered.reshape(-1, self.days, self.features.shape[1]).permute(...)

Materialising every 28-day window would store each row up to 28 times over: 437,000 × 18 × 28 floats, about 880 MB. Slicing per batch costs nothing measurable, and — more importantly — it means Model B reads the same array Model A does, with the same scaler already applied, rather than a second tensor built by a second code path.

3 — The order of operations, and why swapping any two is silent

This sequence is the stage. Everything else is arithmetic.

data.py — prepare()load dataset.parquet
  → clip to ±10
  → select target rows (day_index >= 27 within user)
  → split rows by user using splits.json[seed]
  → fit mean/std on TRAIN target rows only
  → apply to every row (targets and history alike)
  → build tensors
SwapWhat happensError?
standardise before clippingrescaled by a deviation the 716-outlier inflated; every ordinary day squashed toward zeronone
fit the scaler before splittingvalidation statistics leak into training; results improve slightly and inexplicablynone
mask after fittingscaler describes 27,000 warm-up rows no model ever seesnone
skip the mask for Model B onlyModel B gains ~6% AUPRC for freenone

Four ways to get a wrong answer with no symptom. That is why the order lives inside one function rather than being spread across a script, and why three of the four have a test pinning them.

4 — The lines someone might point at

The row mask — one comparison, and the reason it exists

data.pydef target_mask(frame, window_days=WINDOW_DAYS):
    """True for rows that may be *predicted*: day_index >= window_days - 1."""
    return day_index(frame) >= (window_days - 1)

Trivial to read, and it is the single most consequential line in the stage. It is applied identically to Model A and Model B, and to training and evaluation alike. §3 of the companion document explains what breaks without it.

…and the check underneath it that nobody asked for

data.pygaps = frame.groupby(USER_COLUMN, sort=False)[DAY_COLUMN].diff()
irregular = gaps.notna() & (gaps != pd.Timedelta(days=1))
if bool(irregular.any()):
    raise DataError(
        f"{int(irregular.sum())} row(s) break calendar-day density ... "
        f"Model B's windows assume one row per calendar day per user.")

The day index is computed by counting rows within a person, which is only the same thing as counting days if the calendar is dense. Stage 2 guarantees it is. If that ever stopped being true, Model B would take “the 27 rows before this one” and call it a 28-day window when it might span forty days — and the model would train, converge and report a number.

So the code refuses to proceed instead of assuming. It costs one groupby and it is checked on every run.

The clip, and where the count comes from

data.pyvalues = frame[list(FEATURE_NAMES)].to_numpy(dtype=np.float32, copy=True)
touched = int((np.abs(values) > limit).any(axis=1).sum())
np.clip(values, -limit, limit, out=values)

The touched count is not decoration — it is printed on every run (2,138 rows, 0.46%) and it is the diagnostic that says whether ±10 is a sane bound. If that number were 15% rather than 0.5%, the clip would be destroying signal rather than trimming a tail, and the report would show it.

A feature that never varies is left alone, not divided by a floor

data.pymean = features.mean(axis=0, dtype=np.float64)
std  = features.std(axis=0, dtype=np.float64)
std  = np.where(std < STD_FLOOR, 1.0, std)

A np.maximum(std, 1e-6) here would be the obvious choice and would be wrong. large_attachment_count is identically zero across all of r4.2, so its deviation is exactly 0; dividing its floating-point noise by 10−6 turns a dead feature into inputs of order 106. Dividing by 1 leaves it at zero forever, which is what a feature with no data should contribute.

There is a test that constructs exactly this case and asserts the column comes out all zeros and all finite.

The class weight — computed, never written down

train.pyif pos_weight is None and config.use_pos_weight:
    pos_weight = compute_pos_weight(y_train.cpu())
...
criterion = nn.BCEWithLogitsLoss(pos_weight=weight_tensor)

The caller passes it in from PreparedData.pos_weight(), which is defined on the training split and raises if there are no positives. Three seeds produced 229.7, 225.3 and 232.1 — three different training splits, three different weights.

Hardcoding a value, or computing it from the whole table, would put the test set's class balance into the loss function. The test asserts it equals n_neg / n_pos of the training split, that it changes when the split changes, and that it is not the whole table's ratio.

Stopping on the right quantity, and keeping the right epoch

train.pyif record.val_auprc > best_auprc:
    best_auprc = record.val_auprc
    best_epoch = epoch
    best_state = copy.deepcopy({k: v.detach().cpu().clone()
                                for k, v in model.state_dict().items()})
    best_probs = val_probs
    epochs_without_improvement = 0
else:
    epochs_without_improvement += 1
    if epochs_without_improvement >= config.patience:
        break

Two decisions in one block. Early stopping watches validation AUPRC, not validation loss — loss is dominated by the 99.6% of rows nobody cares about, and can improve for several epochs while the ranking gets worse. And the checkpoint kept is the best epoch's weights, not the last, with best_probs saved alongside so the reported metrics describe the file that was actually written.

Seed 42 makes the point: best at epoch 16, ran to 23. Without this, the saved model would be the epoch-23 one and the reported AUPRC would be the epoch-16 one.

The threshold is searched, never assumed

metrics.pyquantiles  = np.quantile(probs, np.linspace(0.0, 1.0, points))
candidates = np.unique(np.concatenate([quantiles, probs[labels == 1]]))

Candidates are quantiles of the observed scores, plus every score a real positive received. A linear grid over [0, 1] would be the obvious choice and would waste almost all of its budget: a weighted model's outputs cluster, and the three chosen thresholds came out at 0.958, 0.974 and 0.9939 — a 512-point linear grid has five candidates above 0.99.

The chosen value is then written inside the checkpoint. A model without its threshold is not a working system, and recomputing it on test data at report time would be leakage of the easiest possible kind to commit by accident.

Seeding happens before the model exists

runner.py# Seed BEFORE the model exists. `train_model` seeds too, but by then the
# weights have already been drawn from whatever state the process was in.
seed_everything(seed)
model = model_factory()

This one was found by a test. Seeding only inside train_model looks correct — but the model is constructed by the caller, one line earlier, so its initial weights come from whatever the process happened to be doing. Two runs of “seed 42” would then differ, and “mean ± standard deviation across three seeds” would be measuring the process as much as the split.

The determinism test mirrors the real call order precisely, so it would fail again if anyone reordered those two lines.

The guard that would reject a good-looking result

run_model_a.py# A non-zero exit code on a suspicious run, so a scripted pipeline stops
# instead of writing a leaked number into a results table.
if summary["leakage_suspected_any_seed"]:
    return 3

Validation AUPRC above 0.95 is treated as a bug. At 0.4% positives with window labels, near-perfect ranking means leakage — most likely a split applied by row instead of by person, or a scaler fitted on everything. The program refuses to write a result rather than celebrate one.

5.1 — The collapse floor, and why it is not a constant

metrics.py@property
def collapse_floor(self) -> int:
    return min(MIN_DISTINCT_PREDICTIONS, max(2, self.n_rows // 10))
This started as a plain constant of 1,000 and a test caught it. No model can produce a thousand distinct scores for 372 rows, so on any small run the guard fired every single time. A guard that cries wolf is a guard that has been turned off by the time it matters — so the floor scales with the number of rows, and on the real validation split of 85,191 rows it resolves back to 1,000.

The rule for choosing them is inherited from Stages 1 to 4: test the things that go wrong silently. No crash, no missing value — just a number that is subtly wrong and survives into the results table. None of them read the real dataset; each builds its own synthetic people, so the suite runs in five seconds and stays honest.

Five failed on the first run. One was a real bug, one was a real design flaw, three were bad tests.
The real bug: same_seed_twice_gives_identical_weights failed because the model was constructed before anything was seeded, so its starting weights depended on whatever the process had already done. The three bad tests were my fault — a comparison split that overlapped itself, and two fixtures constructed so that the thing being tested could not have differed.
If asked “only twenty-eight tests?”

“Twenty-eight chosen by a rule rather than to hit a coverage number: every one targets a failure that gives no error message. The one I would point at builds a validation split fifty times larger and shifted by a thousand, and asserts the feature scaling does not move by a millionth — because if a single validation row had touched that fit, it could not possibly still be near zero. And five of the twenty-eight failed the first time I ran them. One of those was reproducibility being an illusion, which is not something I would have found by reading the code.”

The class weight is the interesting one. 8 — The device, and why it is in the code at all

config.pydef resolve_device(preference: str = DEVICE_PREFERENCE) -> str:
    """``"auto"`` prefers MPS and falls back to CPU; an explicit ``"mps"`` on a
    machine without Metal is a mistake worth an exception rather than a silent
    downgrade, because the whole point of asking for MPS is to test it."""
RunCPUApple GPU (MPS)
sample, 3 seeds3.18 s5.64 s
full data0.77 s/epoch on MPS · whole 3-seed run ≈ 82 s
The CPU won, and that is the honest thing to report. At 641 parameters a batch is a few hundred thousand arithmetic operations — microseconds of work — while every GPU operation costs tens of microseconds simply to dispatch. GPUs win on large matrices, not on many tiny ones.

MPS is used anyway, and the reason is portability rather than speed: a stray .numpy(), an accidental 64-bit float, or an operation with no Metal implementation would all pass silently on CPU and fail the moment the code met a real accelerator. Running on Metal is what proves the pipeline is device-agnostic. The benchmark then reports honestly what that cost.

Both models must use the same backend — floating-point results differ subtly between them, and a reader can fairly ask whether a two-model difference is architecture or arithmetic. The resolved device is printed in the log and stored inside every checkpoint.

9 — What is in a checkpoint, and why all of it

runner.py{

  "standardiser": {mean, std, feature_names},

Weights, threshold and scaler travel together, deliberately. A model whose decision threshold lives in a notebook and whose input scaling lives in a dataframe is not a system — it is a matrix. Stage 7 must apply exactly the transform these weights were trained under and exactly the threshold validation chose, and the only way to guarantee that is for the file to carry them. feature_names is stored too, so loading a checkpoint after someone reorders config.FEATURE_NAMES raises instead of silently scoring the wrong feature.

10 — Questions to rehearse

Walk me through what happens when I run this.

It resolves the device once and prints it. Then, for each of three seeds: read the z-scored table, clip everything to ±10, mark which rows may be predicted, split the rows by person using Stage 4's file, fit a mean and deviation per feature on the training target rows only, apply that to every row, build tensors.

Then it prints the guard block — row counts, positives lost to the mask, the class weight, the random baseline — builds the model, and trains. Each epoch reports five numbers plus a distinct-value count. It stops when validation AUPRC has not improved for seven epochs and keeps the best epoch's weights, sweeps a threshold on validation, and saves weights, threshold and scaler in one file. At the end, mean ± spread across the three seeds, a metrics file and a figure. About two minutes.

What is the most dangerous line in this code?

The row mask, because it is one comparison and it decides whether the entire final comparison means anything. If Model B skipped those rows and Model A did not, Model B would gain about 6% of AUPRC purely because the rows it cannot see are the easiest negatives in the table. Nothing would flag it — you would just conclude that temporal context helps more than it does.

Runner-up is the class weight. Get that wrong and the model learns to say “no” to everyone, which is 99.6% accurate, worthless, and produces a completely healthy-looking loss curve. That is why the per-epoch log has a distinct-value count in it.

Why does the training loop take a “view” instead of a tensor?

Two reasons. The experimental one: it means the loop cannot know which model it is training, so Stage 6 passes a convolutional network and a 28-day window through the identical function. If Stage 6 had to edit the loop, the two models would not have been trained identically.

The practical one: Model B's windows overlap heavily — every row appears in up to 28 of them. Materialising them all would be about 880 MB of mostly duplicated data. The view cuts each batch on demand from the same array Model A reads, with the same scaler already applied, so there is exactly one code path from the parquet file to both models' inputs.

You stop on AUPRC rather than loss. Why?

Because validation loss is dominated by the 99.6% of rows I do not care about, and it can improve for several epochs while the ranking of the interesting rows gets worse. AUPRC is what I actually want maximised, so I select on it directly.

It also changes which weights get saved. Seed 42's best epoch was 16 and it ran to 23 — keeping the last epoch would have saved a model that was measurably worse than the one whose number I report.

Why not use 0.5 as the threshold, like everyone does?

Because the loss is weighted by a factor of about 230, so the outputs are deliberately not calibrated around 0.5 — the model is trained to over-predict the rare class. The three thresholds the sweep chose were 0.958, 0.974 and 0.994. A default of 0.5 would flag an enormous fraction of the data.

The sweep uses quantiles of the observed scores rather than a linear grid, because a weighted model's outputs cluster and a linear grid over [0,1] puts almost all its candidates in empty space — with 512 linear points, only five of them are above 0.99. And the chosen value goes inside the checkpoint, because recomputing it on test data in Stage 7 would be leakage.

Which test would you show me if I only had time for one?

The scaler leakage test. It builds a validation split whose feature values are fifty times larger and shifted by a thousand, runs the real pipeline, and asserts the fitted mean and deviation are unchanged to within a millionth — and adds a sanity floor that the mean must still be near zero, which could not possibly be true if a single validation row had touched the fit.

I would show that one because leakage is the failure that makes results look better, which means nobody goes looking for it.

How much of this does Stage 6 change?

One class in models.py and one entry-point file that passes a 28-day window view instead of a single-day one. The data pipeline, the training loop and the runner are untouched, and the window path already exists and is tested — there is a test asserting the last day of each window is the target row itself.

The check I will run is the guard block: if Model B's preparation prints anything other than 464,687 rows, 27,000 masked, zero positives lost and 2,138 clipped, then the two models are not on the same data and the comparison is void.

The sentence to end on.

“Seven files, twenty-eight tests, two minutes to run. Most of it is not about Model A at all — it is about making sure that the model arriving in Stage 6 differs from this one in exactly one way. The hard parts are the four or five places where being wrong produces no error: a row mask applied to one model and not the other, a clip applied after the rescaling instead of before, a scaler that saw the validation set, a class weight taken from the whole table, and a seed set one line too late. That last one I did not spot by reading the code — a test did.”
