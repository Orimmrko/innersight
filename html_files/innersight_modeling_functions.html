Every function in modeling/

141 functions and methods across ten files, in the order they appear. A one-line summary for scanning, then a full explanation of what the body actually does and why.

modeling/ is where the project stops describing behaviour and starts predicting it. It holds two neural networks — one that sees a single day, one that sees the twenty-eight days ending on that day — and every piece of machinery they share: getting rows into tensors, the training loop, the scoring, and the orchestration across three random seeds. The entire package is built around one constraint: the two models must differ in exactly one respect, temporal context, so almost everything here is deliberately blind to which model it is serving.

How to read this. Each chapter opens with a scan table — every function in the file, one line each — so you can find things fast. Below it, the same functions in file order, grouped by zone, each with its signature, its one-liner, and two to five paragraphs on what the code actually does and what breaks if it does something else.

The ★. Most of these functions are plumbing. A small number are where the real thinking is, and those are starred and boxed in colour — 26 across 141. If you only ever understand those, you can defend the package.

zone 2 · the scaling

A tiny frozen record holding one mean and one spread per feature, plus the four operations that create it, use it, and move it in and out of a checkpoint file.

Standardiser.__post_init__

def __post_init__(self) -> None:

Refuses to finish building the object unless both statistics arrays have exactly one entry per feature, contain no missing or infinite values, and have every spread strictly above zero.

Dataclasses call this automatically the instant the object is constructed, so there is no way to obtain a Standardiser that has not been checked. It runs three tests over both arrays: each must be shaped (18,) — one number per feature, not one per row — neither may contain a missing or infinite value, and no spread may be zero or negative. That last check is the one doing real work. apply divides by the spread with no guard of its own, so a single zero slipping through here would produce infinities in every batch, and a network fed infinities produces a loss of nan that a reader may well interpret as a bad learning rate.

★ Standardiser.fit

@classmethod def fit(cls, features: np.ndarray) -> Standardiser:

Measures each feature's average and spread across the rows handed in. A feature that never changes gets a divisor of 1 rather than its true 0, so it stays flat at zero instead of having its rounding dust magnified into the millions.

Given a block of rows it first insists the block is two-dimensional, eighteen columns wide, and not empty — three failures that would otherwise show up much later as a shape error inside a linear layer. Then it takes the average and the spread down the columns in double precision. The line that matters is the next one: std = np.where(std < STD_FLOOR, 1.0, std). Read it carefully — a tiny spread is replaced by 1.0, not by the floor. The obvious alternative, np.maximum(std, 1e-6), would take a feature that never varies, divide its floating-point dust by a millionth, and hand the network z-scores in the millions. Dividing by 1 leaves such a column at exactly zero forever, which is what a dead feature ought to contribute. This is not hypothetical: large_attachment_count in the r4.2 dataset is identically zero in every row.

Standardiser.apply

def apply(self, features: np.ndarray) -> np.ndarray:

Subtracts the average and divides by the spread in double precision, then narrows to single — Apple's GPU backend rejects doubles, so the cast happens here rather than as a crash inside a graphics kernel.

One expression: ((features.astype(float64) - mean) / std).astype(float32). Both casts are deliberate and in opposite directions. Going up to double precision first means subtracting a large average from a large value does not quietly lose digits. Coming back down to single precision at the end is forced by Apple's Metal backend, which refuses double-precision tensors outright — so the narrowing is written here, in plain numpy, rather than being discovered as an opaque failure the first time a batch reaches the GPU. Note that history rows go through this too, not just the rows being judged: the scaling is measured on training targets but applied to every row in the table.

Standardiser.to_dict

def to_dict(self) -> dict[str, list[float]]:

Packs the two statistics arrays and the feature ordering they were measured under into plain lists, so all three can travel inside the saved model file.

Produces three keys — mean, std and feature_names — as ordinary Python lists so the whole thing can be written into a checkpoint by torch.save. The third key is the interesting one, because nothing in apply ever looks at it. It is recorded purely so that a checkpoint carries a statement of which column each number belongs to, which is what makes the check in from_dict possible months later.

Standardiser.from_dict

@classmethod def from_dict(cls, payload: dict[str, Sequence[float]]) -> Standardiser:

Rebuilds those statistics from a saved file, and refuses if the project's feature ordering has changed since — the numbers would otherwise be applied to the wrong columns without a word.

Reads the recorded feature ordering (falling back to the current one if an older checkpoint lacks it) and compares it to config.FEATURE_NAMES. A mismatch raises immediately, with an error saying the configuration has changed since the file was written. This is guarding against a specific, entirely silent disaster: reorder that tuple and every saved model keeps loading fine, keeps producing probabilities, and applies each feature's scaling to a different feature. Once the arrays are rebuilt, __post_init__ runs again, so a truncated or corrupted checkpoint fails here rather than at the first prediction. Its only caller in the project is evaluation/checkpoints.py.

zone 3 · the two ways of looking at rows

Two small wrappers with the same three-method surface. The training loop can only ask them how many examples there are, hand me batch number N, and move to this device — which is precisely why the loop cannot tell which model it is training.

PointView.__len__

def __len__(self) -> int:

How many days the one-day model will be asked to judge.

Returns the first dimension of the stored tensor. Because this view holds one row per judged day and nothing else, that count is the number of examples the training loop will iterate over — no positions, no history, no arithmetic.

PointView.gather

def gather(self, index: torch.Tensor) -> torch.Tensor:

Pulls out one batch of days by row number, moving the index onto whichever device the rows already live on.

A single index_select along the row axis. The one non-obvious detail is index.to(self.tensor.device): the caller builds its shuffled batch order on the CPU, but the rows may already be on the GPU, so the index is moved to meet them rather than the other way round. That keeps the training loop free of any device bookkeeping.

PointView.to

def to(self, device: str | torch.device) -> PointView:

Copies the whole block of rows to the CPU or the GPU and returns a fresh wrapper around the copy.

Moves the tensor and wraps the result in a new PointView. It has to return a new object rather than mutate in place because the dataclass is frozen — which is itself deliberate, since a view that could change device underneath a running loop would be a very hard bug to see.

PointView.input_shape

@property def input_shape(self) -> tuple[int, ...]:

Reports the shape of a single example, meant for logging. Nothing in the project calls it.

Everything after the row axis, so (18,). It reads like a logging convenience, and it may well have been intended as one, but no call site exists anywhere in the project — the same is true of WindowView's version. Worth knowing only so you are not surprised to find it unused.

WindowView.__len__

def __len__(self) -> int:

How many days the twenty-eight-day model will be asked to judge — one per stored position, not one per stored row.

Counts the stored positions, not the stored rows. That distinction is the whole design of this class: it holds one large array containing every row of every user in the split — history included — plus a much shorter list of which rows are actually judged. The length the loop sees is the short list.

★ WindowView.gather

def gather(self, index: torch.Tensor) -> torch.Tensor:

For each requested day, lifts that day and the twenty-seven before it out of the shared row block, then turns it inside out so features become channels and days the sequence. Cut per batch: storing every window would cost roughly 880 MB.

Five steps, no Python loop. It selects the requested target positions; builds offsets = arange(-27, 1); broadcast-adds the two to get a (batch × 28) grid of absolute row numbers; flattens that grid into one index_select against the shared feature array; then reshapes to (batch, 28, 18) and permutes to (batch, 18, 28) so features become the channels a Conv1d expects and days become the sequence. The final .contiguous() is not cosmetic — a permuted tensor has non-standard memory strides, and the convolution wants them normal.

Nothing here checks that the twenty-eight rows belong to the same person. That safety comes entirely from an invariant established elsewhere: rows are sorted so each user's days are contiguous, and a judged position is never within the first twenty-seven rows of its user. window_view verifies that once, up front; this method then trusts it, which is why it can be a handful of tensor operations per batch instead of a bounds check per window.

WindowView.to

def to(self, device: str | torch.device) -> WindowView:

Moves the row block and the list of positions to the same device together, so a batch is never assembled from tensors sitting in two places.

Moves both the feature array and the position list, together, into a new frozen view. Moving only one would produce a device-mismatch error rather than a wrong answer — but keeping them paired is what lets train.py get away with a single view.to(device) call and no knowledge of what is inside.

WindowView.input_shape

@property def input_shape(self) -> tuple[int, ...]:

Reports features-by-days as the expected shape of one example. Also never called.

Returns (18, 28) — channels first, matching what the convolution receives. Like the PointView version, it is never called.

zone 4 · one split's worth of rows

A frozen record holding every row of one group of users, plus a list of which of those rows are actually judged. Keeping the two apart is what lets the twenty-eight-day model read history it is never scored on.

SplitData.n_targets

@property def n_targets(self) -> int:

How many days in this group are actually judged, as opposed to merely held in memory as history.

The number of stored positions. Read this as “how many days will actually be scored”, which on the real validation split is far fewer than the number of rows held in memory, because every user contributes twenty-seven warm-up rows that exist only as history.

SplitData.n_positives

@property def n_positives(self) -> int:

How many of those judged days fall inside a real attack window.

Sums the label column and casts to int. Labels are stored as floats (0.0 and 1.0) because that is what the loss function wants, so the sum is a float that has to be narrowed here rather than at every call site.

SplitData.n_negatives

@property def n_negatives(self) -> int:

The judged days that are ordinary — the other 99.6%.

Judged days minus attack days. It exists as a named property purely so pos_weight reads as n_negatives / n_positives — the definition of the quantity — rather than as an expression the reader has to verify.

SplitData.positive_rate

@property def positive_rate(self) -> float:

The share of judged days that are attacks — which is exactly the score a coin-flip ranker earns on the headline metric, so no reported figure means anything without it beside it.

Attack days divided by judged days, with a guard returning 0.0 for an empty split. This is the single most important number to print alongside any headline result: because average precision is bounded below by the base rate, a coin-flip ranker scores exactly this. On the real validation split it is around 0.0044, so “AUPRC 0.15” means roughly thirty-four times better than guessing — and “AUPRC 0.15” on its own means nothing at all.

SplitData.point_features

def point_features(self) -> torch.Tensor:

Lifts just the judged days out of the stored block, one row each: the one-day model's entire input.

One index_select pulling the judged rows out of the stored block, producing an (n_targets, 18) matrix. This is the entirety of Model A's input: every judged day, with no memory of the day before it. The warm-up rows are simply not selected — they stay in the array where Model B can still read them.

SplitData.window_features

def window_features(self, days: int = WINDOW_DAYS) -> torch.Tensor:

Builds every window at once as one large tensor, refusing if any of them would reach before the start of the array. Dead code — its docstring says Stage 6 calls it, and Stage 6 does not; nothing in the project does.

The eager equivalent of WindowView.gather, building every window for the whole split as one tensor. It validates that the requested length is between 1 and 28, constructs the same offset grid, checks that no window reaches before row 0, and reshapes and permutes identically.

It is dead code. Its docstring states that Stage 6 calls it and Stage 5 does not; in fact Stage 6 uses window_view, and nothing anywhere in the project calls this. Materialising all windows at once was the design that WindowView replaced, for the memory reason described there — this is the version that did not survive, left behind with its comment still claiming a caller.

SplitData.point_view

def point_view(self) -> PointView:

Wraps those single rows in the small object the training loop knows how to request batches from.

A one-line wrapper: take the judged rows and hand them to PointView. The indirection earns its place because runner.run_experiment takes a “view selector” as an argument, and run_model_a.py passes exactly this method while run_model_b.py passes window_view. Those two references are the entire difference between the two experiments.

SplitData.window_view

def window_view(self, days: int = WINDOW_DAYS) -> WindowView:

Hands back the lazy slicer — but first refuses if any judged day sits too close to the start of its own user's record for a full window to exist behind it.

Before constructing anything it checks target_positions.min() < days - 1 and raises if so. That single comparison is the only place the row mask and the window length are ever checked against each other, and it is checked once per split rather than once per batch — which is why WindowView.gather can be pure tensor arithmetic.

If it were missing, a judged day sitting inside the warm-up would make the gather index negative, and PyTorch's index_select treats negative indices by wrapping to the end of the array. The window would fill with rows belonging to a completely different person, at the wrong end of the calendar, and training would proceed without complaint.

SplitData.describe

def describe(self) -> str:

Writes the one-line census printed for each group before training: users, rows held, rows judged, attack days and their share.

Builds the one-line census printed for each split before training starts: number of users, rows held in memory, rows actually judged, attack days and their share to four decimal places. The reason rows-held and rows-judged are printed separately is that seeing them equal would immediately reveal the row mask had not been applied.

zone 5 · what one seed's preparation produced

A record of the finished train-and-validation pair, plus the counts needed to prove the preparation did what it claims, and the one derived number the loss function depends on.

★ PreparedData.pos_weight

def pos_weight(self) -> float:

Ordinary days divided by attack days, in the training users only — the multiplier that stops the loss from being won by answering “benign” to everything. Refuses outright if training contains no attacks.

Raises if the training split contains no attack days — the ratio would be undefined and training on an unweighted loss at this imbalance is pointless — and otherwise returns ordinary days divided by attack days, computed from the training split alone.

Computing it from the whole table instead would be leakage: the class balance of the held-out users is information about the held-out users, and feeding it into the loss function is exactly the kind of contamination that nothing will ever flag. It also has a practical use as a tripwire. On r4.2 this prints 229.7, 225.3 and 232.1 for the three seeds; the whole-table figure is about 244. If a run logs ~244, the row mask was not applied before the weight was computed, and the two models are not being trained on the same rows.

load_dataset

def load_dataset(path: Path) -> pd.DataFrame:

Reads the table, checks every expected column is present, and sorts it so each person's days sit together in date order. Every position-based operation below silently assumes that ordering.

Four things in order. It checks the file exists and, if not, raises an error that names the exact command to run to produce it. It reads the parquet file. It checks every expected column is present — user, day, scenario, label and all eighteen features — and reports all missing columns at once rather than failing on the first one. Then it sorts by user and day with a stable sort and resets the index.

That final step is load-bearing and easy to skim past. Every position-based operation downstream — the day numbering, the target mask, every one of Model B's windows — assumes that one person's rows sit together in the array in date order. Stage 3 happens to write the file that way; this function refuses to depend on that happening to remain true.

★ clip_z_scores

def clip_z_scores(frame: pd.DataFrame, limit: float = Z_CLIP) -> tuple[pd.DataFrame, int]:

Pins every value into ±10 and reports how many rows had to be touched. A surviving value of 716 would inflate its feature's spread so far that every ordinary day gets squashed toward zero.

Copies the eighteen feature columns into a float32 array, counts how many rows have any value beyond the bound (rows rather than values, so the reported figure answers “how much of the table was affected”), clips in place, and writes the result back into a copy of the frame. Returns both the frame and the count.

The bound is ±10 and it is decided in advance, identically for train, validation and test — a bound chosen from the data would itself be a form of fitting. The justification is a single sentence: beyond ten standard deviations from a person's own baseline, the exact value carries no further information; it is equally off the charts. It matters because the raw z-scores from Stage 3 reach 716 against a mean absolute value of 0.42, and a value that extreme inflates its feature's spread so badly that standardising afterwards squashes every ordinary day toward zero. On the real table this touches 0.46% of rows.

day_index

def day_index(frame: pd.DataFrame) -> np.ndarray:

Numbers each person's days from zero, and refuses if anyone's dates skip a day — a gap would quietly make “twenty-eight rows” span more than twenty-eight days.

Two grouped operations. cumcount() numbers each person's rows from zero, giving the position of every day within that person's own record. diff() on the date column, again grouped by person, gives the gap to the previous row; any gap that is present and not exactly one day is an offence, and the error names up to five of the users responsible.

The density check is the reason this is more than a helper. Model B builds a window by taking twenty-seven array rows before a target, not twenty-seven calendar days. If a person were missing a Tuesday, a “28-day window” would quietly span thirty days, or forty, and every result would still look plausible. Stage 2's calendar fill guarantees density upstream; this refuses to proceed if that ever stops being true. Since target_mask calls it, the check runs on every single run rather than only in tests.

★ target_mask

def target_mask(frame: pd.DataFrame, window_days: int = WINDOW_DAYS) -> np.ndarray:

Marks which days may be judged: a person's twenty-eighth day onward, since that is the first day with a full history behind it. Applied to both models so neither is scored on rows the other never saw.

The body is one comparison: a row may be judged if its position within its own user's record is at least twenty-seven. Three lines of code, and the most consequential decision in the package.

Model B cannot score a person's first twenty-seven days, because no full history window ends there. If Model A scored them and Model B did not, the two models would be measured on different row sets and the comparison would be void. It is worse than untidy: those early days are the warm-up period, where every feature is exactly zero because the person has no baseline yet — they are the easiest negatives in the entire table. Removing them raises the attack rate from 0.411% to about 0.436%, and average precision rises with the base rate mechanically, so Model B would collect roughly 6% of its headline number for free and entirely unearned. The mask costs about 27,000 rows and, because the earliest attack window in r4.2 opens around day 160 of every record, zero attack days — prepare measures that rather than assuming it.

load_splits

def load_splits(path: Path, seed: int) -> dict[str, tuple[str, ...]]:

Reads one seed's three user lists out of the file Stage 4 wrote, accepting either the nested or the flat layout, and refuses if that seed is missing.

Reads the JSON Stage 4 wrote and pulls out one seed's three user lists. payload.get("splits", payload) accepts either the nested layout Stage 4 currently writes or a flattened one, so a future change to that file's shape would not break here silently. A missing seed raises an error that lists the seeds the file does contain. The lists come back as tuples rather than lists, so a caller cannot accidentally mutate the split.

The important thing this function does not do is generate a split. Doing so here would produce a perfectly reasonable-looking run in which Model A and Model B were trained on different people.

_build_split

def _build_split(name, frame, is_target, users, standardiser) -> SplitData:

Takes the rows belonging to one group of people, rescales them with the already-measured statistics, and packages them with the positions, labels and attack types of the judged days.

Given one group of users, it builds a boolean mask over the whole frame, raises if the group matched nothing, applies the already-measured scaling, and checks the result contains no missing or infinite values.

Then the line that has to be exactly right: positions = np.flatnonzero(is_target[belongs]). The target mask was computed over the full table, but the feature array being built here holds only this group's rows. Indexing the mask by the same boolean selector first, and then finding the true positions, produces positions relative to the sliced array rather than the original. Compute them in the other order and every window would be offset by however many rows the earlier users occupy — a mistake that raises nothing and trains fine.

★ prepare

def prepare(seed, *, sample=False, frame=None, splits=None, window_days=WINDOW_DAYS) -> PreparedData:

Performs the whole sequence in the one order that is correct: clip, mark judgeable days, split by person, measure the scaling on training rows only, apply it everywhere. It never builds the test group at all.

The whole pipeline for one seed, in the one order that is correct:

  1. load the table (or accept an injected one, which the tests use — and sort it the same way load_dataset would, so an injected frame cannot behave differently);
  2. clip to ±10;
  3. mark which rows may be judged;
  4. split the users by the Stage 4 assignment;
  5. measure the scaling on training rows that are also judgeable;
  6. apply that scaling to every row, history included;
  7. build tensors.
Along the way it warns — rather than raises — if the mask drops any attack days, because on a trimmed or synthetic frame that is expected and on the real table it is a signal that something upstream moved. It checks both training splits are present, and it checks train and validation share no users before doing any of the expensive work.

Swapping any two of those steps produces a number rather than an exception. Clipping after standardising rescales by a spread the outlier already inflated. Measuring the scaling before the split leaks validation statistics into training. Masking after measuring fits the scaling on twenty-seven thousand warm-up zeros that no model will ever be scored on. And the test split is never built at all — Stage 5 reads the test user list out of the file only in order to ignore it.

log_preparation

def log_preparation(data: PreparedData) -> None:

Prints the pre-flight census and turns three quiet disasters into loud errors: a group with only one class in it, a person on both sides of the split, or no attacks to weight against.

The pre-flight block, printed before a single gradient step. It logs the row count, how many were masked out as warm-up and what fraction that is, how many attack days the mask cost, how many rows were clipped, and then one census line per split.

Interleaved with the logging are two hard failures: a split containing only one class, and any user appearing on both sides. Both are placed after the lines that describe the splits, so when the run stops the log already shows how far it got and what the numbers looked like. ★ sweep_threshold

def sweep_threshold(labels, probs, points=THRESHOLD_SWEEP_POINTS) -> ThresholdChoice:

Searches the observed scores for the cutoff with the best hit-versus-false-alarm balance. Candidates come from the distribution of the scores, not an even grid, because weighted training leaves the outputs bunched together.

Builds a candidate set, then loops. The candidates are 512 quantiles of the observed predictions unioned with every prediction attached to an attack day, deduplicated. For each candidate it counts what would be flagged, skips the ones that flag nothing, computes precision and recall, and keeps whichever gives the best balance between them.

Two design choices are worth stating. Quantiles rather than an even grid over [0, 1], because a model trained with a heavy class weight produces outputs that cluster tightly — an even grid would spend most of its budget on empty stretches of the axis. And the union with the attack days' own scores, because with only a few hundred positives the optimum often sits exactly at one of their values, and a pure quantile grid can step straight over it.

The docstring's argument is that 0.5 is the one value certainly wrong: with a class weight in the loss the outputs are deliberately uncalibrated, so the model's “yes” region can sit anywhere. Note, though, that the degenerate branch — a split with no attack days at all — does return exactly 0.5, with a zero balance score. Harmless, since nothing downstream trusts a threshold from a split with nothing to detect, but it is the one place the code does the thing the comment forbids.

zone 2 · Model B, the experiment

Twenty-eight days in, one score out. Identical to Model A in every respect except that each input carries the twenty-seven days of history before the day being judged.

Builds two filter layers that slide along the time axis, the second one skipping every other day so seven days come within reach at no extra parameter cost. Refuses an even filter width, or a reach longer than the window itself.

Validates first, then builds. An even filter width is rejected because the “same” padding arithmetic below assumes an odd one — with an even width the padding cannot be symmetric and the time axis would drift. Then it computes the reach: 1 + (k-1) + dilation*(k-1), which for a width of 3 and a skip of 2 comes to seven days, and rejects any configuration whose reach exceeds the window, because the second layer would then be looking at nothing but padding — a silent no-op rather than an error.

The stack itself is two convolutions of thirty-two channels each, a rectifier, an optional dropout (again inert, since the configured rate is zero, so an identity layer is installed instead), and a linear head down to one output. The padding on each layer is set so the time axis stays twenty-eight long throughout, which means the averaging step later covers exactly the window rather than a shrinking remnant of it.

The skip on the second layer is the interesting choice. Two stacked width-3 layers see five days; making the second one skip every other day widens that to seven at identical parameter count — the filter has the same number of weights, they are just spaced further apart. Since attack type 2 is a 45-to-59 day drift, reach is the quantity that matters, and buying it with extra layers would cost parameters this model cannot afford. Total: 4,897.

★ train_model

def train_model(model, train_view, train_labels, val_view, val_labels, config, *, val_scenarios=None, pos_weight=None) -> TrainingResult:

Weighted loss, Adam, a full validation pass every epoch, and a stop after seven epochs without improvement. It keeps the best-ranking epoch rather than the last, because validation loss is dominated by the rows nobody cares about.

The loop, and the only function in the package that performs a gradient step. Setup: seed, move the model and both views to the device, count parameters, derive the class weight if one was not supplied, build BCEWithLogitsLoss with that weight and an Adam optimiser, and check that the number of training examples matches the number of training labels.

It then creates one CPU random generator seeded from the run seed, and uses it for every shuffle. That is a deliberate substitute for PyTorch's DataLoader: batch order becomes a function of the seed alone and is identical on CPU and on GPU, so two runs of one seed differ only by whatever the backend's own arithmetic does — the smallest difference the project can arrange.

Each epoch: shuffle, iterate batches, forward, loss, backward, step, and check the loss is finite — a non-finite loss raises immediately with a message pointing at unclipped inputs or a runaway learning rate, rather than propagating nan through every subsequent number. Then a full validation pass, recorded as eight numbers including the two collapse columns. After epoch one it prints the cheap guards. If the epoch's ranking quality improved, it deep-copies the weights to the CPU and remembers that epoch's predictions; otherwise it increments a counter and stops once seven epochs have passed without improvement.

Two decisions inside are the ones worth being able to state. The loss is weighted by the ordinary-to-attack ratio, without which the cheapest route to a lower loss is to answer “benign” to everything. And selection is on ranking quality, not validation loss — validation loss is dominated by the 99.6% of rows nobody cares about and can improve for several epochs while the ranking gets worse. At the end it evaluates the best epoch's stored predictions rather than the last epoch's, so the reported metrics describe the checkpoint that was actually saved, then reloads those weights into the model before returning.

·The five functions to actually remember

Not the five most complex. The five where, if you got them wrong, the number at the end of the project would still look completely reasonable.

1
data.target_mask

Decides which days either model is allowed to be scored on: a person's twenty-eighth day onward. It is the only thing making the two models comparable — the twenty-eight-day model physically cannot score the earlier days, and those early days are warm-up rows where every feature is zero, the easiest negatives in the table. Let the one-day model keep them and it hands the other model about 6% of the headline metric for free, with no error and no warning.

2
data.prepare

Performs five steps in one fixed order — clip, mark judgeable days, split by person, measure the scaling on training rows only, apply it everywhere. Swap any two of them and you get a number rather than an exception: clipping after rescaling divides by a spread the outlier inflated; measuring before the split leaks validation statistics into training. This function is the argument that none of that happened.

3
data.WindowView.gather

Where the twenty-eight-day input is actually built, one batch at a time, out of the same array the one-day model reads. Two things ride on it: the window must end on the day being judged rather than the day before, and it must never cross from one person into the next. Both mistakes leave the tensor exactly the right shape, train without complaint, and answer a different question than the one being reported.

4
train.train_model

The loop, and it is deliberately incapable of knowing which model it is running — that is the reason Stage 6 added a class and touched nothing else. Two decisions inside it are the ones worth stating: the loss is weighted by the ordinary-to-attack ratio, without which the cheapest way to reduce loss is to answer “benign” to everything; and the epoch kept is the best-ranking one, not the last and not the lowest-loss one, because validation loss is dominated by the 99.6% of days nobody cares about.

5
metrics.PredictionStats.collapsed

The one guard against the failure that produces no error at all. A model that has given up and scores every day the same is 99.6% accurate, completely useless, and produces a loss curve that looks healthy the whole way down. Counting how many different scores come out is what catches it — thousands from a model that is genuinely ranking, a handful from one that has collapsed.

The honourable mention. test_the_shift_test_would_catch_a_feature_axis_convolution — a test whose only job is to prove another test isn't passing for free. The obvious way to check that the CNN convolves over time rather than over features (rising ramp vs. falling ramp) turns out not to discriminate at all, and this file says so in code rather than in a comment.
