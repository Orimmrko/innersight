Walk me through your code

The modules that ship in the final product, the design decisions inside them, and the specific lines you should be able to explain if someone points at them.

The one-sentence answer to “what does your code do?”

“It streams five raw activity logs totalling 16 GB, reduces every chunk immediately to per-(user, day) partial counts, and folds those partials into one table of 18 numbers per person per day — so that memory stays bounded by population × days rather than by the size of the input.”

There is no class hierarchy and no framework. The extraction is a set of pure functions plus one frozen dataclass. That is deliberate and is a defensible answer in itself: pure functions are testable without touching a filesystem, which is why the tests hand aggregate_log two two-row DataFrames while production hands it a generator over 28 million rows — down exactly the same code path.

Four layers, each independently testable. The top layer touches files; nothing below it does.

3 — config.py: one place for every constant

No path, threshold, domain list or magic number appears anywhere else in the project. That is worth saying out loud, because it is what makes a claim like “we changed the upload-domain list and re-ran” a one-line change rather than an archaeology exercise.

The most important thing in the file is not a path:

config.pyFEATURE_NAMES: Final[tuple[str, ...]] = (
    "logon_count",              # 0
    "logoff_count",             # 1
    ...
    "cloud_upload_visits",      # 17
)
Why this is the riskiest line in the project. That tuple order is not documentation — it is the input-vector layout. It becomes the CNN's channel order and the column order of every saved checkpoint. Reordering it raises no error and breaks no test; it silently makes every stored artifact score the wrong feature. The module docstring says so, and a unit test asserts the output column order matches it.

The file also encodes the dataset contract as frozen dataclasses:

config.py@dataclass(frozen=True, slots=True)
class LogSpec:
    filename: str
    columns: tuple[str, ...]
    expected_sample_rows: int

This is what lets the extractor validate a file's header against a declared contract before reading a single data row.

4 — extract.py: the design, decision by decision

4.1 The constraint that dictates everything

http.csv is 14.5 GB and 28.4 million rows. Nothing in this module ever holds a log in memory. The input is unbounded; the running state is bounded by population × days — roughly 500,000 rows for r4.2, which fits trivially.

If asked “why is it structured this way?”

“Because the input size is unbounded but the output size is not. A person can generate a million web requests, but they still only generate one row per day. So every chunk is reduced to per-(user, day) partials the moment it is read, and the raw rows are discarded. Memory is a function of how many people and how many days, never of how big the file is.”

4.2 The idea worth explaining first: sums vs distinct counts

This is the single most interesting piece of logic in the extraction, and it is where a naïve implementation is wrong silently.

extract.py@dataclass(frozen=True)
class LogPartial:
    sums: pd.DataFrame                    # additive — combining two is addition
    distinct: dict[str, pd.DataFrame]     # unique (user, day, value) triples

Sixteen of the eighteen features are counts or sums, so partial results from two chunks simply add. Two are not. unique_pcs_used and unique_filenames are distinct counts:

chunk 1:  AAA0001, 2010-01-04, PC-1       distinct count = 1
chunk 2:  AAA0001, 2010-01-04, PC-1       distinct count = 1
                                          ─────────────────
naïve sum                                 = 2      ✗ WRONG
truth: PC-1 seen twice is ONE distinct PC = 1      ✓

So distinct features never count per chunk. They keep unique (user, day, value) triples alive until the very end and count once:

extract.pydef _compact_distinct(parts: list[pd.DataFrame]) -> pd.DataFrame:
    """Concatenate and deduplicate triple frames -- never count in between."""
    return pd.concat(parts, ignore_index=True).drop_duplicates(ignore_index=True)
Why the memory cost is acceptable. The triples are bounded by real behaviour — a person uses a handful of machines a day, not thousands. And conveniently the log that is genuinely enormous needs no distinct counts at all: http.csv's three features are a row count and two URL tallies, so its memory cost is constant regardless of row count. The design and the data happen to agree.
How this bug would have presented itself. Not as a crash. Not as a NaN. As unique_pcs_used being slightly too large — and only in proportion to how many chunks a given user-day happened to straddle, which varies with chunk size. It is the exact class of defect that survives to the results table. That is why it is the first unit test.

4.3 The five builders are pure functions

extract.pydef build_logon_partial(chunk: pd.DataFrame) -> LogPartial:
    keys = _key_frame(chunk)
    when = chunk["date"].dt
    is_logon = chunk["activity"] == LOGON_ACTIVITY

    sums = _sum_by_key(keys, {
        "logon_count":        _count(is_logon),
        "logoff_count":       _count(chunk["activity"] == LOGOFF_ACTIVITY),
        "after_hours_logons": _count(is_logon & _after_hours(chunk)),
        "weekend_logons":     _count(is_logon & when.dayofweek.isin(WEEKEND_WEEKDAYS)),
    })
    return LogPartial(sums=sums,
                      distinct={"unique_pcs_used": _distinct_by_key(keys, chunk["pc"])})

Note is_logon & in both after-hours and weekend counts. Logons only, never logoffs — the logon at 02:00 is the anomaly, and counting its matching logoff would report the same event twice. There is a test for exactly that.

By contrast after_hours_usb counts any device event outside business hours, connect or disconnect, because a drive plugged in at 18:55 and pulled at 19:30 is one after-hours episode either way. Different rule, stated reason.

4.4 A dispatch table, checked at import

extract.pyLOG_FEATURES = {
    "logon":  ("logon_count", "logoff_count", "after_hours_logons",
               "weekend_logons", "unique_pcs_used"),
    "device": ("usb_connect_count", "usb_disconnect_count", "after_hours_usb"),
    ...
}

def _check_feature_partition() -> None:
    """Fail at import if LOG_FEATURES does not exactly partition FEATURE_NAMES."""

This runs at import time, not at call time. A feature owned by two logs would be silently overwritten during the join; a feature owned by none would be silently zero. Neither raises on its own — so the invariant is asserted where it cannot be skipped.

5 — The lines most likely to be questioned

The empty-list guard

extract.pydef _alternation(domains, name):
    if not domains:
        raise ExtractionError(
            f"config.{name} is empty. An empty URL list compiles to a pattern "
            f"that matches every URL, so every http row would count as a hit.")
    return "|".join(re.escape(domain.lower()) for domain in domains)

An empty regex alternation is "", which matches every string. If someone emptied JOB_SEARCH_DOMAINS, all 28 million http rows would count as job-site visits and the feature would look extremely informative. Explicitly refused.

The lookalike-domain regex

extract.py_INTERNAL_ADDRESS_PATTERN = rf"@{re.escape(INTERNAL_DOMAIN.lower())}(?![\w.-])"

The negative lookahead is doing real work. Without it, @dtaa.com.evil.net matches “internal” and an exfiltration address is counted as a colleague. There is a parametrised test for that exact string.

Detecting external recipients by counting, not splitting

extract.pyreturn recipients.str.count("@") > recipients.str.count(_INTERNAL_ADDRESS_PATTERN)

Every email address contains exactly one @. So “more @ signs than internal-domain matches” means at least one recipient is external — two vectorised regex counts instead of a per-row split, which matters across a 1.36 GB email log with 2.6 million rows.

And it scans to, cc and bcc. A mail addressed to a colleague and blind-copied to a personal account reads as entirely internal if you only look at to — which is precisely the exfiltration pattern scenario 2 is built around.

Nullable booleans must not propagate

extract.pydef _count(mask: pd.Series) -> pd.Series:
    return mask.astype("boolean").fillna(False).astype("int64")

Comparing against a column holding NA yields NA, not False. Here NA must mean “did not happen”, not “unknown” — a row with a missing activity value is not evidence of a logon. Going through the nullable boolean dtype first makes this correct for both plain numpy masks and nullable ones.

Cast after filling, never before

extract.pydaily = pd.DataFrame({...}, index=key_index).fillna(0)

# Cast last, after filling: an int64 column cannot hold the NaN that
# reindexing a missing (user, day) introduces.
for feature in FEATURE_NAMES:
    daily[feature] = daily[feature].astype("float64" if feature in FLOAT_FEATURES
                                           else "int64")

Reindexing onto the union key set introduces NaN wherever a log had no row. Casting to int64 before filling would raise; casting after is correct. total_email_size stays float64 deliberately — it is a byte total that overflows int32 and arrives from a nullable column.

Explicit date format, inference only as fallback

extract.pytry:
    chunk["date"] = pd.to_datetime(chunk["date"], format=DATE_FORMAT)
except (ValueError, TypeError):
    logger.warning(...)
    chunk["date"] = pd.to_datetime(chunk["date"], format="mixed")

The ordering is the point. format="mixed" re-infers the layout of every single row — unmeasurable on a 100-row test fixture and costing minutes across 28 million rows. This is a large part of why the full pass takes 90 seconds.

Validating the contract, then reading less than it

extract.pyheader = list(pd.read_csv(path, nrows=0).columns)   # full contract checked
...
reader = pd.read_csv(path, usecols=wanted, ...)     # projection actually read

The header is validated against the complete LogSpec before a single data row is read — so the contract is enforced in full — but only the three to six columns the builder needs are ever materialised. Never content, which is generated filler and most of the bytes on disk. This is the single largest performance decision in the module.

Why groupby dropping NA keys is wanted

extract.pyreturn keys.assign(**columns).groupby(KEY_COLUMNS, sort=False).sum()

pandas drops NA group keys by default. That is the correct behaviour here: a row with no user, or an unparseable date, cannot be attributed to anyone's day. It is counted for nobody rather than silently assigned to a NaN key that would later join onto something.

The compaction knob

extract.py_COMPACT_EVERY: Final[int] = 64

Partial frames are folded together every 64 chunks. Without it, a 14.5 GB file leaves hundreds of thousands of small DataFrames pinned in memory until the end. Purely a memory knob — the result is bit-identical either way, which is why the tests can pass compact_every=2 to exercise the folding path on three tiny chunks.

6 — Two kinds of checking, and why both exist

This distinction is worth being able to articulate; it is a genuinely good answer to “how do you know it works?”

Unit testsRuntime sanity checks

The checks deliberately do not raise. A surprising number is something to look at, not necessarily something wrong — and three of them exist specifically to confirm known r4.2 quirks are still present:

ok    no negative counts                 none
ok    no NaNs anywhere                   none
ok    no duplicate (user, day)           0 duplicates
ok    logons approx logoffs, not equal   470,591 logons vs 384,268 logoffs
 -    file_to_removable_count == file_count: True   (expected True on r4.2)
 -    unique_filenames == file_count: True          (expected True on r4.2)
 -    large_attachment_count total: 0               (expected 0 on r4.2)
The cleverest of those is “logons ≈ logoffs, not equal.” If they were exactly equal, something would be synthesising logoffs. If the ratio drifted far from 1, the activity filter would be broken. The dataset documentation states a small number of daily logons are intentionally not recorded to simulate dirty data — so a small mismatch is the expected state, and the check asserts the mismatch rather than the match.

The 9 tests, and why those 9

The test module's docstring names the criterion: cover the behaviours that are wrong silently — no exception, no NaN, just a number slightly too big — and would not be noticed until the results made no sense.

If asked “only nine tests?”

“Nine tests chosen by a stated criterion, not nine tests for coverage. Each one targets a failure that produces no error message — a distinct count that is slightly too high, a NaN that becomes a z-score, a column order that invalidates a checkpoint. Testing that logon_count counts logons would raise coverage and catch nothing, because that failure is obvious the first time you look at the output.”

7 — Questions to rehearse

Walk me through what happens when I run your extraction.

Five logs are streamed independently. For each, the header is validated against a declared contract, then only the needed columns are read in 50,000-row chunks with an explicit date format. Each chunk goes to a pure builder function that returns per-(user, day) partials — additive sums in one bucket, unique triples for the two distinct counts in another. Those partials are folded as they arrive, compacted every 64 chunks to bound memory. Finally the five per-log tables are joined on the union of their keys, missing values filled with zero, columns ordered by FEATURE_NAMES, and written to parquet. Then a report prints the totals and sanity checks.

Why not just load the CSVs with pandas and group by?

http.csv alone is 14.5 GB — it does not fit in memory, and even if it did, the content column that makes up most of it feeds no feature. The streaming design means memory is bounded by population × days rather than by input size, so the same code runs on a 30-user sample and on the full release without modification.

Which part of this was hardest to get right?

The two distinct counts. Every other feature is additive, so partial results just add — but unique_pcs_used and unique_filenames cannot be counted per chunk and then summed, because the same PC appearing in two chunks of one user-day is one PC, not two. They carry unique (user, day, value) triples to the end and count once. The failure mode is what makes it hard: no crash, no NaN, just a number slightly too large in proportion to how many chunks a user-day happened to straddle. It is the first unit test in the file.

How would this behave on a different CERT release?

The header contract is declared in config.LOG_SPECS and validated before reading, so a schema change fails immediately with a message naming the missing columns rather than producing wrong numbers. One case is handled explicitly: file.csv gains a to_removable_media column on r5+, and the builder uses it if present and otherwise counts every row — which is correct, because r4.2's readme states every file event already is a copy to removable media.

Is any of this code not yours?

The extraction was ported from an earlier, larger version of this project that was abandoned as over-scoped. The unmodified original is kept under extraction/salvage/provenance/ so the reuse is visible rather than claimed, alongside the validation evidence — the six checks run against it, the run logs, and the measured domain-hit counts. Everything asserted about its correctness was re-verified against the data rather than trusted, including the behavioural test that reproduces a known insider's timeline event for event.

Point at any line and ask “why is this here?”

Every non-obvious decision has a comment stating the reason, not the mechanism — 52 comment lines and a docstring on every public function across 881 lines. If a line looks arbitrary, the comment above it names the failure it prevents. Section 5 of this document collects the eight most likely candidates.

The closing line.

“The code is 1,400 lines with no classes holding state and no framework — five pure functions that turn a chunk into partial counts, one fold, one join. Its shape is dictated entirely by one fact: the input is 16 GB and the output is 2.8 MB, so nothing is ever held that scales with the input. Every decision that isn't obvious has a comment naming the failure it prevents, and the nine tests were chosen to cover the failures that would otherwise be silent.”
