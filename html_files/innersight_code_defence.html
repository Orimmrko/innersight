The code, in plain words

What the program does, why it's built this way, and the specific lines someone might point at and ask “why is this here?”

If you only remember one sentence about the code, remember this one.

The input is 16 GB. The output is 2.8 MB. So the program is built so it never holds anything that grows with the input — it reads a small slice, immediately shrinks it to daily counts, throws the slice away, and repeats.

There's no framework and no complicated class structure. It's a set of small functions, each of which takes something in and gives something back without changing anything else.

That's not just a style choice — it's why the tests can be simple. The tests hand the program two tiny fake tables, and the real run hands it 28 million rows, and both go through exactly the same code. Nothing has to be mocked or faked.

2How the program works, step by step

1.  Open one log file
2.  Check its column names match what we expect        ← fails loudly if not
3.  Read 50,000 rows at a time (never the whole file)
4.  For each batch: convert it into daily counts
5.  Add those counts to a running total
6.  Repeat for all five log files
7.  Join the five results together on (person, day)
8.  Fill any gaps with zero
9.  Save one file
10. Print a report with sanity checks

Steps 1–5 happen for each of the five log files independently. Steps 7–8 put them together. That's the whole program.

3The one clever bit: adding up vs counting different things

This is the most interesting part of the code, and the part where an obvious approach is wrong in a way that doesn't crash. If you learn one technical thing to talk about, learn this one.

Remember the program reads the file in batches of 50,000 rows. So one person's single day can be split across two batches.

For most of the 18 numbers, that's fine

batch 1:  Anna, Monday, 3 logins
batch 2:  Anna, Monday, 2 logins
                        ────────
total:                  5 logins    ✓ correct

You just add them. Sixteen of the eighteen numbers work like this.

For two of them, adding is wrong

Two of the numbers count different things, not how many times: "how many different computers did they use" and "how many different filenames".

batch 1:  Anna, Monday, used PC-1     →  1 different computer
batch 2:  Anna, Monday, used PC-1     →  1 different computer
                                         ─────────────────────
adding them gives                        2 different computers   ✗ WRONG
the truth is                             1 different computer    ✓

It's the same computer. Seeing it twice doesn't make it two computers.

How the code handles it

Those two numbers are never counted per batch. Instead the program keeps a list of unique (person, day, thing) combinations all the way to the end, removes duplicates, and only then counts.

extract.pydef _compact_distinct(parts):
    """Combine and remove duplicates -- never count in between."""
    return pd.concat(parts).drop_duplicates()
Why this matters so much. If you got this wrong, nothing would crash. There'd be no error message and no missing values. You'd just get a number that's slightly too big — and only for the people whose day happened to land on a batch boundary, which changes if you change the batch size. It would quietly survive all the way into your final results. That's why it's the very first automated test in the file.
A nice coincidence worth mentioning. Keeping those lists costs memory — but only a little, because a person uses a handful of computers a day, not thousands. And the one genuinely enormous file, the web log, needs none of this: its three numbers are all simple counting. So the expensive technique is only needed on the small files.

4The lines someone might point at

Each of these looks like a small detail. Each one prevents a specific failure. If an examiner points at any line in the file, the comment above it explains why it's there.

Refusing an empty website list

extract.pyif not domains:
    raise ExtractionError(
        "An empty URL list matches EVERY url, so every web request "
        "would count as a job-site visit.")

The problem: the way we search for websites, an empty list doesn't match nothing — it matches everything. If someone emptied the job-sites list, all 28 million web requests would count as job hunting, and that number would suddenly look incredibly useful. The code refuses to run instead.

Not being fooled by a fake company domain

extract.py@dtaa.com(?![\w.-])

The problem: the company's email domain is dtaa.com. An attacker could use an address like someone@dtaa.com.evil.net — which contains "dtaa.com" but is a completely different, external domain. Without that extra bit of pattern, the code would count it as an internal colleague. There's a test for that exact address.

Counting @ symbols instead of splitting addresses

extract.pyreturn recipients.str.count("@") > recipients.str.count(internal_pattern)

The idea: every email address has exactly one @. So if there are more @ symbols than company addresses, at least one recipient is outside the company.

Why do it that way: the alternative is splitting every address list apart row by row, across 2.6 million emails. Counting is one fast operation over the whole column instead.

And it checks to, cc and bcc. An email sent to a colleague and secretly blind-copied to a personal Gmail looks completely internal if you only check "to" — and that's exactly what attack type 2 does.

Treating "unknown" as "didn't happen"

extract.pyreturn mask.astype("boolean").fillna(False).astype("int64")

The problem: if a row has a missing value, comparing it to anything gives "unknown" rather than "no". Left alone, that "unknown" spreads through the calculation. Here a missing value should mean it didn't happen — a row with no recorded action is not evidence of a login. This line makes that explicit.

Filling gaps before converting to whole numbers

extract.py# Cast last, after filling: a whole-number column cannot hold the
# blank that joining a missing (user, day) introduces.
daily = frame.fillna(0)
for feature in FEATURE_NAMES:
    daily[feature] = daily[feature].astype("int64")

The problem: when we join the five log files together, a person-day present in one file and absent from another leaves a blank. Blanks can't be stored in a whole-number column. So we fill the blanks with zero first, then convert. Doing it the other way round crashes.

Telling the date reader what format to expect

extract.pytry:
    chunk["date"] = pd.to_datetime(chunk["date"], format=DATE_FORMAT)
except ValueError:
    chunk["date"] = pd.to_datetime(chunk["date"], format="mixed")

Why the order matters: if you don't tell the date reader the format, it works it out separately for every single row. On a 100-row test that's invisible. On 28 million rows it costs minutes. We tell it the format, and only fall back to guessing if that fails.

This is a large part of why the whole thing runs in 90 seconds.

Checking the whole file, but reading only part of it

extract.pyheader = pd.read_csv(path, nrows=0).columns     # check ALL expected columns exist
reader = pd.read_csv(path, usecols=wanted, ...)  # then read only the ones we need

Both halves matter. We check every expected column is present before reading a single row of data — so if the file is the wrong version, it fails immediately with a clear message instead of producing wrong numbers. But then we only actually load three to six columns, and never the "content" column, which is filler text making up most of the file size.

This is the single biggest speed decision in the program.

The printed checks deliberately don't stop the program. A surprising number is something to look at, not necessarily something broken. Here's what it prints:

ok    no negative counts                 none
ok    no missing values anywhere         none
ok    no duplicated (person, day)        0 duplicates
ok    logins roughly match logoffs       470,591 logins vs 384,268 logoffs
 -    files-to-USB equals file count     True    (expected on r4.2)
 -    unique filenames equals file count True    (expected on r4.2)
 -    big attachments total              0       (expected on r4.2)
The cleverest one is the logins/logoffs check. It requires them to be close but not equal. If they were exactly equal, something would be inventing logoffs that never happened. If they were wildly different, the filter would be broken. The dataset's documentation says a few logins are deliberately left out to simulate messy real-world data — so a small mismatch is the correct state, and the check tests for the mismatch rather than for a perfect match.

Why only 9 tests?

Because they were chosen by a rule, not for a coverage score. The rule is written at the top of the test file:

Test the things that would be wrong silently — no error, no crash, just a number that's a bit off and nobody notices until the results make no sense.

TestWhat it protects against
different computers not double-countedthe batch-boundary problem from section 3
after-hours counts logins onlycounting the matching logoff as a second event
missing days become zero, not blanka blank would break the next stage's maths
column order is fixedreordering silently breaks every saved model
external emails check to/cc/bcc4 cases including the fake-domain trick
empty input gives correct empty resulta malformed empty table crashing the next stage
If someone says “only nine tests?”

“Nine tests chosen by a rule, not nine tests chasing a coverage number. Each one targets a failure that produces no error message. Testing that the login counter counts logins would raise the coverage percentage and catch nothing — that failure is obvious the first time you look at the output.”

6The riskiest line in the whole project

config.pyFEATURE_NAMES = (
    "logon_count",              # 0
    "logoff_count",             # 1
    ...
    "cloud_upload_visits",      # 17
)

That list looks like documentation. It isn't. The order of those 18 names is the order the numbers go into the neural network. It's also the order stored inside every saved model file.

If someone reorders that list, nothing breaks. No error. No failed test. The program keeps running. But every saved model is now reading the wrong number for every feature — a model trained to react to "USB activity" would be reacting to "weekend logins" instead. The results would be nonsense and there'd be no clue why. That's why one of the nine tests does nothing but confirm the output columns come out in that exact order.

7Questions you'll get

Walk me through what happens when you run it.

It opens each of the five log files one at a time. For each, it first checks the column names are what we expect, then reads the file in slices of 50,000 rows, loading only the columns it actually needs. Each slice gets turned into daily counts straight away and the raw rows are thrown out. Those counts are added to a running total. At the end, the five results are joined together on person-and-day, gaps are filled with zero, and one file is saved. Then it prints a report with sanity checks.

Why not just load the files normally?

The biggest one is 14.5 GB — it doesn't fit in memory. And even if it did, most of it is a filler column we don't use. Reading in slices means the memory needed depends on how many people and how many days there are, not on how big the file is. That's why the same code runs on a 30-person test copy and on the full dataset without any changes.

What was the hardest part to get right?

The two "count different things" numbers. Every other number can just be added up across batches, but "how many different computers did this person use today" can't — the same computer appearing in two batches is still one computer. So those keep a list of unique combinations until the very end and count once. What makes it hard is the failure mode: no crash, no error, just a number that's slightly too big depending on where the batch boundaries happened to fall. It's the first test in the file for that reason.

What if you ran this on a different version of the dataset?

The expected column names are written down in the settings file and checked before reading anything, so a different version fails immediately with a message saying which columns are missing — rather than quietly producing wrong numbers. One case is already handled: newer versions have an extra column saying whether a file was copied to USB. If it's there we use it; if it isn't, we count every file copy, which is correct for this version because the documentation says every file event already is a USB copy.

Did you write all of this yourself?

The extraction code was adapted from an earlier, much larger version of this project that I abandoned as too complicated. The original file is kept unchanged in extraction/salvage/provenance/ so what was reused is visible rather than just claimed, along with the checks I ran on it. Nothing about it was taken on trust — including the test where I rebuilt a known attacker's timeline and compared it against the official answer key.

The sentence to finish on.

“It's about 1,400 lines with no framework and no complicated structure — five small functions that turn a batch of raw rows into daily counts, one loop that adds them up, and one join. The shape of it comes entirely from one fact: 16 GB goes in and 2.8 MB comes out, so nothing is ever held in memory that grows with the input. Every line that isn't obvious has a comment saying which mistake it's preventing.”
