Graduation project · CERT r4.2

InnerSight — the pipeline, stage by stage

Seven stages that turn 16 GB of raw activity logs into two trained neural networks and one comparison table.

The one idea: an insider does nothing forbidden — they do normal things at abnormal times, in abnormal amounts. So we never ask “is this action bad?” We ask “is this unlike them?” Every raw count becomes a z‑score against that person’s own history, and the networks learn from deviations, not from counts.

The seven stages

1

Extract

hours · run once
readslogon.csv · device.csv · file.csv
email.csv · http.csv  (~16 GB)
writesdaily_counts.csv
~500,000 rows · ~30 MB

Thirty million individual events get squeezed into 18 numbers per person per day. That’s the entire job.

user      day         logon  after_hrs  usb  files  http  jobsearch  ...
KPC0073   2010-07-05      2          0    0      0   412          0
KPC0073   2010-07-07      3          1    1      0   288          0
NGF0157   2010-07-07      2          0    0     14   533          0

How it survives 14.5 GB

  • Read in chunks. 50,000 rows at a time — never load a whole file.
  • Drop content at read time. It’s generated filler and feeds no feature. It is also most of the file size.
  • Parse dates with an explicit format (%m/%d/%Y %H:%M:%S). Letting pandas guess across 28 M rows costs minutes.
  • Sums combine across chunks; distinct counts don’t. The same PC seen in two chunks is one PC, not two — so those two features collect (user, day, value) triples and deduplicate at the end.
Design note. The keys are the union of (user, day) across all five logs. A missing value means zero, not NaN — “no USB events today” is an observation, not absent data. And a day with no activity at all still deserves a row: a resigned insider who stopped coming in produces exactly that pattern.
Do this first. Kick this off before anything else and let it run in the background while you build stages 2–7 against the 30-user sample. Waiting for it idle is the most likely way to lose a day.
2

Label

seconds
readsdaily_counts.csv
answers/insiders.csv
writes+ two columns: label, scenario

The raw logs contain no labels at all. Nothing in a logon row says good or bad. The truth lives in one separate file that names each insider and the window they were malicious in.

answers/insiders.csv
  dataset  scenario  user      start                end
  4.2      1         KPC0073   07/07/2010 20:05:29  07/15/2010 03:08:16

becomes

  user      day         ...   label   scenario
  KPC0073   2010-07-05  ...     0       -        ← before the window
  KPC0073   2010-07-08  ...     1       1        ← inside it
  NGF0157   2010-07-08  ...     0       -        ← not an insider

One row = one user-day. Label 1 if that day falls inside that user’s attack window, else 0. Carry the scenario number too — you need it in stage 7 to report per-scenario results.

Known imperfection, worth writing down. The published windows mark the signature event, not the full run-up. Insider BIH0745’s labelled window is 65 minutes long, yet his heaviest after-hours USB copying sits outside it. So some genuinely anomalous days are labelled benign, and your model gets “punished” for finding real anomalies. That is a property of the dataset, not a bug in your work — say so in the write-up.
3

Baseline — the z-scores

~1 minute
readsdaily_counts.csv (18 raw counts)
writesdataset.csv (18 z-scores + label)

This stage is the thesis. Everything else is plumbing around it.

For each user, walk their days in order. Score today against their own past, then absorb today into the running average:

for each day t, per feature:
    z[t]  = (count[t] - running_mean) / max(running_std, floor)   # score first
    running_mean, running_std  ←  update with count[t]            # then absorb

Why this works

Same raw number, two people, opposite meanings:

Persontheir normaltodayz-scorereading
Accountant, never used USB0 ± 03+20alarm
Hardware engineer4 ± 1.53−0.67Tuesday
  • Score before absorbing. Update first and today’s spike gets swallowed into the baseline it is measured against — it partly hides itself.
  • The standard-deviation floor stops division by zero for someone whose history is all zeros. That person’s z stays at exactly 0 while they do nothing, and explodes the first time they act. The zero is what makes the spike enormous.
  • No training here. This is arithmetic, so class imbalance cannot hurt it — the hardest part of the problem is solved before any network sees anything.
Leakage check. A user’s running mean only ever looks at their own earlier days, so it cannot leak the future. Give each user ~30 days of history before you trust their z-scores.

Split by user, never by day. If a user’s Monday is in train and his Tuesday is in test, the model has already met him — same person, same habits, same baseline. Your test score becomes fiction. Pick users; their days follow them.

Stratify by scenario as well as by insider/benign. There are only 10 scenario-3 insiders in the entire dataset, so a naive 20% test split can leave you with 2 — or 0.

Both models read this same file. If each script rolls its own split, the comparison in stage 7 means nothing.
5

Model A — the MLP

minutes
input(18,) — today’s z-scores, one user, one day
outputone probability · ~640 parameters
18  →  32  →  1        Adam, lr 1e-3, batch 256
                       BCEWithLogitsLoss(pos_weight ≈ 300)

It sees one day at a time. It can learn “high USB deviation together with high after-hours deviation is suspicious”, but it has no idea what yesterday looked like. That limitation is the point — it’s the control in your experiment.

The one thing that will silently kill this project. ~0.4% of rows are positive, so a model that answers “not malicious” to everything scores 99.6% accuracy and is worthless. pos_weight makes each positive count ~300× in the loss. Without it the model collapses to all-zeros within about two epochs, and the loss curve will look perfectly healthy while it happens.

Keep it small on purpose

You have ~1,700 positive user-days and ~640 parameters — roughly 2.6 positives per parameter, which is healthy. The instinct to make the network bigger because the problem is hard is exactly backwards here: a bigger network memorises those 1,700 rows and generalises to nothing.

Chapter · the central difficulty

The 0.4% problem

Out of roughly 500,000 user-days, about 1,700 are malicious. Everything hard about this project comes from that one ratio. This chapter is the theory of why it breaks a neural network — and then the concrete list of things the code has to do about it.

Part 1

Theory — why rarity breaks learning

1.1The numbers, exactly

QuantityValue
Total rows (user-days)~500,000
Positive rows (inside an attack window)~1,700
Negative rows~498,300
Positive rate0.34%
Ratio negative : positive≈ 293 : 1

Now translate that into what a training batch looks like. With batch_size = 256:

expected positives per batch  =  256 × 0.0034  =  0.87

→ the typical batch contains ZERO positive examples
→ roughly 4 batches in 10 contain exactly one
→ the model spends most of its updates being told only "say no"

That last line is the whole problem, and it is worth sitting with. This is not "the model sees few positives." It is most gradient updates contain no positive information at all.

1.2Why the model gives up — the gradient argument

Binary cross-entropy for one example, where y is the label and p the predicted probability:

L  =  −[ y·log(p)  +  (1−y)·log(1−p) ]

y = 1  (malicious) →  L = −log(p)        "push p UP"
y = 0  (benign)    →  L = −log(1−p)      "push p DOWN"

The batch loss is the average over all examples. In a batch of 256 with one positive, 255 examples say “down” and one says “up”. The arithmetic is not subtle: the cheapest way for the optimiser to reduce loss is to make every output small.

It works. Predicting p ≈ 0.003 everywhere drives the loss to a very low number very quickly, the gradients shrink to almost nothing, and the loss curve flattens into what looks like a beautifully converged model.

Why this is so dangerous. There is no error message. The loss goes down. The curve looks textbook. Accuracy reads 99.66%. Every dashboard you would normally trust says the training succeeded — and the model has learned to say “nobody is an insider”, which is 99.66% correct and 100% useless.

1.3The key insight: this is three problems, not one

Most people fix one of these and wonder why things still look broken. They are independent, and they have different fixes.

ProblemSymptomWhere it livesFix
1. Evaluation 99.66% accuracy on a useless model your metrics, not your model AUPRC · AUROC · P@50. Ban accuracy.
2. Decision model ranks well but flags nobody the threshold, not the weights pick the cutoff on validation, never 0.5
3. Optimisation minority class learned slowly / underfitted the loss function pos_weight in BCE

Problems 1 and 2 are mandatory and nearly free. Problem 3 is real but the most over-engineered — people reach for exotic sampling schemes when their actual issue was that they measured accuracy and thresholded at 0.5.

1.4The reframe that makes 0.4% survivable

You are not building a classifier. You are building a ranker. The goal is not to label 500,000 days correctly — it is to push the malicious ones to the top of a sorted list. A security analyst has time for 50 people a week, not half a million days.

This changes what “success” means. The model may be numerically “wrong” about thousands of days deep in the list and still be an excellent system, provided the real insiders surface near the top. AUPRC and precision@50 measure exactly that; accuracy measures something nobody cares about.

1.5The mathematics of the fix

Weighted binary cross-entropy adds one multiplier to the positive term:

L  =  −[ w·y·log(p)  +  (1−y)·log(1−p) ]

w  =  n_negatives / n_positives  ≈  293

Now a single positive example contributes as much gradient as 293 negatives. The batch of 256 that contained one positive and 255 negatives becomes, in gradient terms, roughly 293 vs 255 — a balanced argument instead of a rout. The “say no to everything” shortcut stops being cheap.

An alternative you should know the name of, focal loss:

FL  =  −α · (1 − p_t)^γ · log(p_t)          α ≈ 0.75,  γ = 2

The (1 − p_t)^γ term shrinks the contribution of examples the model already gets right, so the gradient concentrates on hard cases rather than on the ocean of obvious negatives. It often performs slightly better — at the cost of two extra hyperparameters to justify in your defense.

Recommendation. Use weighted BCE. Mention focal loss in the report as a considered alternative. One argument beats two hyperparameters when you have three days.

1.6The full toolkit, with honest verdicts

ApproachWhat it doesVerdict

1.7Why the popular fixes are wrong here

  • SMOTE. It invents new positives by interpolating between existing ones. Halfway between two insiders’ z-score vectors is a person who never existed and whose behaviour means nothing. Worse, synthetic rows have no user ID — so they cannot respect your user-level split, and they will leak across it.
  • Aggressive undersampling. Throwing away 95% of the benign days also throws away the variety of normal behaviour — which is precisely what the model needs in order to know what normal looks like.
  • “Just collect more positives.” There are 70 insiders. That is the dataset. r4.2 is already the dense release, deliberately unrealistic in insider density — the real world is far rarer, not less.
  • Accuracy, F1 at 0.5, or a confusion matrix at the default threshold. All three will tell you a broken model is fine.
Part 2

Practice — what the code must actually do

Not code — the list of decisions the code has to encode, grouped by where they live.

APreparing the data

  • Count positives and negatives per split, and print them. Before a single epoch runs. If the test split contains 0 positives, every metric you compute afterwards is undefined and you will not notice.
  • Compute pos_weight from the TRAINING split only. Computing it over the whole dataset uses test-set information to set a training hyperparameter. Small leak, real leak, easy to avoid.
  • Stratify the user split by scenario, not just by insider/benign. Only 10 scenario-3 insiders exist. A naive random split can hand you 0 of them in test, which silently deletes a third of your per-scenario results table.
  • Shuffle rows within the training set, never across the split boundary. Shuffling is for batch composition. Users must stay inside the group they were assigned to.

BThe loss

  • Use BCEWithLogitsLoss(pos_weight=…), not sigmoid followed by BCELoss. The fused version is numerically stable at the extreme probabilities this problem produces. The split version can produce NaN when p gets very close to 0 — which is exactly where your model will be operating.
  • The model outputs a raw logit. No sigmoid inside the model. The loss applies it internally. A sigmoid in both places silently squashes your outputs twice and the model will barely train.
  • Apply sigmoid manually only at evaluation time, when you need an actual probability to rank or threshold.

CThe training loop

  • Consider a larger batch — 512 instead of 256. At 0.34% positives, a batch of 512 expects ~1.7 positives instead of ~0.87. Fewer completely-negative batches means less noisy gradients. Cheap, since the model is tiny.
  • Log five numbers every epoch, not one: train loss · validation loss · validation AUPRC · validation P@50 · mean predicted score. The last one is your collapse detector.
  • Early-stop on validation AUPRC, not on validation loss. Loss is dominated by the 99.66% of rows you don’t care about. AUPRC is the thing you actually want maximised, so select on it directly.

DModel selection and the threshold

  • Keep the checkpoint from the best-AUPRC epoch, not the last epoch. Training past the optimum is normal; shipping the overfitted final weights is not.
  • Sweep thresholds on validation, pick the one maximising F1, and freeze it. Never assume 0.5. With a weighted loss the outputs are deliberately not calibrated around 0.5 — the weighting shifts them.
  • Save the threshold inside the checkpoint, next to the weights. A model without its threshold is not a working system. Recomputing it on test data at report time would be leakage.
  • Apply that frozen number to test. Once.

EGuards that catch silent failure

  • After epoch 1, print min / max / mean / std of the predicted scores. If max − min is near zero, the model has collapsed to a constant. This single check catches the failure this chapter is about.
  • Count the distinct predicted values. A healthy model produces thousands of distinct scores. A collapsed one produces a handful.
  • Assert that AUPRC beats the random baseline (the positive rate, ≈ 0.0034). Below that, something is genuinely wrong — inverted labels, a broken split, or a shuffled join.
  • Sanity-check by hand: score the known insiders in the test split. If KPC0073’s USB nights don’t rank near the top of his own timeline, no aggregate metric will save you.
  • Fix the seeds, and run 3 of them. With ~14 insiders in test, one landing differently swings your number visibly. Report mean ± std, not a single lucky run.

FWhat to report

  • The ablation: Model A with and without pos_weight. Five extra minutes of training and it turns an assertion into a measurement. Report AUPRC, P@50 and mean predicted score for both. Whatever the outcome, you tested it.
  • State the random baseline next to every AUPRC. “AUPRC 0.42 against a random baseline of 0.0034” is a defensible sentence. “AUPRC 0.42” alone means nothing to a reader.
  • Report per-scenario recall separately. Scenario 3 has ~20 positive days in the entire dataset. If it performs badly, the count is the explanation.

The one-line summary. Weight the loss so the minority can be heard, judge with AUPRC so you can tell whether it was, choose the threshold on validation so the model can act — and print the mean predicted score every epoch so that if it all silently fails, you find out in thirty seconds instead of on day four.

The rule that saves the deadline

Every stage writes a file. The next stage reads that file. Nothing recomputes.
Stage 1 takes hours. Stages 5–7 you will run twenty times while debugging. If the CNN script reaches back to the raw logs, every bug costs an afternoon.
