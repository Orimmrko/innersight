InnerSight · Stage 5 · defence preparation

The fair fight, and the number Model B has to beat

Stage 5 is two jobs in one. It builds the machinery both models share — so that the comparison at the end measures the one thing it is supposed to measure — and it trains the first of the two. What came out, what it means, and the answers to the questions you are likely to be asked. Written to be read out loud.

Say this first, if you say nothing else.

“The whole project is one comparison: two networks, identical data, identical settings, and one difference — Model A sees a single day, Model B sees the twenty-eight days ending on that day. If anything else differs between them, the result means nothing. Stage 5 is where I made sure nothing else differs, and then trained Model A to find out what one day is worth.”

“It is worth about thirty-five times random guessing. That is the number Model B has to beat, and it is measured, not assumed.”

1 — What Stage 5 does

Stages 1 to 4 produced a table: 464,687 person-days, eighteen z-scores each, a label saying whether that day was inside an attack, and a split assigning every person to train, validation or test. Nothing has been learned from it yet.

Stage 5 does four things:

  • Decides exactly which rows get scored, once, for both models — the decision that makes the final comparison honest or worthless.
  • Prepares the numbers — clip the extremes, then rescale each feature across the population.
  • Builds a training loop that does not know which model it is training, so Stage 6 can hand it a completely different architecture and change nothing else.
  • Trains Model A — one day in, one number out — across three seeds, and reports what it can do.
And one thing it deliberately does not do. It never opens the test split. Not once, not to peek. Stage 5 trains on train, selects on validation, reports validation. The test users are read out of the split file only in order to be ignored. Test is opened a single time, in Stage 7, for both models together — which is also why there is exactly one place in the whole codebase that reads it.

2 — The real job: making the fight fair

It is tempting to think of Stage 5 as “the training code”. It is not. The training loop is about eighty lines and there is nothing clever in it. The part that took the thinking is a set of three decisions that all have the same shape: get them wrong and you still get a number, a plausible one, with no error message anywhere.

2.1 — Rule one: one row set, for both models, for training and evaluation

Model B cannot score a person's first 27 days. There is no 28-day window ending there. So the obvious thing is to let Model A score them and let Model B skip them.

That obvious thing would have handed Model B roughly 6% of its result for free.

The rows Model B cannot see are the warm-up period — Stage 3 blanks everyone's first 30 days, because a baseline built from three days is fiction, so every feature on those rows is exactly zero. They are the easiest negatives in the entire table.

Remove 27,000 easy negatives and the positive rate rises from 0.407% to 0.432%. AUPRC rises with the positive rate mechanically — that is what the random baseline is. Model B would have scored about 6% higher than Model A while being no better at anything.

So the rule is written once and applied everywhere: within each person, only days from their 28th onward are ever predicted — by either model, for training and for evaluation alike.

rows                        464,687
masked out as warm-up        27,000   (5.8%)   = 1,000 people × 27 days
positives lost to the mask         0   ← measured on every run, not assumed

Zero positives lost, and that is not luck: the earliest attack window in r4.2 opens on 10 June 2010, about 160 days into everybody's record. The code measures and prints it on every run anyway, because “it cannot happen” is exactly the kind of statement that stops being true when a dataset is regenerated.

The distinction to have ready. The mask says which rows are predicted, not which rows are readable. Model B still reads the 27 days before each target to build its window — they are simply never themselves a thing it is asked about. That is why the code keeps each person's whole history in one array and carries positions into it, rather than pre-cutting a matrix of target rows.

2.2 — Rule two: clip the extremes before rescaling, not after

Stage 3's z-scores reach 716. The typical absolute z-score is 0.42. That is a single input roughly seventeen hundred times the normal magnitude.

The instinct is to fix this by standardising — subtract the mean, divide by the standard deviation, everything comes out around 1. It does not work, and the reason is worth being able to say:

Standardising a heavy tail makes it worse, not better. An outlier at 716 dominates that feature's standard deviation. Divide by that inflated number and every ordinary day in the feature is squashed toward zero — you have not removed the outlier, you have deleted everything else. So the clip comes first, at a fixed ±10 decided in advance, identical for train, validation and test.

It touches 2,138 rows — 0.46% of the table. The defence is one sentence: beyond ten standard deviations from a person's own baseline, the exact value carries no further information; it is equally off the charts.

2.3 — Rule three: fit the scaler on training rows only

Each of the eighteen features has its own typical magnitude, so the first layer of the network is handed a badly-conditioned problem unless they are put on a common scale. That rescaling is fitted on the training rows and then applied, unchanged, to validation and test.

This is not a second helping of Stage 3, and the difference is a likely question

They look similar and they are orthogonal. Merging them would make it impossible to say which normalisation the models are benefiting from — which is precisely why Stage 3 was kept separate.

Fitting on all rows instead would leak validation statistics into training. Nothing would complain; the number would simply be slightly, unaccountably better. There is a test for it that builds a validation split fifty times larger and shifted by a thousand, and asserts the fitted statistics do not move at all.

The line to use if asked why the order matters

“Load, clip, mask, split, fit on train, apply, build tensors — in exactly that order. Swap any two of those and you still get a trained model and a plausible number. Clip after standardising and you have rescaled by a deviation the outlier inflated. Fit before splitting and you have leaked. Mask after fitting and your scaler describes twenty-seven thousand rows that no model ever sees. None of those three raises an error. That is why the order lives in one function and the tests check it.”

3 — The loss: the most likely way this project fails

Positives are 0.4% of the data. A batch of 512 days contains, on average, 2.2 attack days.

Train that with an ordinary loss and roughly 510 examples say “predict lower” while two say “predict higher”. The cheapest way to reduce the loss is to output near-zero for everything. The model converges on “nobody is an insider” — which is 99.6% accurate and completely worthless.

And the loss curve looks perfectly healthy the whole time. There is no error, no warning, no missing value. Training loss goes down, validation loss goes down, everything looks like a model learning. It is the single most likely way this project produces a beautiful graph and nothing else.

The fix is to weight the rare class by how rare it is — n_negatives / n_positives, computed from the training split, at training time, on every run:

seed  42    pos_weight = 229.7    [263,462 negatives / 1,147 positives]
seed 123    pos_weight = 225.3    [260,841 negatives / 1,158 positives]
seed 456    pos_weight = 232.1    [259,723 negatives / 1,119 positives]

Three different numbers, because three different training splits. Hardcoding one value, or computing it from the whole table, would put the test set's class balance into the loss function — leakage, and of a kind nothing will ever flag.

A detail worth knowing before it is asked. The brief predicted this weight would be about 244; it came out about 230. That is correct and not a discrepancy: it is computed on the rows that are actually scored, after the warm-up mask, where the training positive rate is 0.43% rather than 0.41%. If a later stage ever prints 244, the mask is not being applied before the weight.

How we would know if it happened anyway

Every epoch prints five numbers, not one, and the last two exist solely to catch this:

epoch   train_loss   val_loss   val_AUPRC   val_P@50   mean_predicted_prob   distinct

A collapsed model gives every row essentially the same score. So the code counts distinct predicted values. In the real run it saw 84,067 to 87,393 distinct scores across 85,000–88,000 validation rows: essentially every day got its own number. A collapse would show single or double digits.

The ablation. Rather than assert any of this, the code has a --no-pos-weight switch that trains the identical model on the identical rows with a plain unweighted loss, writing to separate output files so it cannot overwrite the real result. It is the difference between “weighting the loss matters” and “weighting the loss matters, and here is the table”. This is the one measurement still outstanding at the time of writing — one command, about ninety seconds.

4 — Model A, and why it is deliberately tiny

18 inputs  →  32 hidden units (ReLU)  →  1 output        641 parameters

The output is a raw score, not a probability — the sigmoid lives inside the loss function, and putting a second one in the model would squash the output twice, shrink the gradients and leave it barely able to train, with no error and a merely disappointing curve.

The instinct to make the network bigger is backwards here, and this is a good thing to be asked.

There are about 1,140 attack days in the training split and 641 parameters — roughly 1.8 positive examples per parameter. That ratio is healthy. Double the network and the model has enough capacity to memorise those 1,140 rows individually, at which point it generalises to nothing and the validation score gets worse while the training loss gets better.

Model A is also the control arm. Its job is not to be the best possible one-day model; it is to be an honest measurement of what one day is worth, so that whatever Model B gains is attributable to temporal context rather than to capacity.

“The same predictions score 0.94 by the metric most insider-threat papers report, and 0.12 by the one that reflects what an analyst experiences. I report both, and I lead with the second. And the one genuinely encouraging number

P@50 = 0.573. Take the fifty highest-scoring days out of eighty-five thousand and about twenty-nine of them are real attack days. That is a usable queue built by a 641-parameter network that has never seen more than one day at a time. It is the number to lead with when asked whether any of this works.

7 — The finding nobody planned: the threshold is the unstable part

Per-scenario recall, at each seed's own chosen threshold:

Scenario 2 recall reads 40% → 20% → 9%. It looks like the model falling apart. It is not.

The ranking barely moved. The threshold moved.

AUPRC across those same three runs is 0.124, 0.169, 0.162 — a narrow band. What jumped is where the cut was placed: 0.958, then 0.974, then 0.994. Choosing a threshold by maximising F1 at 0.4% positives means searching a very flat, very noisy surface, so the winning point hops around even when the underlying model does not.

Seed 42 produces a system that raises two alerts a day and catches 40% of attack days at 12% precision. Seed 456 produces one that raises an alert every five days and catches 12% at 45% precision. Same architecture, same settings, same data — two entirely different products, and the difference is one number chosen on a noisy curve.

The reporting rule this forces, and it applies to Stage 7 as well. AUPRC is stable across seeds and may be quoted as mean ± standard deviation. Recall-at-a-threshold is not, and a single-seed per-scenario recall is a statement about the threshold lottery rather than about the model. Per-scenario results are therefore reported pooled across all three seeds, as counts.

Scenario 3 makes the same point in miniature. Every validation split contains exactly four scenario-3 attack days — arithmetic, not luck, because all ten of those insiders have precisely two attack days each. Recall on four rows has five possible values. “2 of 4 attack days” is honest; “50%” is a percentage doing an impression of a measurement.

8 — What this predicts about Model B

Model A's per-scenario pattern is the interesting part, because the three attack types are not equally suited to a one-day model.

  • Scenario 1 (40.5%) — someone leaving the company who uploads data on the way out. Often a single loud day. A one-day model can see this.
  • Scenario 2 (22.7%) — long, gradual behaviour change over weeks; the median window is around eight weeks. This is precisely what a one-day model cannot see, because each individual day is only mildly odd. It also supplies about 88% of all positives, so it dominates any unweighted average.
  • Scenario 3 (33.3%, 4 of 12) — two days, quiet, deliberate. Very few rows; treat any percentage here with suspicion.
The specific, falsifiable prediction to make before Stage 6 runs. If temporal context is worth anything, the gain should show up disproportionately in scenario 2 — the slow drift that only becomes visible as a trend across a month. If Model B improves scenario 1 and leaves scenario 2 where it is, then the 28-day window is adding capacity rather than context, and the honest conclusion is that the thesis was not supported. Writing that down in advance is what makes the eventual answer worth something.

9 — Weaknesses, said before anyone asks

The threshold selection is the weakest link

Covered in §7. F1-maximisation on this class balance is genuinely noisy. A stronger design would fix the operating point by budget — “the 500 highest-scoring days” — which is both more stable and closer to how an analyst team actually works. It is the first thing I would change with more time.

Seed 42 probably stopped a little early

Its best epoch was 16 and it stopped at 23, while the other two were still improving at 40 and 29. Its early AUPRC curve was noisy — 0.072 at epoch 4, then 0.052 at epoch 5 — so a patience of seven likely cut it short, which is the most probable reason it is the lowest of the three. Left as is deliberately: the rule is identical for both models, so it cannot bias the comparison it exists to serve.

The labels are windows, not events

Every day inside an attack window is labelled positive, including days the insider did nothing unusual. Some of what Model A “misses” is days that carry no signal to find. This inflates the apparent miss rate and there is no way to fix it without re-labelling by hand.

One dead feature

large_attachment_count is identically zero throughout r4.2. It survives into the model as a permanently silent input. Kept because the definition is right and the release simply lacks the data; the scaler handles it explicitly rather than dividing by nothing.

Validation is being used twice

It selects the stopping epoch and it selects the threshold, and then it is reported. That is mildly optimistic, and it is exactly why the test set exists and stays sealed until Stage 7. The honest framing: every number in this document is a selection number, not a final one.

And one guard that would refuse a good-looking result. If validation AUPRC ever came back above 0.95, the run stops and exits with an error code instead of writing a results file. At 0.4% positives with labels this coarse, near-perfect ranking does not mean success — it means leakage, most likely a split applied by row instead of by person. The program is written to treat its own best-ever number as a bug.

11 — Questions to rehearse

Your AUPRC is 0.15. That is not very good, is it?

Against a random baseline of 0.0043, so it is about thirty-five times better than chance — and the more useful way to say it is that of the fifty highest-scoring days out of eighty-five thousand, roughly twenty-nine are real attack days.

But I would not argue that 0.15 is good. Model A is the control arm. It sees one day at a time, and two of the three attack types in this dataset are defined by behaviour that plays out over weeks. The number I actually care about is the difference between this and Model B, because that difference is the thing the project set out to measure. A high number here would arguably have been a worse result — it would have meant temporal context had nothing to add.

Why not just report the AUROC of 0.94?

Because it would be misleading, and I can show why with the same predictions. 99.6% of days are ordinary. AUROC gives enormous credit for correctly ignoring eighty-five thousand of them. AUPRC only asks about the part of the ranking anyone would look at.

Concretely: that 0.94 model, at its chosen threshold, flags 1,168 days of which 143 are real. Roughly one alert in eight. Both numbers are in the report, and I lead with the honest one.

Why drop 27,000 rows? Isn't more data better?

Not when only one of the two models can use them. Model B has no 28-day window before someone's 28th day, so if Model A scored those rows and Model B did not, the two would be measured on different data and the comparison would be meaningless.

And the direction of the bias is not neutral. Those rows are Stage 3's warm-up, where every feature is exactly zero — the easiest negatives in the table. Dropping them lifts the positive rate from 0.407% to 0.432%, which lifts AUPRC mechanically. Model B would have collected about 6% for nothing. It costs 27,000 rows and, measured on every run, zero positives.

You standardised in Stage 3 and again in Stage 5. Isn't that doing the same thing twice?

They are orthogonal. Stage 3 normalises across time within a person — is this unusual for them. Stage 5 normalises across the population within a feature — are these eighteen inputs on scales the first layer can work with.

They are kept in separate stages on purpose, so it stays possible to say which one the models are benefiting from. And the Stage 5 one is fitted on the training rows only, then applied unchanged to validation and test; fitting it on everything would leak, and there is a test that would catch that.

How do you know the model didn't just learn to say “no” to everything?

Because that is the most likely failure mode at this class balance, so it is measured rather than hoped for. Every epoch logs the mean predicted probability and the number of distinct predicted values. A collapsed model gives nearly every row the same score.

The real run produced 84,000 to 87,000 distinct scores across 85,000 to 88,000 validation rows — essentially every day got its own number. There is also a guard that warns automatically if the count falls below a floor, and a test that feeds a deliberately degenerate model through the whole loop to prove the guard actually fires. Testing the alarm, not just the building.

Your scenario-2 recall is 40%, then 20%, then 9%. Which is it?

All three, and the spread is the finding. Across those same three runs the AUPRC is 0.124, 0.169 and 0.162 — a narrow band — so the model's ranking is stable. What moves is the threshold: 0.958, 0.974, 0.994, chosen by maximising F1 on a very flat surface at 0.4% positives.

So I report AUPRC as mean ± standard deviation, and per-scenario results pooled across all three seeds as counts — 225 of 990 attack days. Quoting one seed's per-scenario recall would be quoting the threshold lottery. It is also the first thing I would change with more time: fix the operating point by alert budget instead, which is both more stable and closer to how an analyst team works.

Why three seeds? Why not just run it once?

Because Stage 4 measured that the split alone moves the numbers a great deal — scenario-1 test positives swing from 32 to 56 across these three seeds, a 75% range, before any model exists. Attack windows differ enormously in length, so which insiders land in which split matters.

One run is one draw of that lottery. Generating several and keeping the tidiest would be selection on the results; reporting the spread across all three is the honest version, and here the spread is itself informative — it is what revealed the threshold instability.

What is the one thing most likely to be wrong with Stage 5?

The threshold selection, and I have said so in the write-up. Everything up to the ranking is tested and stable; the last step — converting a ranking into a yes/no decision — sits on a noisy surface and jumps between seeds.

The thing I was most worried about was the class weighting failing silently and producing a beautiful loss curve attached to a model that says “no” to everyone. That one is now measured on every run rather than assumed, which is why the distinct-value count is in the per-epoch log.

What has to be true for Stage 6's comparison to mean anything?

That the only difference between the two models is how many days each one sees. So the row set, the clipping, the scaler, the loss, the optimiser, the learning rate, the batch size, the stopping rule, the threshold procedure, the seeds and the hardware are all shared code, not shared intentions.

Concretely, the training loop takes a model object and never inspects it — there is nothing in it that knows whether it is training a small network on one day or a convolutional one on twenty-eight. Stage 6 adds an architecture and an entry point. If it ever needed to edit the training loop, the two models would not have been trained identically and I would have to say so.

The sentence to end on.

“Stage 5 is mostly not about Model A. It is about making sure that when Model B arrives, the two of them differ in exactly one way. Three decisions carry that — one row set for both models, clip before you rescale, and fit the scaler on training data only — and all three share the property that getting them wrong produces a perfectly plausible number and no error at all. Model A then answers the question the project needed answered first: one day of a person's behaviour, scored against their own history, is worth about thirty-five times random guessing, and finds roughly twenty-nine real attack days in its top fifty. Whatever Model B adds to that is the measured value of remembering the previous month.”
